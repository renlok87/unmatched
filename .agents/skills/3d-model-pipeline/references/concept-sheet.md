# Concept-sheet: строгие правила концепт-листа (этап 1 пайплайна 3D-модели)

> Reference skill-а `3d-model-pipeline`. Место в пайплайне: заявка (0) → **концепт-лист в Codex (1, этот
> файл)** → генерация в Tripo3D (2) → приёмка (3) → доработка в Blender (4) → H2-bake и look-dev (4.5) →
> анимация/VFX/SFX (5) → упаковка под UE (6).
>
> База правил — проверенный измерениями прогон ImageGen → Tripo (4 персонажа + 3 пропса, 36 видов):
> `docs/art-pipeline/imagegen-inputs/CONSISTENCY-REVIEW.md`, `checks-report.json`, `manifest.json`,
> `art/imagegen/mvp-v1/prompts/ref-king-arthur-v4-back.txt`. Всё внешнее (Tripo help, Layer.ai, Scenario и
> т. п.) помечено «(не проверено)». Статусы: **измерено** — число из прогона; **применено** — работало в
> проверенном потоке; **предложено** — правило этого документа, впервые применяется на следующем прогоне.

## 1. Вход этапа (из заявки, этап 0)

Обязательные поля asset card, без которых этап 1 не стартует:

| Поле | Пример |
|---|---|
| `ASSET_ID` | `ASSET-MEDUSA-001` (каталог `art/pipeline-candidates/ASSET-<NAME>-001`) |
| Роль (по анатомии, не по игровой роли) | `hero` = прямоходящий гуманоид; `creature` = не-гуманоид (крылатые, четвероногие, многоголовые — Цербер остаётся `creature`, даже если игра зовёт его «героем»); `prop` = неживой предмет. Определяет позу §4 и маршрут этапа 2 |
| Целевой полигонаж | POLY_BUDGET заявки: герой 15–25k треугольников, жёсткий потолок 45k; помощник 8–15k |
| Высота фигуры | FIGURE_HEIGHT_M заявки (игровой размер, м); концепт-лист держит одну шкалу роста во всех видах (800 px ± 3 %), метраж проверяется этапами 4.5/6 |
| Референсы | стиль, эталон качества (`art/imagegen/hero-quality-v1/reference/medusa-quality-reference.png` — единственный в репо; для нового ассета эталон утверждает пользователь на этапе 0) |
| UE-имена | `SK_<Hero>_…`, `AM_<Hero>_…`, `T_<Hero>_…` — на этапе 1 только фиксируются, не используются |
| Описание и якоря | внешность, костюм, материалы, оружие и рука (гуманоидам), поза, признаки силуэта, число голов/конечностей у не-гуманоидов |

## 2. Холст и сетка

Один вид = один файл. «Лист» (`sheet-…`, раздел 6) — отдельная сборка для приёмки, в Tripo не идёт.

| Параметр | Правило | Статус |
|---|---|---|
| Холст вида | ровно 1024×1024 px, PNG, RGB без альфы; ≤ 20 MB (фактически 0,17–0,66 MB) | измерено: CONSISTENCY-REVIEW.md:41 |
| Фон вида | однотонный `#808080` RGB(128,128,128), допуск ±12; рамка 16 px ≥ 99,9 % однородна | применено: checks-report.json → thresholdsProposed |
| Шаг сетки | 128 px (8×8 на 1024); решётка anchored к линии земли и центральной колонке x=512 | предложено (канонического шага нет ни в одном источнике) |
| Цвет линий сетки | `#00C8FF` (чистый голубой, не встречается в палитре) — только на листе и направляющих | применено в scratch-потоке: SCRATCH-MODEL-PIPELINE.md §3 |
| Линия земли | низ подставки на y=920 в промпте; после нормализации 917±2 у всех видов набора | измерено: CONSISTENCY-REVIEW.md:42; prompts/ref-king-arthur-v4-back.txt:4 |
| Рост фигуры | 6¼ клетки = 800 px от земли до макушки (без оружия), разброс между видами ≤ 3 % | измерено 787–812 px у четырёх героев (CONSISTENCY-REVIEW.md:75,86,104) |
| Верхняя граница | ничего выше y=102: поле ≥ 10 % с каждой стороны (FAIL < 2 %, WARN < 9,5 %) | применено; минимум прогона 10,3 % |
| Подставка | центр x≈512; ширина подставки в пределах ±3 % от целевой во всех видах | измерено: CONSISTENCY-REVIEW.md:43 |
| Направляющие | горизонтали ориентиров (макушка, глаза, подбородок, плечи, талия, колени, земля) сквозь все виды листа | внешняя практика layer.ai (не проверено) |
| Тонкие элементы | ≥ 2 % ширины кадра (≥ 21 px), иначе удалить | применено: prompts/ref-king-arthur-v4-back.txt:11 |
| Видимая сетка | только на листе `sheet-…` и в числах промпта (y=920). В файлах видов сетки нет: она ломает однородность рамки и попадает в геометрию Tripo («no text, logos or labels»; Sloyd/Modelfy о тексте и метках — не проверено) | правило этого документа |
| Единая шкала | один рост, одна линия земли, одна ширина подставки на всех видах; выравнивается программной **изотропной** нормализацией (анизотропия ≤ 1 % WARN). Раздельный масштаб X/Y запрещён: Harpy front, сжатый по Y на 3,6 %, дал задокументированную ошибку пропорций | измерено: CONSISTENCY-REVIEW.md:49; образец нормализатора `art/imagegen/mvp-v1/_tools/normalize-v4.py` (CONSISTENCY-REVIEW.md:163) |

## 3. Набор проекций и подача в Tripo multiview

Tripo Studio multiview имеет ровно 4 именованных слота `front/left/right/back`; слотов `top` и
`three-quarter` нет (применено: `tools/tripo-pipeline/check_inputs.py:68`; WARN `non-multiview-roles-present`
в CONSISTENCY-REVIEW.md:52). Практический оптимум — **3 вида из 4**: front + один профиль + back, второй
профильный слот пуст (применено ко всем четырём героям: CONSISTENCY-REVIEW.md:66,77,92,96,106,110).
Одно фронтальное изображение на чистом фоне даёт самый когерентный результат; вход ≥ 1024 px, ниже 512 px —
деградация геометрии, файл < 10 MB (tripo3d.ai help — не проверено; «2048×2048 ideal» — тоже не проверено,
локальный комплект 1024² был достаточен).

| Роль (имя файла) | Назначение | Подача в Tripo | Порядок |
|---|---|---|---|
| `front` | якорь дизайна; утверждается первым, все прочие виды перерисовываются от него | слот `front` | 1 |
| `left` | профиль: собственный левый бок персонажа к камере, лицо влево по кадру | слот `left` | 2 |
| `right` | второй профиль: только если детали оружейного борта (Merlin — посох в правой руке, подавался `right`) | слот `right` вместо `left` | 2 (вариант) |
| `back` | спина: плащ, колчан, крылья, капюшон | слот `back` | 3 |
| `three-quarter` | только человек и приёмка силуэта; слота нет | не подаётся | — |
| `top` (пропы) | только человек; по базовой линии не нормализуется | не подаётся | — |

Имя роли = имя слота Tripo (подтверждено только пилотом Medusa `d562f057`; для остальных персонажей
соответствие не перепроверено — `docs/art-pipeline/imagegen-inputs/manifest.json:6`). Пропы: `side`
кладётся в слот `left` (осесимметричные: бочка), асимметричная фурнитура — только `front`+`back`, пока
человек не подтвердит сторону (инцидент фонаря: петли против защёлки — CONSISTENCY-REVIEW.md:135-136).

## 4. Поза и ракурс

Общее для всех видов (дословные строки промпта — применено: prompts/ref-king-arthur-v4-back.txt:3,12):

> Strict orthographic projection, no perspective, camera at mid-height of the object, object centered.
> … View the disk precisely edge-on so no top ellipse is visible. Horizontal shoulder and base lines.

| Тип | Правило | Статус |
|---|---|---|
| Гуманоид (hero) | **A-pose**: руки ~45° от корпуса, ладони нейтрально, ноги на ширине плеч; оружие вертикально в анатомической ПРАВОЙ руке, левая пустая | требование этапа 2 (авториг/анимация Tripo); внешний консенсус «A-pose лучше деформаций плеч» — meshy/autorig/mocaponline (не проверено). Исторический прецедент mvp-v1 — нейтральная стойка не A/T (CONSISTENCY-REVIEW.md:70,85,100); риск слипания рук с одеждой там задокументирован — деформации плеч проверять на этапе 3/4 |
| Существо (creature, крылатое) | устойчивая поза на подставке, не A-pose; крылья отведены назад ~35–45° и «no extra wings»; для рига крыльев отдельная rest pose | применено к Harpy; угол 35–45° — оценка, PNG не подтверждает (CONSISTENCY-REVIEW.md:115) |
| Существо (creature, четвероногое/многоголовое — напр. Цербер) | естественная стойка: все четыре лапы на подставке, спина горизонтальна, центральная голова смотрит вперёд, боковые развёрнуты ≤ 45° от оси; хвост опущен нейтрально; число голов и их ракурсы — якорь во всех видах. «Оружие в руке» и A-pose не применяются | предложено (норма этого документа; четвероногих в проверенном прогоне mvp-v1 не было) |
| Проп (prop) | базовая ориентация вертикально; фурнитура полностью видна на front; минимум front+side, осесимметричным достаточно front | применено: бочка, фонарь, основание стола |

Запрещено: перспектива, 3/4 вместо профиля, зеркалирование файла («do not redesign or mirror»),
коллаж нескольких видов в одном кадре («never make a collage» — prompts/ref-king-arthur-v4-back.txt:2).

## 5. Свет, фон, палитра

Свет и фон (дословно, применено: prompts/ref-king-arthur-v4-back.txt:6-7):

> Plain uniform mid-gray background RGB(128,128,128), no gradient, no floor, no cast shadows, soft even
> frontal lighting, no rim light, no ambient occlusion darkening, no depth of field.

Внешние ограничения согласуются (не проверено): глубокие тени и жёсткие блики интерпретируются как
геометрия («shadows are the enemy», Sloyd); несколько источников света (Scenario); пёстрые фоны и текст
(Modelfy). Измеренный локальный риск: низкий контраст кромки силуэта к фону — если ≥ 10 % пикселей кромки
ближе 30 к `#808080`, автоснятие фона в Tripo съест часть кромки (применено: скала основания стола,
12,8–18 % — CONSISTENCY-REVIEW.md:51).

Палитра: **2–3 основных цвета + один акцент** (применено: prompts/ref-king-arthur-v4-back.txt:10).
Дрейф среднего цвета фигуры между видами ≤ 30 (порог `fgColorDriftWarn` — checks-report.json). Свотчи с
hex **прямо на листе**: полоса внизу `sheet-…`, каждая зона — квадрат цвета + hex-подпись; тот же список —
в `palette.json` сета. В файлах видов никаких подписей и свотчей нет.

## 6. Именование файлов и размещение

Сет концептов живёт в `art/imagegen/` по образцу существующих Codex-сетов (`env-v1`, `*-codex`):

```
art/imagegen/concept-v1-codex/                     # сет этапа 1 (имя — предложено)
  README.md                                        # статус сета, что принято, что открыто
  generation-inputs.json                           # реестр выбора (машиночитаемый)
  _tools/                                          # нормализация, сборка листа (Pillow)
  <content-key>/                                   # lowercase-kebab: medusa, king-arthur
    ref-<key>-v<N>-<view>.png                      # виды: front|left|right|back|three-quarter
    sheet-<key>-v<N>.png                           # лист: сетка + направляющие + свотчи
    palette.json                                   # зоны: hex
    prompts/ref-<key>-v<N>-<view>.txt              # точный отправленный промпт каждой попытки
    _jobs/ref-<key>-v<N>-<view>.json               # параметры вызова (без seed)
```

Правила (применено в mvp-v1): `ref-<персонаж>-v<версия>-<вид>.png`; новая попытка того же вида = `v<N+1>`;
исключённые кандидаты не удаляются — хранятся с причиной; замена фиксируется полем `supersededBy` в
**манифесте сета** (в mvp-v1 — `art/imagegen/mvp-v1/manifest.json`, дубль в
`docs/art-pipeline/imagegen-inputs/manifest.json`; в `generation-inputs.json` этого поля нет). В `generation-inputs.json` на каждый вид: `role`, `path`, `sha256`,
`width`, `height`. Запись job — только ключи `assetId/role/version/path/promptPath/refs/prompt`; seed не
используется и не записывается (проверено по `art/imagegen/mvp-v1/_jobs/ref-king-arthur-v4-back.json`).
Прогон этапа 2 пишется уже в `art/pipeline-candidates/ASSET-<NAME>-001/<run-id>/` по конвенциям PIPELINE.md.

## 7. Готовый промпт-пак для Codex

Вставляется в Codex как есть после заполнения `{{плейсхолдеров}}` из asset card. **Куда вставлять:** Codex —
отдельная внешняя агентская сессия пользователя с `image_gen`; этот скилл и запускающий агент её сами не
запускают и не имеют инструмента генерации изображений. Передача пакета — по образцу
`docs/art-pipeline/CODEX-2D-PACKAGE-PROMPT.md` (готовый «промпт-пак для Codex»; там же правило: Codex пишет
только в свою папку и не коммитит). В проверенном окне 2026-09-28 Codex imagegen не использовался и требовал
одобрения computer-use (`docs/art-pipeline/evidence/s3-baseline-2026-09-28/credits-ledger.json` →
`codexImagegen`) — запуск согласуется с пользователем; доступа нет → эскалация до этапа 1. Инструкции — по-русски;
промпт-ядро для `image_gen` — по-английски дословно (рабочий язык image-промптов проекта, эталон —
`art/imagegen/mvp-v1/prompts/ref-king-arthur-v4-back.txt`). Строки ядра менять нельзя, можно только
заполнять плейсхолдеры и блок REQUESTED VIEW.

```text
====================================================================
ЭТАП 1 ПАЙПЛАЙНА 3D-МОДЕЛИ UNMATCHED — КОНЦЕПТ-ЛИСТ ДЛЯ TRIPO3D
====================================================================
Ассет:    {{ASSET_ID}}
Роль:     {{ASSET_KIND}}            hero | creature | prop
Ключ:     {{CONTENT_KEY}}           lowercase-kebab
Описание: {{ASSET_DESCRIPTION}}     внешность, костюм, материалы, оружие и рука,
                                    поза, главные признаки силуэта
Палитра:  {{PALETTE}}               2–3 основных hex + 1 акцент
Якоря:    {{ANCHORS}}               что фиксирует идентичность между видами:
                                    оружие и рука, браслет и нога, точное число
                                    складок плаща, «no extra wings» у крылатых
Профиль:  {{PROFILE_SIDE}}          left (по умолчанию) | right (если ключевые
                                    детали на правом борту, как посох у Merlin)
Виды:     front, {{PROFILE_SIDE}}, back   (+ three-quarter — только референс)
Каталог:  art/imagegen/concept-v1-codex/{{CONTENT_KEY}}/

ПРАВИЛА ЭТАПА (нарушение любого = вид не зачитывается):
1. Один вид = один вызов image_gen = один PNG 1024x1024. Коллаж запрещён.
2. Порядок: front первым; front утверждается (проходит автопроверки и глазами)
   ДО генерации остальных. Каждый следующий вид — перерисовка ОДНОГО
   утверждённого front: referenced_image_paths = [утверждённый front];
   back дополнительно ссылается на готовый профиль вторым изображением.
3. Перерисовка = «rotate the SAME rigid figure and base, do not redesign or
   mirror». Редизайн, зеркалирование, смена позы запрещены.
4. Seed не использовать и не записывать. Job-JSON — только ключи
   assetId/role/version/path/promptPath/refs/prompt.
5. Пиксели результатов не править. Линию земли/масштаб выравнивает
   изотропная нормализация (образец art/imagegen/mvp-v1/_tools/normalize-v4.py),
   не ручная правка. Спецификацию под картинку не подгонять.
6. Писать только в свой каталог и в реестр сета. Не коммитить (решение
   пользователя 2026-10-05: Codex пишет только в свою папку и не коммитит).
7. Каждая попытка: prompts/<файл>.txt (точный промпт) + _jobs/<файл>.json.
8. После генерации: нормализовать все виды; собрать sheet-<key>-v<N>.png
   (виды в ряд на общей линии земли; горизонтальные направляющие ориентиров
   #00C8FF сквозь все виды; линейка шага 128 px; полоса свотчей с hex внизу);
   прогнать автопроверки порогов раздела «Чек-лист»; записать реестр.
9. Остановка: вид не проходит после 4 попыток; image_gen недоступен;
   описание противоречит референсам. Тогда README с числами и вопросами.

ПРОМПТ-ЯДРО (отправлять в image_gen дословно; {{…}} заполнить, остальное
не трогать; ANCHORS-блок составь по-английски из якорей ассета, по образцу
«upright straight sword in anatomical RIGHT hand, empty left hand»):
---
Redraw the attached concept as a production turnaround for image-to-3D generation.
Output a SINGLE separate square image exactly 1024x1024 for the requested view. The other
FRONT, LEFT SIDE, BACK, RIGHT SIDE views will be requested separately; never make a collage.
Strict orthographic projection, no perspective, camera at mid-height of the object, object centered.
Identical pose, proportions, scale and colors across the turnaround; bottom of the base on image
y=920 of 1024 in every view.
Whole object including base visible, nothing cropped, at least 10% margin on every side.
Plain uniform mid-gray background RGB(128,128,128), no gradient, no floor, no cast shadows,
soft even frontal lighting, no rim light, no ambient occlusion darkening, no depth of field.
Style: stylized tabletop miniature, matte hand-painted resin look, large simplified forms,
readable silhouette, low-poly friendly: remove chainmail rings, engravings, tiny emblems and
individual small feathers.
Keep 2-3 main colors plus one accent. No text, logos or labels.
Thin physical elements must be at least 2% of image width thick.
Neutral circular low dark charcoal stone base, flat smooth top, no cobbles, no colored team ring.
View the disk precisely edge-on so no top ellipse is visible. Horizontal shoulder and base lines.

Input is the APPROVED FRONT DESIGN. Rotate the SAME rigid figure and base to the requested view,
do not redesign or mirror. Keep exact proportions, {{PALETTE_EN}}. {{ANCHORS_EN}}.
Preserve all heights and base diameter. The top of the base must be invisible, edges horizontal,
no perspective.
REQUESTED VIEW: {{VIEW_BLOCK_EN}}
One isolated figure. Match the front image scale; leave at least 10% empty margin.
Output only this single view.
---

VIEW_BLOCK_EN по видам (дословно):
- front: FRONT: camera directly in front, face fully visible.
- left:  LEFT SIDE: the character's OWN left side faces the camera, head facing frame-left.
- right: RIGHT SIDE: the character's OWN right side faces the camera, head facing frame-right.
- back:  BACK: camera directly behind, back of head faces camera, no face visible. Item in the
  anatomical RIGHT hand appears to image RIGHT.
- three-quarter: THREE-QUARTER FRONT VIEW (human reference only, never sent to Tripo).

ПОЗА ПО РОЛИ:
- hero: A-pose, руки ~45° от корпуса, ноги на ширине плеч, оружие вертикально в правой
  руке, левая пустая.
- creature (крылатое): устойчивая поза на подставке; крылья назад 35–45°, «no extra wings»; не A-pose.
- creature (четвероногое, напр. Цербер): естественная стойка на четырёх лапах, спина
  горизонтальна, центральная голова вперёд, боковые ≤ 45°; число голов — якорь всех
  видов; оружие/A-pose не применяются.
- prop: базовая ориентация; фурнитура целиком на front; асимметричная фурнитура — боковые
  виды не подавать в Tripo до подтверждения человеком.

ВЕРНУТЬ: файлы видов + sheet + palette.json + prompts/ + _jobs/ + запись в
generation-inputs.json; до 10 строк: статус, версии видов, итог автопроверок, что не вышло.
====================================================================
```

## 8. Чек-лист приёмки концепт-листа

Проверяет та же модель-приёмщик, что на этапе 3 («Opus xhigh» или «Sol 6.1 xhigh»). Профили внешние
(SKILL.md §2): нет предоставленного пользователем способа их вызвать — остановка и эскалация до первой
приёмки, самостоятельно принимать лист запускающий не может. Сначала обязательны
автопроверки (0 FAIL на рекомендованных видах), затем рубрика. Автопроверки — пороги проверенного прогона
(`checks-report.json → thresholdsProposed`): канвас 1024×1024 PNG RGB ≤ 20 MB; фон RGB(128,128,128) ±12;
рамка 16 px ≥ 99,9 % однородна; поля FAIL < 2 % / WARN < 9,5 %; разброс базовой линии ≤ 2 px; ширина
подставки ±3 %; разброс высоты ≤ 3 % (WARN); анизотропия нормализации ≤ 1 % (WARN); кромка к фону < 10 %
пикселей ближе 30 (WARN); дрейф среднего цвета фигуры ≤ 30. Скрипт-эталон
`python tools/tripo-pipeline/check_inputs.py --check-only` жёстко читает `art/imagegen/mvp-v1`
(check_inputs.py:44) — на новом сете он не работает. Для нового сета запускающий агент ДО приёмки создаёт
`<сет>/_tools/check_views.py`: порт `check_inputs.py` с параметром корня (каталог сета) и теми же порогами
`checks-report.json → thresholdsProposed`; гейт «0 FAIL» считается по этому скрипту. Готового проверочного
скрипта в `_tools/` сета изначально нет (там нормализация и сборка листа) — его пишет запускающий агент;
правка самого `tools/tripo-pipeline/check_inputs.py` (параметр корня) — отдельная задача репозитория, прогон
она не блокирует.

Автопроверки (скриптом, до модели):

- [ ] Каждый рекомендованный вид: PNG RGB 1024×1024, без альфы, ≤ 20 MB
- [ ] Фон `#808080` ±12 по всем видам; рамка 16 px однородна ≥ 99,9 %
- [ ] Поля ≥ 10 % с каждой стороны во всех видах; ничего не обрезано
- [ ] Базовая линия у всех видов набора в пределах 2 px; центр подставки x≈512
- [ ] Ширина подставки ±3 % от целевой; разброс высоты фигуры ≤ 3 %
- [ ] Нормализация изотропная (анизотропия ≤ 1 %); цветовой дрейф фигуры ≤ 30
- [ ] Реестр `generation-inputs.json`: у каждого вида role/path/sha256/размеры; исключённые
      кандидаты с причиной; замены с `supersededBy`
- [ ] Каждая попытка имеет prompts/*.txt и _jobs/*.json; seed в job-записях отсутствует

Приёмка моделью (глаза + рубрика; лист открывать как картинку, не по трассировке):

- [ ] Все виды строго ортогональны: нет перспективы, камера на средней высоте, объект центрирован,
      подставка в ребро (верхний эллипс не виден), линии плеч и земли горизонтальны
- [ ] Один и тот же персонаж во всех видах: поза, пропорции, костюм, цвета; никакого редизайна и
      зеркалирования («rotate the SAME rigid figure»)
- [ ] Якоря сходятся во всех видах: оружие в той же анатомической руке (front слева в кадре / back
      справа в кадре), браслет на той же ноге, то же число складок/голов/перьев; у крылатых —
      «no extra wings»
- [ ] Соглашение сторон: left = собственный левый бок персонажа к камере (проверка по оружию/браслету)
- [ ] Поза по роли: hero — A-pose ~45°; creature — устойчивая (крылья назад без двоения; четвероногие —
      стойка на четырёх лапах, головы вперёд, число голов сходится по видам); prop —
      фурнитура читается на front
- [ ] Свет плоский: нет падающих теней, rim, AO, DOF, градиента фона, пола
- [ ] Палитра = заявленной (2–3 + акцент); свотчи с hex на листе совпадают с цветами фигуры
- [ ] Силуэт low-poly дружелюбен: мелочь (кольчуга, гравировки, мелкие перья) убрана; тонкие
      элементы ≥ 2 % ширины кадра; ничего не слиплось в нечитаемую массу
- [ ] На листе: виды на одной линии земли, направляющие ориентиров проходят через одни и те же
      точки всех видов; рост 800 px ±3 %; поля ≥ 10 %
- [ ] Комплектность подачи: front + профиль + back чистые; three-quarter/top в подачу не попали;
      коллажей нет

Рубрика (коэффициент 0–10, порог прохода **8.0** — та же шкала, что на этапе 3):

| # | Критерий | Вес |
|---|---|---:|
| 1 | Ракурс и ортогональность (перспектива, ракурс, подставка в ребро) | 2.0 |
| 2 | Межвидовая консистентность (якоря, поза, пропорции, IoU-ориентир front↔зеркальный back 0,89–0,94 — измерено по четырём героям) | 2.5 |
| 3 | Масштаб и выравнивание (земля, рост ±3 %, подставка ±3 %, поля) | 1.5 |
| 4 | Палитра (соответствие заявленной, дрейф ≤ 30, свотчи на листе) | 1.5 |
| 5 | Силуэт и low-poly-дружелюбность | 1.5 |
| 6 | Гигиена холста и файлов (фон, одна фигура, нейминг, реестр) | 1.0 |

Коэффициент = Σ(оценка критерия 0–10 / 10 × вес). Любой критерий ≤ 3 — провал листа независимо от
суммы (грязный фон, коллаж, редизайн между видами). Ориентир IoU не заменяет глаза: высокое значение
не подтверждает геометрию (CONSISTENCY-REVIEW.md:54).

## 9. Протокол перегенерации при провале

Максимум **3 цикла** перегенерации после первой приёмки (итого до 4 приёмок листа), затем эскалация
пользователю. Обоснование N=3: доработка в Blender (этап 4) допускает 2 цикла — там ручная работа;
дешёвая генерация видов в проверенном scratch-потоке допускала 4 попытки на вид; концепт-лист между
ними — генерация дешёвая, но каждый цикл тратит приёмку модели.

1. Автопроверки FAIL → перегенерация вида **до** передачи листа модели-приёмщику (цикл не тратится).
2. Провал рубрики → перечитать замечания приёмщика; перегенерировать ТОЛЬКО провальные виды. Не-фронтальные
   виды перерисовываются от утверждённого front по промпт-ядру с уточнённым REQUESTED VIEW.
3. Провал front → сначала front, затем **все** зависимые виды заново (они определяются от front).
4. На один вид — не более 4 попыток генерации суммарно за этап (прецедент scratch-потока).
5. При недоказанном противоречии видов не перегенерировать вслепую: сначала определить дефектный вид
   (прецедент Harpy — двоение крыльев не подтвердилось, а ретрай был бы пустой тратой:
   CONSISTENCY-REVIEW.md:121, harpy-candidate-report.md).
6. Каждый цикл: обновить реестр (новые версии `v<N+1>`, старые — `supersededBy`), записать промпты и
   job-файлы попыток, повторить автопроверки и приёмку целиком (не только провальный критерий).
7. После 3-го проваленного цикла — стоп, эскалация пользователю: лист, числа рубрики и автопроверок по
   циклам, что решать (ослабить требование, сменить референс, отдать в Blender минуя порог).
