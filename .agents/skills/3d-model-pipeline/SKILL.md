# 3D-model-pipeline

Этот файл — навигация и решения; тяжёлые детали живут в `references/` и открываются на нужном этапе.
Числа сверены с файлами репозитория (источники — в концах справочников); внешние веб-факты помечены
«(не проверено)».

## 1. Когда использовать — и когда нет

Использовать: новая модель под игровой ассет — новый герой, существо или проп, от заявки (этап 0) до
ассетов в `/Game/PipelineCandidates/<Key>/`. Любой триггер из описания = запуск этого пайплайна.

НЕ использовать: разовые правки существующих ассетов (перекраска MI, замена текстуры, правка одного
клипа, перестановка пропа) — они идут обычной задачей репозитория, без заявки и концепт-листа. Новая
смысловая деталь существующей модели = новая заявка этапа 0, а не цикл правки.

## 2. Роли

| Роль | Кто | Зона ответственности |
|---|---|---|
| Запускающий агент | сессия, начавшая прогон | оркестрация этапов 0–6, выбор профиля приёмщика, evidence и коммиты, приём эскалаций |
| Codex | генератор концептов | этап 1: модельный лист по промпт-паку; пишет только в свой каталог `art/imagegen/...`, не коммитит |
| Tripo3D Studio | генерация | этап 2: multi-view → 3D, сегментация, ретопология, текстуры; вручную в браузере, одна вкладка на ассет |
| Приёмщик | модель «Opus xhigh» (дефолт) или «Sol 6.1 xhigh» (по выбору запускающего) | этапы 3 и 5: коэффициент 0–10 по рубрике; модель не правит |
| Исполнитель доработки | всегда лично «Opus xhigh» | этапы 4 и 4.5: правки в Blender по брифу из карточки; не делегируется |

Codex, приёмщик и исполнитель — ВНЕШНИЕ исполнители, не инструменты этого скилла; скилл не содержит
команды их запуска. Как они подключаются:
- **Codex** — отдельная агентская сессия пользователя с `image_gen`; промпт-пак §7 `references/concept-sheet.md`
  передаётся в неё целиком (образец такой передачи — `docs/art-pipeline/CODEX-2D-PACKAGE-PROMPT.md`; там же
  правило «пишет только в свою папку и не коммитит»). В проверенном окне 2026-09-28 Codex imagegen не
  использовался и требовал одобрения computer-use (`credits-ledger.json` → `codexImagegen`).
- **Приёмщик / исполнитель** — внешние профили моделей; способ вызова предоставляет пользователь (своя сессия,
  CLI, инструмент). Конфигурация профилей в репозитории не зафиксирована (не проверено).
- **Tripo Studio** — работа в браузере; прецедент проверенных прогонов — «Claude in Chrome», своя вкладка
  (`docs/art-pipeline/ADDING-AN-ASSET.md` §2 п. 1). Конкретный инструмент автоматизации скилл не фиксирует.

Правила ролей: приёмщик не правит; повторная приёмка — тем же профилем, что первая; вердикт — только по
свежим рендерам, не по отчёту исполнителя. **Доступность внешних исполнителей проверяется до первого их
шага**: нет предоставленного пользователем способа вызвать Codex, приёмщика или открыть Studio — остановка
и эскалация пользователю (этап 1 — концепт, этап 3 — первая приёмка, этап 2 — первая платная операция).
Подменять внешнего исполнителя самим запускающим запрещено: агент не принимает свою же работу и не
«кликает за пользователя» без его ведома.

## 3. Карта пайплайна

0. **Заявка** — asset card фиксирует ID, роль, риг-совместимость, полигонаж, высоту, референсы, UE-имена;
без неё этап 1 не стартует; непокрытая контрактом анатомия и отсутствующие внешние решения — эскалация здесь же.
1. **Концепт в Codex** — ортогональные виды 1024×1024 на `#808080` по промпт-паку; приёмка рубрикой ≥ 8.0.
2. **Генерация в Tripo3D** — модель по маршруту роли, сегментация/ретопология/текстуры, экспорт GLB + source-spec.
3. **Приёмка** — 10 рендеров, рубрика 5 измерений, карточка JSON; маршрут по порогам 8.0 / 5.0.
4. **Доработка в Blender** — лично «Opus xhigh», только пункты карточки, максимум 2 цикла.
4.5. **H2-bake и look-dev** — high-poly поколение H2 (маршрут B этапа 2) → bake high→low, MatID/Edge/
TeamAccent/LUT, MI от мастеров; выход `SK_<Hero>_H2.fbx` + H2LD-набор — вход этапов 5–6.
5. **Анимация и VFX/SFX** — риг UM_HUMANOID_17_v2 (только гуманоидная анатомия — гейт RIG этапа 0),
клипы, сокеты, CUE-реестр; приёмка ≥ 8.0.
6. **Упаковка под UE** — FBX по UM_FBX_v1, текстуры ORM, импорт, валидация, реестр.

## 4. По этапам

### Этап 0. Заявка (asset card)

Заполни шаблон §6 — обязательны все поля. Создай каталог ассета `art/pipeline-candidates/ASSET-<NAME>-001/`
(структура — §7) и сохрани карточку файлом `asset-card.yaml` в его корне (норма этого скилла: у существующих
ассетов карточек-файлов нет — они старше скилла; этап 3 ищет заявку именно по этому пути).
Переход дальше: карточка заполнена, сохранена как `ASSET_DIR/asset-card.yaml` и все её решения (RIG-гейт,
FIGURE_HEIGHT_M, эталон качества, UE-имена) получены или эскалированы.

### Этап 1. Концепт-лист в Codex

Открой `references/concept-sheet.md`: готовый промпт-пак с `{{плейсхолдерами}}`, правила холста и сетки
(1024×1024, фон `#808080`, линия земли y=920, рост 800 px ± 3 %), контракт слотов Tripo
(front/left/right/back, оптимум 3 вида) и чек-лист приёмки листа.
Ключевое: front утверждается первым, все прочие виды — перерисовки одного front («rotate the SAME rigid
figure»); в файлах видов нет сетки, свотчей и подписей; нормализация изотропная; до 4 попыток генерации
на вид, максимум 3 цикла перегенерации после первой приёмки.
Переход дальше: автопроверки 0 FAIL и коэффициент рубрики ≥ 8.0; после 3 проваленных циклов — эскалация.

### Этап 2. Генерация в Tripo3D

Открой `references/tripo3d-stages.md`: маршруты по ролям (герой h31 ≈ 190–210 studio-credits; H2
high-poly 65; существо — маршрут героя; проп — одно изображение), все стадии API v3 (не проверено),
цены Studio, структура прогона, типовые ошибки.
Ключевое: рабочий путь — Studio вручную; локальный CLI `tools/tripo-pipeline/tripo_pipeline.py` начинает
с `prepare-generation --dry-run`; порядок: генерация → сегментация → ретопология (цель ≈ 0,5× бюджета,
факт ×1,9–2,2) → одночастная ветка Smart UV через клон → экспорт GLB всех состояний; журнал кредитов —
сразу после каждой операции.
Переход дальше: чек-лист §11 справочника — sha256 и байты в `reports/tripo-run.json`, source-spec
`unmatched.tripo-pipeline.source-spec/1`, `claims.art_accepted: false` (приёмку ставит только этап 3).

### Этап 3. Приёмка (коэффициент)

Открой `references/acceptance-and-blender.md`: обязательный набор из 10 рендеров (8 ракурсов turntable +
2 крупных плана, JPEG 1200 q92), рубрика 5 измерений по 2 балла с якорями 0–2, карточка схемы
`unmatched.art-acceptance/1`.
Ключевое: приёмщик смотрит картинки, а не отчёты; карточка и кадры — в
`art/pipeline-candidates/<ASSET-ID>/evidence/acceptance/<ГГГГММДД>-r<N>/`; числа отчётов — справочные.
Переход дальше: ≥ 8.0 → этап 4.5 (H2-bake и look-dev), затем этап 5; 5.0–7.9 → этап 4; < 5.0 → возврат на этап 1/2. Без рига пороги
пропорциональны максимуму 8: ≥ 6.4 / 4.0–6.3 / < 4.0.

### Этап 4. Доработка в Blender

Тот же справочник `references/acceptance-and-blender.md` (§8–§10): список правок строится только из
измерений карточки ниже 80 % максимума (< 1,6 из 2); типовые правки привязаны к инструментам репозитория
(`candidate_build/`, `pack_segmented_atlas.py`, пресет UM_FBX_v1, риг UM_HUMANOID_17_v2); шаблон брифа — §10.
Ключевое: исполнитель — всегда «Opus xhigh»; правки выражаются кодом и профилем, а не кликами GUI;
силуэт, пропорции и палитру концепта не править никогда (это возврат на этап 1/2); исходники Tripo
только читаются.
Переход дальше: повторная приёмка ≥ 8.0; максимум 2 цикла (`r1`→`r2`→`r3`), дальше — эскалация
пользователю с пакетом карточек и кадров.

### Этап 4.5. H2-bake и look-dev

Между принятой кандидат-моделью (этапы 3/4) и входом этапа 5 стоит обязательный конвейер high-poly
проработки: `<дата>-h2-tripo → -h2-bake → -h2-lookdev` (run-каталоги: у Arthur/Merlin/Medusa —
`20260929-h2-*`; у Harpy look-dev делала вторая generation — `20260929-h3-tripo → -h3-bake →
-h3-lookdev`, каталога `h2-lookdev` у неё нет; HANDBOOK §4.2–4.5). Шаги: high-poly поколение H2 в Tripo
(маршрут B справочника этапа 2, ~65 studio-credits) → bake high→low в Blender → look-dev: карты
MatID/Edge/TeamAccent, LUT, MI от мастеров.
Исполнитель — тот же внешний профиль, что на этапе 4; правки кодом и профилем, headless.
Выход: `SK_<Hero>_H2.fbx` (цель спеки h2anim этапа 5) и H2LD-меш + текстуры (вход этапа 6).
Суффикс стадии `H<N>LD` = номер ПОСЛЕДНЕГО high-poly поколения ассета: первое — H2 (Arthur, Merlin,
Medusa → `H2LD`), следующее поднимает номер (Harpy прошла второе — `H3LD`); маршрут генерации кандидата
(h31) на суффикс не влияет. Смена поколения = смена UE-имён (этап 0 поле UE_NAMES) и правка C++/реестров.
Переход дальше: look-dev-набор собран и сверен съёмкой зон против концепта; H2LD-имена зафиксированы.

### Этап 5. Анимация, VFX, SFX

Открой `references/animation-vfx-sfx.md`: скелетный стандарт UM_HUMANOID_17_v2 (иерархия, единицы,
root motion), базовый набор D-11 — 4 клипа × 4 героя, fps 24, notify `Contact`; конвейер H2Anim с
командами; VFX (сокеты создаёт UE-импорт, реестр CUE→Niagara, детерминизм) и SFX (нейминг `SW_`/`MS_`,
микс, правило «звук на CUE, notify — только тайминг»).
Ключевое: один FBX на клип, обязательно с узлом меша; сокеты в Blender не делаются; новый ролевой клип —
только под конкретную игровую потребность (слот в `clip-manifest.json` + спека + C++ + `cue-table.json`
+ реестр 03).
Переход дальше: валидаторы PASS (это не приёмка) и коэффициент ≥ 8.0; максимум 2 цикла правок.

### Этап 6. Упаковка под UE

Открой `references/ue-import-package.md`: пресет UM_FBX_v1 (таблица параметров), раздельные
`SK_`/`SM_`/`AM_` (клип — обязательно с узлом меша), текстуры «ORM, не RM», структура
`/Game/PipelineCandidates/<Key>/`, порядок импорта, чек-лист валидации, 3 правки подключения в игру и
13 типовых ловушек.
Ключевое: Import Uniform Scale = 1.0, Import Materials = false (MI делаются от мастеров); меш сажается
на канонический скелет через skeletal-adopt (`ue.target_skeleton`); UE-шаги — под блокировкой
`C:/tmp/ue-editor.lock`.
Переход дальше: `ue-import-report.json` — все checks passed; автотесты; снимок до/после
`protected_unchanged: true`; реестр `03-asset-registry.csv` обновлён.

## 5. Дефолты и точки решения

| Точка | Дефолт | Альтернатива / граница |
|---|---|---|
| Профиль приёмщика (этапы 3, 5) | «Opus xhigh» | «Sol 6.1 xhigh» по явному выбору запускающего; повторная приёмка — тем же профилем |
| Порог приёмки | 8.0 / 10 | без рига 6.4; 5.0–7.9 (без рига 4.0–6.3) → Blender; ниже — возврат на этап 1/2 |
| Циклы концепт-листа (этап 1) | максимум 3 перегенерации после первой приёмки | дальше — эскалация пользователю |
| Циклы доработки (этапы 4, 5) | максимум 2 «правка → повторная приёмка» | третья правка не запускается — эскалация с динамикой коэффициента по карточкам |
| Бюджет Tripo | ~400 studio-credits на героя (потолок); окно автономии 300 | цена считывается с кнопки ДО клика; не хватает остатка — стоп; две неудачные генерации подряд — стоп |
| Повторная генерация тех же входов | запрещена (`prepare-generation` — код 3) | только `--allow-duplicate --duplicate-reason "…"` |
| Риг | в Blender по контракту UM_HUMANOID_17_v2 | Tripo-авториг не используется; если когда-нибудь — строго после финальной топологии |
| Прогоны и профили | всегда НОВЫЙ run-каталог и НОВЫЙ файл профиля | закоммиченные каталоги и профили не переиспользуются и не правятся |
| Доступность внешних исполнителей | пользователь предоставляет способ вызова (Codex, приёмщик, Studio-браузер) | нет способа — стоп и эскалация до их первого шага; подмена ролей запускающим запрещена (§2) |
| Окно кредитов Tripo | читается остаток из журнала перед первой платной операцией | окно 300 кредитов — решение пользователя от 2026-09-28 ТОЛЬКО на то окно; новое окно подтверждается пользователем |
| Эскалация пользователю | остановка и передача решения | пакет: карточки, кадры, список незакрытых правок, рекомендация (возврат на 1/2 или решение пользователя) |

## 6. Шаблон заявки (asset card)

```yaml
# Заявка этапа 0. Без любого поля этап 1 не стартует.
# Сохраняется как asset-card.yaml в корне каталога ассета (§7); формат — YAML этого шаблона.
ASSET_ID: ASSET-<NAME>-001            # каталог art/pipeline-candidates/ASSET-<NAME>-001
ROLE: hero | creature | prop          # по АНАТОМИИ, не по игровой роли: hero = прямоходящий гуманоид;
                                       #   creature = не-гуманоид (крылатые, четвероногие, многоголовые —
                                       #   Цербер остаётся creature, даже если игра зовёт его «героем»);
                                       #   prop = неживой предмет. От ROLE зависят поза концепта (этап 1)
                                       #   и маршрут генерации (этап 2)
RIG: UM_HUMANOID_17_v2                # ТОЛЬКО для гуманоидной анатомии (+ расширения контракта
                                       #   crown_snakes/cloth/wing_tip). Четвероногие и многоголовые
                                       #   контрактом НЕ покрыты (validate_clip.py принимает только
                                       #   Medusa|Arthur|Merlin|Harpy) — стоп и эскалация пользователю
                                       #   на этапе 0: либо новая версия контракта (unmatched.rig-contract/3
                                       #   + правка валидатора и rig_rules.py), либо отказ от ассета.
                                       #   Надевать четвероногого на гуманоидный скелет запрещено.
POLY_BUDGET: герой 15-25k треугольников, потолок 45k   # помощник 8-15k; проп — из заявки пользователя.
                                       #   POLY_BUDGET — единственный источник бюджета для этапов 2–4;
                                       #   «Предложение 04» HANDBOOK (решение за GD-058) и практика H2
                                       #   30-45k — измерения/предложения, в карточку не смешиваются
FIGURE_HEIGHT_M: <высота фигуры, м>    # игровой размер; бюджет Specs() в uu = м × 100; существующие
                                       #   герои 0.42-0.55 м (42-55 uu, S08HeroesV2.cpp Specs()).
                                       #   Гейм-дизайн-решение: числа нет — эскалация на этапе 0;
                                       #   прописывается в Specs() на этапе 6 (±1 % автотест)
REFERENCES:
  - <эталон качества>                  # в репо единственный образец — medusa-quality-reference.png;
                                       #   для нового ассета эталон выбирает/утверждает пользователь на
                                       #   этапе 0 (кого/что считать «качеством»); нет файла и нет
                                       #   решения → эскалация. Прочие референсы — стиль и детали видов
UE_NAMES:                             # фиксируются на этапе 0, используются на этапах 5–6
  skeletal_mesh: SK_<Hero>_H2LD       # суффикс H<N>LD = номер последнего high-poly поколения (этап 4.5):
                                       #   первое — H2 (Arthur/Merlin/Medusa), следующее — H3 (Harpy);
                                       #   маршрут генерации кандидата h31 на суффикс не влияет.
                                       #   Проп: SM_<Name>
  clips: AM_<Hero>_Idle | AM_<Hero>_LungeAttack | AM_<Hero>_HitReact | AM_<Hero>_DeathSettle
  textures: T_<Hero>_H2LD_{BC,N,ORM,MatID,Edge,TeamAccent} + T_UM_MatLUT_<Hero>
                                       # фактические имена слегка варьируют по героям (Medusa …_Edge,
                                       #   Arthur …_EdgeMask; LUT — T_UM_MatLUT_Arthur): точные имена
                                       #   фиксируются здесь и проверяются ls фактической папки на этапе 6
DESCRIPTION: внешность, костюм, материалы, оружие и рука, поза, главные признаки силуэта
ANCHORS: что фиксирует идентичность между видами (оружие и рука; число голов и их ракурсы; «no extra wings» у крылатых)
ASSET_DIR: art/pipeline-candidates/ASSET-<NAME>-001
```

## 7. Evidence: куда писать

Каталог ассета — `art/pipeline-candidates/ASSET-<NAME>-001/` (образцы: ASSET-MEDUSA-001, ASSET-HARPY-001,
ASSET-KING-ARTHUR-001, ASSET-MERLIN-001, ASSET-DECOR-KIT-001):

```
art/pipeline-candidates/ASSET-<NAME>-001/
  asset-card.yaml                       # заявка этапа 0 (шаблон §6; норма этого скилла)
  source-specs/tripo-<task8>.json       # схема unmatched.tripo-pipeline.source-spec/1
  build-profiles/<name>.json            # правке не подлежат; новая версия — новый файл
  evidence/acceptance/<ГГГГММДД>-r<N>/  # этап 3/4: card.json + frames/ (10 JPEG)
  <run-id>/                             # каждый прогон — НОВЫЙ каталог
```

- **Run-id** `<YYYYMMDD>-<этап/вариант>`: 20260928-tripo-h31, 20260928-blender-um-fbx-v1,

## 8. Ограничения и правила проекта

- **Не гонять дорогие стадии без нужды.** Риг и retarget — только после финальной топологии (ремеш,
  сегментация и completion срезают риг); Smart UV отказывает на многочастных моделях — одночастная ветка
  через клон «Сохранить как новую модель»; цель ретопологии ≈ 0,5× бюджета; неиспользованный бесплатный
  повтор (×3) не тратить.
- **Сохранять промежуточные результаты.** Экспорт GLB всех состояний прогона; sha256 и байты каждого
  файла — в `reports/tripo-run.json`; журнал кредитов пополняется сразу после каждой операции;
  исходники Tripo только читаются и хешируются.
- **Правила проекта.** Коммит — `git commit --no-verify`; не трогать чужие незакоммиченные файлы; Codex
  на этапе 1 пишет только в свой каталог и не коммитит; правки модели — через профиль/скрипт (headless),
  не через ручные клики GUI.
- **Цены и лимиты.** Studio-кредиты и API-кредиты учитываются раздельно; цена — с кнопки до клика;
  остановка: остатка лимита не хватает или две неудачные генерации подряд.
