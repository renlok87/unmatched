# Задание другой LLM: подготовить диздок игры для Unreal Engine + Blender

Дата: 18 сентября 2026. Проект: Unmatched / `unmached`.

## Как использовать этот документ

Передай другой LLM **этот файл целиком**. Документация бэкенда уже написана в `docs/backend-api/`; приложи её отдельно или дай агенту доступ к репозиторию. Не проси повторно документировать сервер.

Результат работы LLM — заполненный пакет проектных решений, по которому агент разработки сможет последовательно собрать игру в Unreal Engine, подготовить модели в Blender и подключить существующий сервер. Это задание на подготовку документации, а не уже утверждённый дизайн игры.

Тебе как автору игры нужно выбрать желаемый результат: внешний вид, способ взаимодействия, объём первой версии и приоритеты. Поиск по репозиторию, заполнение таблиц, описание состояний интерфейса, списки ассетов и проверку согласованности должна сделать LLM.

## 1. Твоя роль и правила работы — инструкция для LLM

Ты — геймдизайнер, UX-дизайнер и технический художник проекта. Подготовь **GDD + спецификацию интерфейса + художественное руководство + задания на ассеты Blender + план проверяемой первой версии**.

Главный вопрос документа: **что именно игрок видит, делает и чувствует, и какие конкретные материалы нужны разработчику для реализации этого опыта?**

### 1.1. Что уже известно

- Есть веб-проект игры с React/Phaser, отдельной веб-админкой и сервером NestJS/GraphQL/PostgreSQL/Redis.
- Автор хочет игровое приложение на Unreal Engine и модели, подготовленные через Blender.
- Документация сервера уже существует в `docs/backend-api/`. Используй её как описание текущей реализации; не пересказывай все запросы, классы и механики заново.
- В `docs/unreal/` есть прежние архитектурные решения, планы и C++-сниппеты. Это входные материалы; наличие плана или сниппета не доказывает готовность функции.
- Цель текущего задания — описать продукт и контент достаточно точно для последующей реализации. Не переписывай сервер и не начинай массовое производство моделей на этой стадии.

### 1.2. Как обозначать уверенность

Используй четыре метки:

| Метка | Когда использовать |
|---|---|
| `ФАКТ` | Подтверждено конкретным исходником, проверкой приложения или предоставленным материалом |
| `РЕШЕНИЕ` | Автор явно выбрал вариант; запиши дату и формулировку выбора |
| `ПРЕДЛОЖЕНИЕ` | Твоя рекомендация, которую автор ещё не утвердил |
| `ВОПРОС` | Без ответа нельзя принять соответствующее решение |

Не превращай рекомендацию в решение только потому, что автор не ответил. Независимые разделы продолжай заполнять. Для блокирующих вопросов покажи варианты и объясни, что зависит от ответа.

Различай три вещи: **правило настольной игры**, **текущее поведение сервера**, **желаемое поведение цифровой версии**. При расхождении добавь запись в реестр решений, а не исправляй правило молча.

### 1.3. Рабочий процесс

1. Прочитай этот brief и оглавления существующих документов. Составь карту источников без их переписывания.
2. Задай автору первую порцию из 5–7 важных вопросов из раздела 3. По остальным предложи разумные варианты.
3. Подготовь краткое видение и границы первой версии. Покажи два подходящих визуальных направления с конкретными отличиями.
4. После выбора направления подробно заполни документы из раздела 4.
5. Самостоятельно проверь связи: механика → ввод → экран → серверная операция → анимация/звук → ассеты → критерий приёмки.
6. Верни пакет, список нерешённых вопросов и точную задачу для первого этапа реализации.

Не отвечай одним общим описанием или пустым шаблоном. Заполни всё, что можно вывести из доступных данных. Не выдумывай результаты запуска, профилирования, импорта моделей, проверки ссылок или тестов.

Если репозитория нет, используй приложенные документы. Указывай недоступные источники и запрашивай только материалы, необходимые для конкретного решения. Сам этот brief содержит достаточную основу, чтобы начать интервью и дизайн.

### 2.2. Полезные конкретные данные

В Prisma-модели героя есть `miniModelUrl`, `characterCardUrl`, `imageUrl`, `avatarUrl`, `sidekicks`, `additionalMinis`. У карты есть изображения, текст, значения и эффекты. У доски есть размеры, `cells`, `features` и изображения.

Выборочная проверка через API:

| Объект | Проверенные данные |
|---|---|
| Medusa | 16 HP, movement 3, три записи Harpies в `sidekicks`, 11 записей карт; `miniModelUrl` и `characterCardUrl` заполнены |
| King Arthur | 18 HP, movement 2, Merlin в `sidekicks`, 16 записей карт; `miniModelUrl` и `characterCardUrl` заполнены |
| Cobble City | Размер 5 × 6, 30 элементов `cells`; первые ячейки содержат координаты и `zones` |

Количество записей карт здесь не равно размеру колоды: учитывай поле количества копий. Заполненный URL модели не означает, что модель доступна, имеет пригодную сетку, скелет, лицензию или импортируется в UE.

В каталоге досок также видны размеры вроде 400 × 230. Не делай вывод, что это корректная сетка из 92 000 игровых клеток: проверь реальную структуру `cells` и договорись о системе координат выбранной доски до моделирования.

## 5. Видение игры и границы

Заполни:

1. Описание игры в 2–3 предложениях: жанр, игроки, основной выбор, визуальная подача.
2. Для кого игра, какие знания настольных правил предполагаются.
3. Три принципа дизайна. Например: «поле читается с основной камеры», «игрок понимает причину недоступного действия», «эффекты не задерживают принятие решений». Это примеры, а не утверждённые принципы.
4. Чем UE-версия улучшает нынешний опыт: объёмная сцена, камера, тактильность карт, свет, звук, отзывчивость.
5. Основной цикл сессии: запуск → вход → выбор режима → комната → выбор героя → партия → результат → следующая партия.
6. Целевая длительность матча, хода, ожидания соперника. Если сервер задаёт таймеры, сошлись на него.
7. Чёткие списки `MVP`, `после MVP`, `не планируется` с причиной.
8. Платформы, языки, управление, настройки, целевой компьютер и качество графики.

**Предложение стартового объёма:** Windows, мышь/клавиатура, онлайн 1 на 1 в приватной комнате, два героя с помощниками, одна доска, полный цикл партии, восстановление соединения. Герои Medusa и King Arthur и доска Cobble City — кандидаты из текущих материалов; их пригодность нужно подтвердить проверками правил и геометрии.

Не добавляй весь каталог, магазин, сезоны, коллекционирование, кампанию, VR или мобильную версию автоматически. Если автор их хочет, оцени отдельный объём.

### 6.2. Минимальный перечень

- Выбор героя, просмотр способности и колоды, готовность и старт матча.
- Начальная расстановка и сообщение о первом ходе.
- Выбор своего героя/помощника, просмотр чужого бойца.
- Манёвр: выбор бойцов, доступных позиций, усиления и подтверждения.
- Атака: боец, цель, карта, усиление, отмена до отправки.
- Защита: ожидание, выбор карты/допустимого отказа, таймер, раскрытие результата.
- Scheme-карта, выбор целей и условий.
- Отложенные эффекты, в том числе выбор бойца, позиции и варианта.
- Способности/стойки выбранных для MVP героев.
- Просмотр карты, руки, сброса и колоды в пределах разрешённой информации.
- Завершение хода, исчерпание действий, смерть помощника, победа/поражение.
- Выход из партии, подтверждение последствий, возврат после разрыва сети.

Для каждого пункта укажи `поддерживается / ограничено / требует проверки / требует изменения сервера`. Само наличие кнопки или GraphQL-операции не доказывает, что сценарий работает целиком.

### 6.3. Обязательные подробные сценарии

Напиши пошагово три истории:

1. Новый игрок запускает приложение, входит в комнату и делает первый осмысленный ход.
2. Игрок атакует, соперник защищается, срабатывает эффект с дополнительным выбором, управление возвращается правильному игроку.
3. Связь пропадает после отправки действия, клиент возвращается и показывает актуальную партию без повторного расхода карты.

В каждом шаге должны быть действие игрока, видимая реакция, источник данных и условие перехода. Слова «затем работает бой» не заменяют описание.

## 7. Спецификация интерфейса

### 7.1. Карта экранов

Определи необходимость и приоритет каждого экрана: запуск/подключение, вход, главное меню, список комнат, комната, выбор героя, загрузка матча, игровой HUD, инспектор карты, меню паузы/настроек, потеря связи, результат партии. Матчмейкинг, обучение, история и рейтинг — только в выбранном объёме.

Для каждого экрана заполни:

```text
UI-ID / название / назначение:
Как попасть / как выйти:
Основной сценарий:
Макет: расположение блоков, размеры, якоря, безопасные области.
Контент каждого блока и источник:
Действия и клавиши:
Пустое состояние:
Загрузка / ожидание:
Недоступность и её причина:
Ошибка / повтор / отсутствие сети:
Фокус ввода и поведение Escape:
Изменение размера окна / длинный текст / локализация:
Звуки и переходы:
Критерии приёмки:
```

Предоставь хотя бы схематические макеты основных экранов. Если инструмента рисования нет, используй блоковую ASCII-схему или таблицу координат; не называй отсутствующие картинки готовыми макетами.

### 7.2. Особое внимание игровому HUD

Опиши положение и поведение:

- Своей руки, увеличенной карты, выделения, подтверждения розыгрыша.
- Панелей игроков: здоровье, действия, статус хода, количество карт.
- Поля, подсветок выбранной фигуры, доступных клеток и целей.
- Способности героя и помощников, стоек и ресурсов, если они нужны MVP.
- Панели атаки/защиты, таймера и очереди дополнительных выборов.
- Сброса, колоды, журнала событий и подсказок.
- Состояния связи и блокировки новых действий во время синхронизации.

Для выбора карты отдельно реши: hover, один клик, двойной клик, drag-and-drop, просмотр правой кнопкой, отмена. Не допускай, чтобы просмотр карты случайно отправлял игровое действие.

Дай таблицу состояний ввода: `ничего не выбрано → боец выбран → карта выбрана → цель выбрана → подтверждение → запрос выполняется → подтверждено/ошибка`. Для каждой стрелки укажи событие, допустимость отмены и реакцию при входящем обновлении состояния.

### 7.3. Доступность и настройки

Установи выбранные требования: масштаб UI, размер текста, контраст, обозначение зон не только цветом, отключение тряски камеры, сокращённые анимации, громкость музыки/эффектов, поведение при потере фокуса окна. Проверяй русский текст реальными длинными названиями карт.

Не делай цвет единственным различием между «можно ходить», «можно атаковать» и «ожидается выбор эффекта».

### 7.4. Графические ассеты интерфейса

Составь отдельные задания на шрифты, пиктограммы действий/ресурсов/зон, рамки и рубашки карт, панели, кнопки, курсоры и индикаторы загрузки. Включи их в общий asset manifest с типом `UI`.

Для каждого семейства зафиксируй назначение, размеры в макете и экспорте, прозрачность, отступы, зоны растяжения, состояния `normal/hover/pressed/disabled/focus/selected`, светлый/тёмный фон и формат поставки. Укажи редактируемый исходник и формат, проверенный в выбранном UE-пайплайне; векторный исходник не означает автоматически готовую runtime-текстуру.

Для шрифтов проверь кириллицу, цифры, знаки, начертания, условия использования и fallback. Для карт реши, какие надписи запечены в изображение, а какие выводятся локализуемым текстом поверх него. Для иконок приложи проверку в минимальном используемом размере; для рамок — растяжение и длинные заголовки. Цветовые и размерные параметры оформи общей таблицей, чтобы разные экраны не расходились.

## 8. Художественное направление

Нужен понятный визуальный контракт для моделирования и сборки сцены.

### 8.1. Сравнение направлений

Предложи два варианта, подходящих автору. Например:

| Направление | Характер | Следствия для производства |
|---|---|---|
| Настольные миниатюры | Стол, подставки, читаемые силуэты, короткие движения фигурок | Можно начать со static mesh и анимации перемещения объектов |
| Живая диорама | Объёмное окружение, персонажи с жестами и боевыми движениями | Потребуются риги, клипы, дополнительные проверки перекрытия клеток |

Для выбранного варианта задай: пропорции, степень стилизации, материалы, палитру, акцент игрока, свет, контраст игрового и декоративного слоя, фон за пределами поля.

Для каждого референса запиши ссылку/файл и точный признак: «угол камеры», «шероховатый окрашенный пластик», «толщина рамки карты». Укажи, что из референса не переносится. Стиль описывай воспроизводимыми признаками.

### 8.2. Камера и читаемость

Определи тип проекции, стартовый угол, диапазон приближения, вращение, панорамирование, возврат к обзору, ограничения поля. Для каждой величины укажи значение или вопрос; не смешивай фокусное расстояние и FOV без выбранной модели камеры.

Нужны три контрольных кадра: общий вид партии, максимальное полезное приближение, бой/просмотр карты. На общем виде должны различаться фигуры и игровые зоны. Камера не должна прятать обязательный выбор или вызывать ошибочный клик после автоматического движения.

Если есть кинематографические вставки, задай длительность, возможность отключения, поведение при следующем событии сервера и возврат к прежней камере.

### 8.3. Доска и декорации

Раздели логическую доску, кликабельные области, декоративную геометрию и фон. Укажи, какие объекты могут перекрывать фигуры, когда крыша/стена скрывается и как читаются проходы.

Для каждой доски потребуй вид сверху, положение игровых ячеек, стартовые позиции, зоны, масштаб, границы камеры, набор декораций и список допустимых визуальных условностей.

Не изменяй правила перемещения ради удобства 3D-модели. Физическая коллизия декораций не должна становиться новым источником игровых правил.

## 9. Техническое задание на Blender

### 9.1. Общий стандарт ассетов

Заполни стандарт **до массового моделирования**:

| Параметр | Что требуется зафиксировать |
|---|---|
| Версии | Точные версии Blender, UE, экспортёра/импортёра и необходимых дополнений |
| Единицы | Рабочие единицы Blender, единицы экспорта, итоговый размер в UE |
| Оси | Вверх, направление лица/движения, преобразование координат при импорте |
| Pivot | Точка опоры фигурки, pivot дверей и сборных декораций |
| Трансформации | Правила применения scale/rotation, отрицательного масштаба и зеркальных объектов |
| Геометрия | Бюджет треугольников LOD0, силуэт, допуски тонких деталей, требования к нормалям |
| Материалы | Максимум слотов, общий master material, параметры цвета команды |
| UV | Каналы, допустимые перекрытия, плотность, lightmap UV при необходимости |
| Текстуры | Размеры, набор карт, упаковка каналов, цветовое пространство, нормали |
| Коллизии | Отдельно выбор мышью, визуальные препятствия и нужная физика |
| LOD | Уровни, критерии переключения и допустимость упрощения силуэта |
| Rig | Скелет, root, лимиты влияний, sockets и совместимость анимаций, если нужен |
| Экспорт | Формат, сохранённый preset и повторяемая процедура |
| Файлы | Исходный `.blend`, экспорт, текстуры, превью, manifest, описание |
| Приёмка | Контроль масштаба, ориентации, материалов, коллизий, анимаций в UE |

UE по умолчанию использует сантиметры для длины и систему координат Z-up с X вперёд. Задай явное соответствие Blender → UE и проверь его на тестовом объекте. [Единицы UE](https://dev.epicgames.com/documentation/en-us/unreal-engine/units-of-measurement-in-unreal-engine), [координаты UE](https://dev.epicgames.com/documentation/en-us/unreal-engine/coordinate-system-and-spaces-in-unreal-engine).

Не выдавай один набор настроек FBX за универсальный: пресет должен пройти проверку именно на выбранных версиях и типе меша. Документация Epic указывает FBX 2020.2 для своего FBX pipeline; это не означает, что любой экспорт Blender автоматически полностью совместим. [FBX Content Pipeline](https://dev.epicgames.com/documentation/en-us/unreal-engine/fbx-content-pipeline).

Проверочный набор: куб известного размера, асимметричная стрелка направления, фигурка с pivot на опоре; при использовании skeletal mesh — короткий клип с root и движением конечности. Сохрани ожидаемые и полученные размеры/ориентацию.

### 9.2. Индивидуальное задание на модель

```text
ASSET-ID / название / этап:
Роль: герой / помощник / поле / декорация / интерактивный объект.
Стабильный content key и связь с каталогом:
Есть ли исходник: путь или URL, статус доступности, условия использования.
Решение: использовать / доработать / сделать заново.
Референсы: спереди, сбоку, сзади; что в них обязательно.
Силуэт с игровой камеры:
Стиль, пропорции, выражение и поза:
Размеры в сантиметрах в UE, габарит подставки:
Количество отдельных объектов и material slots:
Что должно двигаться отдельно:
Static или skeletal mesh и причина:
Бюджет треугольников, текстур, материалов, LOD:
Pivot, оси, коллизии:
Rig / sockets / анимации, если нужны:
Варианты, цвет команды, повреждения:
Исходные и экспортные файлы:
Проверка в Unreal:
Связанные UI/CUE/QA:
```

Сделай такую карточку **на каждый уникальный тип модели MVP**. Три одинаковых помощника могут быть тремя экземплярами одного ассета; три разных персонажа нельзя записать одним расплывчатым «сделать помощников».

### 9.3. Предварительный набор для кандидата MVP

Если автор подтвердит Medusa vs King Arthur:

- Модель Medusa.
- Модель Harpy, используемая для трёх фигурок, если выбран одинаковый внешний вид.
- Модель King Arthur.
- Модель Merlin.
- Подставки/маркеры владения, выделения и состояния.
- Одна доска с подтверждённой геометрией.
- Стол/основание и ограниченный набор декораций.
- Общие материалы, необходимые текстуры, коллизии и превью.

Сначала инвентаризируй существующие `miniModelUrl`. Не требуй заново создавать модель только потому, что она пока не лежит локально. Не считай URL готовым UE-ассетом без проверки.

### 9.4. Автоматизация через Blender

Укажи, какие операции целесообразно воспроизводить Python-скриптами: создание базовых форм, расстановка модулей, нормализация имён, экспорт, отчёт по полигонам и материалам, генерация превью.

Для каждого скрипта определи вход, выход, параметры, повторный запуск, место логов и проверку результата. Не обещай скриптом автоматически получить художественно качественного персонажа только по короткому тексту.

### 9.5. Сдача ассета

Для каждого ассета требуй:

1. Редактируемый `.blend` с понятными коллекциями и без потерянных текстур.
2. Экспортный файл и точные настройки экспорта.
3. Текстуры и перечень материалов.
4. Превью с игровой камеры, силуэт и при необходимости wireframe.
5. Отчёт: размеры, треугольники, материалы, скелет, анимации, коллизии, LOD.
6. Результат импорта и проверки в UE или честный статус «ещё не проверено».
7. Запись в asset manifest и происхождение исходников.

## 10. Анимации, VFX и звук

Создай таблицу:

```text
CUE-ID, событие, условие запуска, объект, анимация, VFX, звук,
длительность, задержка до feedback, блокирует ли ввод,
можно ли пропустить, что делать при новом событии,
что делать при reconnect, fallback, связанные QA
```

Минимальные события: hover/select, допустимый/недопустимый выбор, взятие карты, розыгрыш, перемещение, объявление атаки, защита, раскрытие, урон, лечение, смерть фигуры, способность, следующий ход, победа/поражение, разрыв/восстановление связи.

Определи, когда достаточно перемещения static mesh, а когда нужна скелетная анимация. Сетевой результат не должен зависеть от завершения красивого ролика. При догоняющей синхронизации не проигрывай заново всю старую очередь эффектов.

Для звука задай характер, группы громкости, частоту повторения, приоритет одновременных эффектов и варианты отсутствующих ассетов. Для музыки — состояния меню/партии/результата и переходы. Уровень подробности подбери под выбранный MVP.

## 11. Данные и интеграция: только необходимые решения

### 11.1. Разделение ответственности

**Предложение, согласующееся с прежней архитектурой:** сервер принимает и проверяет действия, рассчитывает правила и хранит состояние; Unreal отвечает за ввод, визуальное представление и обратную связь; Blender — за исходники ассетов; веб-админка остаётся инструментом управления контентом.

Опиши это в короткой схеме. Не вводи UE dedicated server, GAS, отдельную БД или переписывание правил на C++ без конкретного требования, которого не удовлетворяет текущая архитектура.

### 11.2. Что нельзя потерять при дизайне клиента

- HTTP GraphQL и подписки должны рассматриваться как два источника обновлений одной партии, а не две независимые игры.
- Серверные ответы содержат JSON внутри строк. Формат и nullability брать из контракта, не из предположения о «типичном GraphQL».
- Полное состояние и `gameStateUpdated` отличаются по набору данных. В проверенном коде подписка сериализует `players`, `fighters`, `handZones`, `boardState`, `metadata`, не отдельные `decks`/`discardPiles`.
- Ответ на действие и сетевое событие могут описывать одну последовательность. Нужно определить подавление повторного отображения, восстановление пропусков и устаревших ответов.
- CUID базы, имя, slug, ID бойца, ID пользователя и ID экземпляра карты — разные понятия. Визуальная привязка не должна путать их.
- Наличие `contentVersion` не доказывает автоматического обновления контента после редактирования. В проверенном коде версия задана константой; политика публикации/кэша требует явного решения.
- Скрытая рука соперника должна отображаться по согласованному контракту скрытых данных. Не восстанавливай закрытые карты через каталог по доступному ID. Полноту серверной фильтрации проверяют отдельно.

Это ограничения для UX и интеграции, а не задание написать повторный справочник API.

### 11.3. Привязка данных к моделям

Создай отдельный manifest, не выдавая его за существующую серверную схему:

```text
assetKey, entityType, stableContentKey, sourceReference,
blendPath, exportPath, unrealAssetPath, variant,
version, sourceHash, verificationStatus, fallbackAssetKey
```

Укажи, как строится соответствие стабильного ключа контента и ID текущей БД. Один cuid нельзя навсегда зашить в имена моделей, если база может быть пересоздана.

**Предложение для MVP:** импортировать и упаковывать модели вместе с клиентом, связывая каталог с UE-ассетами через manifest. Поле `miniModelUrl` само по себе не обеспечивает загрузку и преобразование произвольной GLB-модели в работающий ассет packaged game. Runtime-загрузку моделей проектировать отдельно только если она нужна.

Опиши fallback для отсутствующей модели, текстуры, перевода и неизвестного content key. Укажи, какие правки админки видны без сборки клиента, какие требуют публикации контента, а какие — пересборки игры.

### 11.4. Геометрия игрового поля

Нужен отдельный контракт соответствия:

```text
координата/идентификатор серверной ячейки
→ игровая зона и связи
→ позиция на 3D-доске
→ область выбора мышью
→ посадочная точка и ориентация фигурки
```

Зафиксируй начало координат, направления осей, масштаб, высоту опоры, границы, инверсию экранного Y и правила преобразования обратно. Если используешь формулу — приложи минимум три проверочных точки, включая противоположные углы и соседние клетки.

Не подменяй игровую сетку данными картинки. Для нерегулярной доски потребуются явные позиции/связи или согласованный адаптер; изменение серверной схемы оформляется отдельным решением.

### 11.5. Таблица расхождений

```text
GAP-ID | желаемый опыт | существующее поведение и источник |
влияние на MVP | решение: принять/обойти/изменить сервер/отложить |
задача | критерий проверки
```

Используй уже описанные в `docs/backend-api/` ограничения. Уточняй, какие проверены сейчас, а какие известны только из документации. Не обещай исправления в рамках написания GDD.

## 12. Матрица контента

Для каждого героя MVP и затем поэтапно для остальных составь:

```text

статус базовой механики, уникальные механики, необходимые UI-состояния,
поддержка сервера, сценарии проверки,
арт карты персонажа, рубашка, портрет, модель,
помощники и дополнительные фигуры,
анимации, VFX, звук, нерешённые вопросы
```

Для карт добавь количество копий, типы эффектов, дополнительные выборы и необходимость уникального оформления. Для досок — достоверность геометрии, зоны, особенности, источники изображения/3D и статус проверки.

Числа 84/880/30 — отправная точка инвентаризации, а не автоматическая цель первой версии. Не расписывай сотни почти одинаковых карточек вручную, если таблицу можно получить из данных, а затем отдельно описать исключения.

## 13. Производительность и технические границы

Попроси целевой компьютер. До ответа любые цифры называй предварительными бюджетами.

Зафиксируй: разрешение, FPS, frame time, RAM/VRAM, время запуска/загрузки партии, максимальную задержку локальной обратной связи, максимальное число фигур и одновременно видимых эффектов.

Бюджеты моделей и текстур должны следовать из контрольной сцены на целевом железе. Не назначай «100 тысяч полигонов на героя» без масштаба кадра и количества объектов. Не включай Nanite/Lumen/ray tracing только по наличию технологии.

Укажи настройки качества и деградацию: тени, постобработка, детализация декораций, эффекты, разрешение. Игровые подсветки и читаемость не должны исчезать на минимальных настройках.

Сетевые сценарии: задержка, потеря связи, повтор ответа, устаревшее событие, истёкшая сессия. Для каждого нужен видимый исход и способ восстановления. Измерения выполнять в packaged build, а не объявлять FPS редактора результатом готовой игры.

## 14. Первая проверяемая версия и этапы

Предложи этапы с демонстрацией после каждого:

| Этап | Результат | Условие перехода |
|---|---|---|
| 0. Утверждение направления | Видение, MVP, выбор камеры и фигурок, список решений | Нет блокирующих вопросов по первой партии |
| 1. Техническая проба | Вход UE в существующий сервер, получение контента/состояния, проба Blender → UE | Доказана работоспособность выбранных интеграций |
| 2. Серая игровая сцена | Одна доска и временные фигуры, базовый HUD | Можно выбрать объект и отправить корректное действие |
| 3. Полная партия | Два клиента проходят матч с обязательными эффектами | Победа/поражение и восстановление связи работают |
| 4. Эталон качества | Одна законченная модель и участок доски в целевой камере | Автор утверждает вид; подтверждены бюджеты |
| 5. Контент MVP | Все выбранные модели, карты, UI, эффекты и звук | Пройдены игровые и визуальные проверки |
| 6. Сборка | Запускаемая игра вне редактора, инструкция подключения | Чистый запуск и повторяемая демонстрация |

Это рекомендуемая последовательность, её можно изменить под приоритет автора. Не делай весь каталог до проверки одной партии и одного ассета.

Карточка задачи:

```text
TASK-ID / название / цель:
Входные решения и материалы:
Область ответственности: UE / Blender / UI / сервер / документация.
Конкретные выходные файлы/ассеты:
Зависимости:
Шаги реализации:
Проверка:
Условие готовности:
Риски и вопрос, способный изменить оценку:
Относительный размер или диапазон оценки с допущениями:
```

Задачи должны заканчиваться наблюдаемым результатом: «игрок выбирает карту и видит подтверждённую атаку», а не только «создать класс».

## 15. Приёмочные сценарии

Преобразуй требования в проверки Given/When/Then. Для каждой проверки укажи подготовку, участников, ожидаемое состояние, визуальный результат и доказательство.

Обязательный минимум:

1. **QA-001:** два игрока входят в одну комнату, выбирают допустимых героев, начинают одну и ту же партию.
2. **QA-002:** при действии вне своего хода UI объясняет недоступность; попытка не меняет состояние.
3. **QA-003:** манёвр расходует ресурсы только после подтверждения сервера; повторный клик не создаёт второе действие.
4. **QA-004:** атака/защита/результат и обязательный дополнительный выбор видны правильному игроку.
5. **QA-005:** закрытые карты соперника не раскрываются ни в HUD, ни в инспекторе/журнале.
6. **QA-006:** отключение после отправки действия и повторное подключение не расходуют карту повторно.
7. **QA-007:** одинаковое обновление из HTTP и подписки не проигрывает урон/анимацию дважды.
8. **QA-008:** победа/поражение завершают ввод в партии и дают понятный выход к следующему действию.
9. **QA-009:** Blender-модель после импорта имеет ожидаемые размеры, ориентацию, pivot, материалы и коллизию выбора.
10. **QA-010:** общий вид поля позволяет различать фигуры, зоны и доступные действия без максимального приближения.
11. **QA-011:** длинные русские названия и увеличенный UI не закрывают обязательные кнопки.
12. **QA-012:** отсутствующий ассет заменяется понятным fallback и не ломает партию.
13. **QA-013:** изменение разрешённого контента в админке проявляется согласно выбранной политике обновления.
14. **QA-014:** packaged build запускается без редактора и подключается к настроенному адресу сервера.

Если сохраняется совместимость с веб-клиентом, добавь партию UE ↔ Web. Если MVP не включает конкретную механику, явно исключи соответствующий сценарий и объясни ограничение каталога.

Отдельно проверь пару реальных случаев: помощник с 1 HP, несколько одинаковых помощников, две копии одной карты в руке, карта с длинным текстом, переход фазы во время открытого инспектора.

## 16. Пример достаточной детализации

Ниже **иллюстративное предложение**, а не утверждённый дизайн и не готовый wire-format:

```text
GDD-ATK-001 — Подтверждение атаки.
Игрок выбирает своего бойца, карту атаки и допустимую цель.
UI показывает выбранную тройку, стоимость и кнопку подтверждения.
До отправки Escape отменяет текущий выбор; карта не потрачена.
После подтверждения повторное подтверждение блокируется.
Локально появляется короткий feedback «действие отправлено».
Карта не раскрывается сопернику раньше разрешённого сервером момента.
При принятии сервером UI переходит в подтверждённую фазу боя.
При отказе UI объясняет причину и сверяет выбор с актуальным состоянием.
При сетевой неопределённости показывает восстановление; не повторяет
мутацию вслепую. Политика повтора определяется контрактом операции.
Фигурка может выполнить короткое движение, которое не рассчитывает урон.
При reconnect старый эффект не проигрывается заново как новая атака.
Проверки: корректная атака, неверный ход, устаревшая цель, двойной клик,
HTTP/WS в разном порядке, потерянный ответ.
```

Иллюстративная карточка модели:

```text
ASSET-MEDUSA-001 — Миниатюра Medusa.
Статус: предложение до выбора художественного направления.
Назначение: узнаваемая фигура на общей камере, привязка к medusa.
Сначала проверить существующий miniModelUrl.
При варианте «настольные миниатюры»: static mesh, pivot на опоре;
выделение и движение выполняются в UE, скелет без нужды не требуется.
Размер, геометрический бюджет, материалы и текстуры задаются после
выбора масштаба доски и контрольной камеры — это блокирующие поля.
Сдача: .blend, экспорт, текстуры, manifest, превью на поле,
подтверждение масштаба/ориентации/выбора мышью в UE.
```

## 17. Когда документ достаточно готов для реализации

Для выбранного первого этапа должны выполняться все условия:

- Есть однозначный объём и список исключений.
- Выбран визуальный стиль, камера и способ представления фигур.
- Каждый обязательный игровой выбор имеет экран/состояние ввода.
- Все обязательные механики связаны с существующим контрактом или отдельной задачей изменения.
- Есть перечень уникальных моделей и заполненные задания на них.
- Установлен и проверяемо описан масштаб Blender → UE → игровое поле.
- Известно, как серверный контент сопоставляется с упакованными ассетами.
- Ошибки, ожидание и восстановление связи описаны наряду с успешным сценарием.
- Нет неизвестных решений, замаскированных под факт.
- Есть задачи первой итерации и критерии её демонстрации.

Не нужно решать весь будущий каталог до начала разработки. Нерешённые вопросы поздних этапов допустимы, если они не меняют основу первого этапа.

## 18. Финальный ответ LLM автору

Верни:

1. Заполненные файлы или единый документ.
2. Краткий список решений автора и отдельно твоих предложений.
3. Не более 10 действительно блокирующих вопросов, с вариантами ответа.
4. Список необходимых референсов/исходников, которые нельзя получить из проекта.
5. Перечень расхождений с существующим сервером без повторного описания API.
6. Готовое задание агенту реализации на первый этап, со ссылками на требования и критериями завершения.

**Главный критерий качества:** разработчик и художник должны одинаково понять, что делать, что показать на проверке и когда остановиться. Объём текста сам по себе не является качеством.
