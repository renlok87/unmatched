# Deep research 2026-10-05: хвосты набора DE и генерация музыки

Workflow `deep-research` (`wf_530acfce-5e2`): 5 направлений поиска, проверка каждого утверждения тремя голосами, синтез. Вопрос — хвосты из [CLOSEOUT §7](CLOSEOUT-2026-10-04.md) и генерация музыки через SYNTX.

## Итог

Проверку тремя голосами прошли 20 утверждений, после объединения получилось 12 выводов. Они хорошо закрывают три темы: батчинг и occlusion в UE (п. 1), лицензии на AI-музыку (п. 5) и импорт звука в UE 5.8. Хуже закрыты event log и catch-up анимаций (пп. 2–3). По UMG-вводу (п. 4) подтверждён только инструмент для тестов (Automation Driver), причины потери первого клика не подтверждены.

1. **Плашки ходов.** Отдельные динамические материалы (DMI) на каждой плашке ломают автоинстансинг: draw-вызовы сливаются только при идентичных shader bindings. Нужна одна ISM с одним материалом, одной секцией и без теней, а состояние плашки хранить в custom data. Даже так одна ISM не гарантирует ровно один draw. Occlusion queries в UE выключаются только глобально. На уровне компонента их убирают лишь косвенно, например через Nanite.
2. **Эффекты в бою.** Подтверждённый образец — Hearthstone. Сервер шлёт не снимки состояния, а поток изменений, сгруппированных во вложенные типизированные блоки (атака, способность, триггер). По этим блокам клиент восстанавливает причину каждого изменения и порядок анимаций. Скрытая информация фильтруется на сервере отдельно для каждого игрока.
3. **SYNTX.** По оферте все права на результат принадлежат заказчику, коммерческое использование разрешено без условия о тарифе. При этом оферта не отменяет условий провайдеров моделей. У ElevenLabs Music все self-serve планы запрещают «Studio Games», это разрешает только Enterprise. Коммерческие права Suno привязаны к подписке Pro/Premier и скачиванию через собственный канал Suno. Кроме того, п. 9.3 оферты SYNTX запрещает автоматизированный доступ и эмуляцию действий пользователя без письменного разрешения. Это прямо касается генерации через Chrome силами агента.

## Выводы (по уверенности)

### 1. [high, голоса 3-0]

[UE, п.1] Автоматический dynamic instancing объединяет два mesh draw command в один только при идентичных shader bindings (FMeshDrawCommand::MatchesForDynamicInstancing). Между ними может отличаться только InstanceID или вершинные потоки с частотой instance. Отсюда следует:
- отдельные компоненты-плашки, у каждой из которых своя Dynamic Material Instance или свои параметры MI, в один draw не сольются, потому что у каждой MI свой uniform buffer;
- значения в Custom Primitive Data хранятся в GPUScene и батчинг не ломают.

Практический вывод: собрать все плашки в одну ISM с одним материалом и передавать состояние (кандидат, выбрана, недоступна) через PerInstanceCustomData или Custom Primitive Data вместо отдельных DMI.

Источники: https://dev.epicgames.com/documentation/en-us/unreal-engine/mesh-drawing-pipeline-in-unreal-engine, https://dev.epicgames.com/documentation/en-us/unreal-engine/storing-custom-data-in-unreal-engine-materials-per-primitive

Проверка: Голоса 3-0, первичная документация Epic с пометкой UE 5.8. Проверяющий нашёл MatchesForDynamicInstancing и в API FMeshDrawShaderBindings. На странице Custom Primitive Data Epic прямо пишет, что смена параметров MI обычно ломает батчинг, а CPD снижает число draw за счёт автоинстансинга. Совпадение bindings — условие необходимое, но не достаточное: ещё должны совпадать PSO и вершинные/индексные буферы.

### 2. [medium, голоса 3-0]

[UE, п.1] Объединение одинаковых мешей в одну ISM не гарантирует ровно один draw call. Батч дробится:
- на секции материалов в меше;
- на отдельные проходы (shadow depth, depth prepass, velocity);
- на LOD.

Поэтому ISM с плашками-гексами может стоить несколько draw. Счётчик stat RHI / DrawPrimitive учитывает все проходы. Чтобы приблизиться к одному draw на проход: один слот материала в меше плашки, CastShadow=false, без лишних LOD.

Источники: https://uhiyama-lab.com/en/notes/ue/instancing-draw-call-optimization/, https://dev.epicgames.com/documentation/fortnite/reducing-draw-calls-in-fortnite

Проверка: Голоса 3-0, но основной источник — блог (обновлён 2026-09). Часть про слоты материалов независимо подтверждает документация Epic по Fortnite: «10 мешей × 5 материалов = 50 draw», рекомендован 1 материал на меш. Разбиение по проходам проверяющий вывел из общей архитектуры mesh pass. Отдельной первичной страницы Epic с этим утверждением он не нашёл.

### 3. [high, голоса 3-0]

[UE, п.1] Occlusion: что стоит каждая отдельная плашка и как это отключить.

Как работает по умолчанию:
- В любом проекте UE по умолчанию включены View Frustum culling и Hardware Occlusion Queries.
- Стоимость HW-occlusion растёт с числом запросов к GPU.
- Документация говорит «запрос на Actor». Исходники UE 5.8 показывают, что на деле запрос идёт на каждый примитив (scene proxy), то есть у каждого компонента-плашки свой запрос.
- Movable-примитивы всегда идут по пути индивидуального запроса каждый кадр, а динамически спавнящиеся плашки как раз Movable.

Как отключить:
- Только глобально: r.AllowOcclusionQueries=0 или Project Settings > Rendering > Culling > Occlusion Culling.
- Флага на уровне ISM-компонента нет.
- Косвенно запросы не делаются для Nanite-прокси (CanBeOccluded=false, bIsAlwaysVisible), для примитивов с CustomDepth, для материалов с disable depth test и для примитивов ближе r.NeverOcclusionTestDistance.
- Есть show flag DisableOcclusionQueries на сцену и возможность задать CVar через device profile.

Про рекомендацию Epic: Precomputed Visibility требует запечённого света и плохо подходит проекту на Lumen.

Источники: https://dev.epicgames.com/documentation/en-us/unreal-engine/visibility-and-occlusion-culling-in-unreal-engine, C:/Program Files/Epic Games/UE_5.8/Engine/Source/Runtime/Renderer/Private/SceneVisibility.cpp, C:/Program Files/Epic Games/UE_5.8/Engine/Source/Runtime/Engine/Classes/Engine/RendererSettings.h, C:/Program Files/Epic Games/UE_5.8/Engine/Source/Runtime/Engine/Private/PrimitiveSceneProxy.cpp

Проверка: Три утверждения с голосами 3-0, первичная документация Epic (UE 5.8). Проверяющие сверились с локальными исходниками UE 5.8:
- GHZBOcclusion=0 по умолчанию;
- ключ FPrimitiveOcclusionHistoryKey(PrimitiveId);
- bAllowApproximateOcclusion=(Mobility!=Movable);
- GOcclusionCullEnabled — единственный глобальный флаг;
- RendererSettings связывает чекбокс с r.AllowOcclusionQueries.

Уточнения:
- ранее закрытые статичные примитивы группируются до 16 на запрос;
- видимые перезапрашиваются вероятностно;
- часть стоимости ложится на render thread (CPU), а не только на GPU.

### 4. [high, голоса 3-0]

[UE, п.4] Для автотестов синтетических кликов подходит Automation Driver. В нём есть ожидания Until::ElementExists, ElementIsVisible, ElementIsInteractable и ElementIsScrolledToBeginning с интервалом (необязателен, по умолчанию 1 с) и таймаутом. «Interactable» означает, что виджет IsEnabled, его видимость IsHitTestVisible и hit-test фейкового курсора в центре виджета попадает в этот виджет. Это ловит гонку «виджет ещё не готов или перекрыт».

Ограничения:
- модуль Developer, в Shipping его нет;
- синхронный API нельзя вызывать на GameThread;
- действия драйвера и так неявно ждут до ImplicitWait (по умолчанию 3 с).

Утверждение, что драйвер подменяет платформенный слой и клики идут тем же путём, что реальный ввод ОС, опровергнуто (0-3). Значит, тест драйвером может не воспроизвести потерю первого клика, если её причина в захвате мыши вьюпортом или в фокусе окна ОС.

Источники: https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-driver-in-unreal-engine, C:/Program Files/Epic Games/UE_5.8/Engine/Source/Developer/AutomationDriver/Public/WaitUntil.h, C:/Program Files/Epic Games/UE_5.8/Engine/Source/Developer/AutomationDriver/Private/SlateWidgetElement.cpp

Проверка: Голоса 3-0. Первичная документация Epic, сверенная с исходниками UE 5.8: перегрузки в WaitUntil.h:105–157, интервал по умолчанию в WaitUntil.cpp:188–190, критерий interactable в SlateWidgetElement.cpp:145+, неявное ожидание в DriverSequence.cpp:153–172. Утверждение про инъекцию ввода на платформенном уровне опровергнуто 0-3.

### 5. [medium, голоса 3-0]

[Backend, п.2] Готовый образец: Hearthstone передаёт клиенту не снимки состояния в конце действия, а поток изменяющих состояние Power-пакетов: FULL_ENTITY, SHOW_ENTITY, HIDE_ENTITY, TAG_CHANGE (меняет один тег за раз), BLOCK_START/BLOCK_END, CREATE_GAME, META_DATA и другие. Изменения сгруппированы во вложенные типизированные блоки: ATTACK, JOUST, POWER, TRIGGER, DEATHS, PLAY, FATIGUE, а в новых версиях ещё REVEAL_CARD, GAME_RESET, MOVE_MINION, DECK_ACTION; RITUAL удалён. Блок может вкладываться в другой, когда одно действие вызывает другое. По блокам клиент восстанавливает причинность («что вызвало что») и проигрывает анимации в правильном порядке и с правильными целями.

Вывод для нашего snapshot-стрима: «линии эффектов» надёжнее строить по явному журналу применённых эффектов с причинными блоками (эффект → изменения), который сервер шлёт вместе со снимком. Восстанавливать их сравнением соседних снимков ненадёжно, потому что причинность в итоговом состоянии теряется.

Источники: https://hearthsim.info/docs/gamestate-protocol/, https://raw.githubusercontent.com/HearthSim/python-hearthstone/master/hearthstone/enums.py

Проверка: Голоса 3-0 по двум утверждениям. Источник вторичный: протокол восстановлен сообществом HearthSim по Power.log, официальной спецификации Blizzard нет. Это всё же де-факто эталон: enum зеркалит protobuf игры. Список пакетов неполон: в текущем enum 17 типов, включая TAG_LIST_CHANGE, который меняет несколько тегов сразу. META_DATA не изменяет состояние.

Вывод: трек Suno, сгенерированный через агрегатор SYNTX, скорее всего не считается скачанным через разрешённый канал Suno. Значит, грант подписчика Suno на него, вероятно, не распространяется, и права определяются офертой SYNTX и неизвестным соглашением SYNTX с Suno.

Источники: https://www.musicinafrica.net/magazine/suno-adjusts-ai-music-ownership-terms-after-warner-music-partnership, https://help.suno.com, https://suno.com/terms, https://blog.suno.com

Проверка: Голоса 3-0 по двум утверждениям. Часть про бесплатный план проверяющий подтвердил по первичным статьям help.suno.com (уверенность high). Часть про платные права опирается на вторичный источник от декабря 2025 и уточнена по текущим ToS (уверенность проверяющего medium). Вывод про путь через SYNTX — логическое следствие условия о скачивании, а не прямая формулировка. Отдельное утверждение, что после урегулирования с Warner платные подписчики «не владельцы», опровергнуто 0-3.

### 12. [high, голоса 3-0]

[Музыка → UE, п.5] Импорт аудио в UE 5.8:
- форматы Sound Wave: .wav, .ogg, .flac, .aif, .opus, .mp3;
- разрядность 16 или 24 бит, частота дискретизации любая;
- каналы: моно, стерео, 4.0, 5.1, 7.1;
- всё внутри конвертируется в 16-bit WAV, причём 24-bit источники при конвертации не дитерятся, поэтому Epic рекомендует импортировать 16 бит.

Практика: финальный трек и стингеры довести до 16-bit WAV с дизерингом во внешнем аудиоредакторе, затем импортировать. Генерацию лучше скачивать в lossless (WAV или FLAC). Утверждение «исходный кодек не влияет на итоговое качество» опровергнуто 0-3, а повторное сжатие MP3/OGG-источника накапливает потери (это вывод). 32-bit float WAV выходит за документированную поддержку.

Источники: https://dev.epicgames.com/documentation/en-us/unreal-engine/importing-audio-files

Проверка: Голоса 3-0 по двум утверждениям. Первичная документация Epic с пометкой UE 5.8, загружена 2026-10-05. Локализованные версии (pt-br, ja) совпадают. Сама возможность импорта не говорит о качестве бесшовного цикла: точки петли проверяются отдельно.

## Пробелы и оговорки

Что осталось без проверенных утверждений. По этим темам в отчёте только выводы, а не подтверждённые факты:
- Пункт 1: decals против мешей против одного динамического материала доски; Nanite для плашек (подтверждено только, что Nanite обходит HW occlusion queries); методика замера через stat RHI / stat SceneRendering / ProfileGPU / Unreal Insights / r.DumpDrawCalls.
- Пункт 2: MTG Arena (GRE-сообщения), Gwent, Slay the Spire и Unmatched Digital Edition.
- Пункт 3: политики speed-up, collapse и drop-oldest, ограничение задержки очереди, синхронизация текста с визуалом. Есть только пример из Hearthstone Battlegrounds.
- Пункт 4: причины потери первого клика (SetInputMode GameAndUI, bIsFocusable, режим захвата мыши вьюпортом, кэш hit-test в Slate, инвалидация).
- Пункт 5: промпт-практики для бесшовных лупов и стингеров на 2–3 с, целевые LUFS для музыки и SFX, точки петли, MetaSounds и настройки looping у Sound Wave.

Слабые источники и расхождения:
- Протокол Hearthstone восстановлен сообществом HearthSim по логам, а не опубликован Blizzard. Списки enum в разных версиях расходятся.
- Пункт про ISM, которая не даёт ровно один draw, опирается на блог. Независимо подтверждена только часть про слоты материалов.
- Документация Epic говорит, что occlusion query делается «на Actor». Исходники UE 5.8 показывают, что запрос делается на каждый примитив. В отчёте принята версия исходников.

Сроки действия:
- Все лицензионные условия зависят от даты: оферта SYNTX от 03.07.2026, ElevenLabs Music Terms от 26.05.2026, Suno ToS действуют с 03.09.2026. Условия Suno заметно менялись в 2025–2026 годах.
- Ничто из найденного не устанавливает, какие условия провайдеров действуют при генерации через агрегатор. Оферта SYNTX возлагает ответственность за права третьих лиц на заказчика.

Риск для самой генерации музыки. Пользователь просил, чтобы агент сам сгенерировал музыку в Chrome. По словам проверяющего, п. 9.3 оферты SYNTX запрещает автоматизированный доступ, в том числе эмуляцию действий пользователя и автоматический ввод, без письменного разрешения SYNTX. Генерацию через браузерную автоматизацию или неофициальный MCP стоит согласовать с пользователем: получить письменное разрешение SYNTX или сделать генерацию вручную. Этот отчёт — только синтез исследования. Сама музыка в его рамках не генерировалась.
