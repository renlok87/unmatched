## 1. Разделение ответственности — INT-001

`РЕШЕНИЕ` (преемственность: D-01, D-03, принцип P4 и прежний ADR `docs/unreal/01-architecture-decision.md` «тонкий server-authoritative клиент»; дата подтверждения пакета 2026-09-18; сам ADR — ПЛАН, не реализация).

```text
┌─────────────┐   GraphQL HTTP + WS (graphql-transport-ws)   ┌──────────────────────┐
│  UE-клиент  │ ─────────── мутации (11 шт) ───────────────► │  Сервер NestJS        │
│ ввод,       │ ◄───── HTTP-ответ GameMutationResult ─────── │  АРБИТР и ИСТИНА:     │
│ презентация │ ◄───── подписка gameStateUpdated(since) ──── │  правила, состояние,  │
│ feedback,   │                                            │  таймеры, скрытая     │
│ локальные   │ ◄───── контент-queries (heroes/cards/boards) │  информация, VS_AI-бот│
│ подсказки   │                                            └──────────────────────┘
└─────────────┘                                                      ▲
      ▲ baked-ассеты (манифест 06, пересборка)                        │ контент-queries
      │                                                                │
┌─────────────┐                                            ┌──────────────────────┐
│   Blender   │ — исходники моделей (.blend → FBX → UE)     │  Веб-админка          │
│             │                                            │  управление каталогом │
└─────────────┘                                            │  (контроль данных)   │
                                                           └──────────────────────┘
```

Правила границы:

| Сторона | Отвечает за | Не делает |
|---|---|---|
| Сервер | проверка действий, расчёт правил, хранение состояния, таймеры боя, фильтрация скрытой информации, бот VS_AI, матчмейкинг (после MVP) | не отдаёт правила клиенту для исполнения; не раздаёт 3D-ассеты |
| UE-клиент | ввод, презентация, анимации/VFX/звук (CUE-xxx), локальные ПОДСКАЗКИ (BFS-достижимость GDD-014, причины недоступности GDD-016), хранение токенов (USaveGame), дедуп по sequenceNumber | не считает правила (P4); не восстанавливает скрытое (P4); не хранит игровое состояние как истину |
| Blender | исходники ассетов по стандарту `04`, экспорт FBX | не производит runtime-контент |
| Веб-админка | управление каталогом контента | не управляет партиями и не заменяет клиент |

Запреты (`РЕШЕНИЕ`-преемственность, до появления конкретной потребности, которой текущая архитектура не удовлетворяет): UE dedicated server; GAS (Gameplay Ability System); отдельная БД у клиента; перенос игровых правил на C++ клиента. Все четыре пункта — прямое продолжение прежнего ADR (отвергнуты там же); ни одна потребность MVP (D-03, D-04) их не требует.

## 2. Решения на границе клиент ↔ сервер

Формат каждого: проблема → решение (с меткой) → последствие. Источники фактов: `docs/backend-api/04, 06, 07, 10, 11`; выжимки `_sources/facts-backend.md`.

### INT-002. Двухфазный парсинг JSON-строк

- Проблема: сервер возвращает JSON внутри строк (`state` в `query gameState`; `players`, `fighters`, `handZones`, `boardState`, `metadata` в подписке; `metadata.combatInfo`/`pendingEffects` — вложенные структуры) — `ФАКТ` 04:110-131, 04:442-453, 06.
- Решение: `РЕШЕНИЕ` (преемственность прежнего плана 07; единственно возможное по контракту). Парсинг двухфазный: (1) GraphQL-ответ → DTO с JSON-строками; (2) десериализация каждой строки во внутренние структуры UE. Nullability и имена полей — только по контракту 07 и фактической introspection (см. INT-010), не по «типичному GraphQL» (бриф §11.2).
- Последствие: слой UmModel получает юнит-тесты на фикстурах-дампах реальных ответов (задача TASK-011 их создаёт); любое поле может отсутствовать → парсер толерантен и пишет Warning-лог (сравните INT-007 fallback).

### INT-003. Дедупликация HTTP-ответ + подписка по sequenceNumber

- Проблема: HTTP-ответ мутации и событие `gameStateUpdated` несут одно и то же состояние с одним `sequenceNumber` — `ФАКТ` 04:530. Без дедупликации урон/анимации проигрываются дважды.
- Решение: `РЕШЕНИЕ` (P4; ФАКТ 04:524-529). Единый центр применения состояния: каждый снапшот применяется ровно один раз — по первому приходу номера; второй источник того же номера отбрасывается молча (без анимаций). CUE-очередь запускается из применения состояния, не из источника.
- Последствие: QA-007 (дубль HTTP+WS = одна анимация урона); UI-HUD-CONN (02 §4.8) и S5→S6 машины состояний ввода (02 §6) опираются на это правило.

### INT-004. Gap-протокол и реконнект

- Проблема: события могут приходить с пропуском (`seq > last+1`), при обрыве нужно догнать без повторного расхода карт.
- Решение: `РЕШЕНИЕ` (ФАКТ 04:524-529, 11:288-302 — актуальные доки; прежний план отвергал `eventsSince` — отклонено как устаревшее допущение, `_sources/facts-unreal-legacy.md` п.4). Алгоритм:
  1. `seq <= last` → отбросить (устаревшее/дубль);
  2. `seq == last+1` → применить;
  3. `seq > last+1` → gap: `eventsSince(gameId, lastSeq)` пачками по 100 (`hasMore`) → при большой дыре полный `query gameState`;
  4. Реконнект: `lastSeq` → `query gameSequence(gameId)` → `eventsSince` пачками → свежий `gameState` → перевзять подписку `gameStateUpdated(gameId, since: lastSeq)`;
  5. Журнал вычищается через 30 дней → тогда сразу полный `gameState` (`ФАКТ` 11:300).
- Последствие: никогда не отправлять мутацию повторно «вслепую»; решение о повторе — только после сравнения seq и состояния (GDD-013, сценарий C файла 01); оверлей UI-SCR-RECONNECT (02 §2.8) визуализирует «Пропущено событий: N».

### INT-005. Одна in-flight мутация + локальный feedback

- Проблема: параллельные мутации порождают гонки seq и лишние отказы; на сервере distributed lock TTL 10 с на мутацию — `ФАКТ` 11:123-129.
- Решение: `РЕШЕНИЕ` (преемственность прежнего плана FUmActionGate; P4). Пока мутация in-flight, все игровые кнопки/клетки/карты неактивны с причиной «Отправка действия…»; ввод не накапливается. Повторный клик не отправляет вторую мутацию (QA-003).
- Последствие: у игрока всегда есть локальный feedback «Отправлено…» (02 §4.8); при ошибке — баннер причины + сброс выбора (P2); при сетевой неопределённости — путь S6E из 02 §6 (ждать подписку 3 с → «Проверить состояние»), не слепой ретрай.

### INT-006. Оптимистичное применение своего хода — в MVP НЕТ

- Проблема: `04` допускает оптимистичное применение собственной мутации; прежние планы категорически запрещали предикцию (`_sources/facts-unreal-legacy.md` п.5). Противоречие философий.
- Решение: `ПРЕДЛОЖЕНИЕ` (для утверждения автором; по умолчанию действует с первого дня). В MVP НЕ применять оптимистично: после подтверждения игрок видит «отправлено», изменение применяется только по первому подтверждённому снапшоту (INT-003). Обоснование: пошаговая игра, целевой сервер локальный (задержка ≪ 100 мс); выигрыш предикции мал, цена — рассинхрон подсветок и усложнение отката при отказе сервера.
- Последствие: задержка видимого результата = RTT (обычно незаметна); переоценка — после MVP вместе с/live-балансом. Связанный Q: нет (решение инженерное, не продуктовое); при утверждении автором — перевести в `РЕШЕНИЕ` с датой.

### INT-007. Таймер защиты: primary `timeoutAt`, fallback локальный расчёт

- Проблема: прежний план (`docs/unreal/05-ui-screens.md`, ADR §1.3) утверждает, что `combatInfo.timeoutAt` «никогда не доставляется», и предписывает считать дедлайн локально `startedAt + 30 с`; актуальные доки содержат `timeoutAt` в примерах и рекомендуют его (04:225,233,406,531). Противоречие план↔дока.
- Решение: `ПРЕДЛОЖЕНИЕ` (совпадает с 02 §4.5). Primary — `metadata.combatInfo.timeoutAt` (серверный дедлайн, работает при реконнекте); fallback — локальный расчёт от момента наступления фазы COMBAT + 30 с, если поле отсутствует/нулевое. Окончательная сверка с живым сервером — спайк TASK-011/TASK-012 (после `attack` проверить фактическое наличие и формат поля в подписке).
- Последствие: парсер обязан терпеть отсутствие поля (INT-002); таймер реконнекта не «прыгает» (GDD-006: остаток по timeoutAt, не по локальным часам); QA-004/QA-106 проверяют оба пути.

### INT-008. Обход auto-resolve-без-урона (GAP-001)

- Проблема: при таймауте защиты сервер переводит бой в `COMBAT_RESOLVE`, но урон НЕ применяет (TODO сервера) — `ФАКТ` 10 §3.3, 11:397. Правило настольной игры нарушается («не защитился — получил»).
- Решение: `ПРЕДЛОЖЕНИЕ` (обход из 01 GDD-006; прежний план предлагал то же — «resolveCombat атакующим через ~1,5 с»). Клиент АТАКУЮЩЕГО по истечении локального таймаута (timeoutAt + страховочная пауза ~1,5–2 с, чтобы не отнять окно у «думающего» защитника) сам вызывает `resolveCombat` — контракт разрешает вызов участником боя в фазе COMBAT (`ФАКТ` 04 §9). Тогда резолв и урон проходят штатно. В VS_AI кнопка резолва у атакующего дополнительно задерживается (GAP-010).
- Последствие: UI никогда не обещает «урон применится сам»; баннер «Сервер разрешил бой автоматически (без урона — известное ограничение)» — резерв на случай, когда обход не сработал (02 §4.5); серверная задача «применять урон в auto-resolve» — после MVP (GAP-001, решение «изменить сервер» отложено); QA-106.

### INT-009. Перемещение: `maneuver`, не `moveFighter` (GAP-006)

- Проблема: `moveFighter` тратит действие без добора карты; манёвр настольной игры = движение + добор. Веб-клиент в реальной игре ходит именно `moveFighter` (`ФАКТ` `_sources/facts-web-ux.md`) — его UX нельзя брать как эталон правил.
- Решение: `РЕШЕНИЕ` (следует из D-01: правила не меняются). UE-клиент использует только `maneuver` (пути бойцов + опциональный буст + добор); `moveFighter` скрыт из UI и не вызывается. Различие поведения UE/веба на одном сервере допустимо (обе мутации валидны).
- Последствие: ввод «клик по клетке при выбранном бойце» открывает режим манёвра (путь), а не мгновенный шаг. Таблица 02 §4.10 и машина состояний 02 §6 приведены в соответствие с INT-009 координатором 2026-09-18; QA-003/QA-103-серия.

### INT-010. Скаляры Int vs Float — сверка introspection до написания парсера

- Проблема: прежний план требует Float для `since`/`sequenceNumber`/`turnCount`/`seatOrder`/`version`; актуальная схема 07 объявляет `Int`/`Int!` (`_sources/facts-unreal-legacy.md` п.3; `_sources/facts-backend.md`). Ошибка типа ломает парсер на корню.
- Решение: `РЕШЕНИЕ` (инженерное, 2026-09-18): до написания боевого парсера выполнить introspection-спайк (TASK-011): получить фактическую схему `http://localhost:3000/graphql`, зафиксировать типы всех скаляров состояния, числа парсить по фактическому типу; JSON-числа — толерантно (int/float), но DTO — по introspection.
- Последствие: спайк закрывает противоречие «план↔дока» фактом; результат фиксируется в отчёте TASK-011 и в этой строке (обновить при выполнении).

### INT-011. WS-коды 4403/4408/4409 и пересоздание WS после refresh

- Проблема: наборы WS-кодов прежнего плана (4400/4401/4406…) не совпадают с фактическими (4403/4408/4409) — `ФАКТ` 06:256,585-590.
- Решение: `РЕШЕНИЕ` (по контракту). Обрабатывать: **4403** Forbidden (токен отклонён) → тихо `refreshTokens` (ротация: старый refresh инвалидируется — хранить оба, `ФАКТ` 02) → **пересоздать WS-соединение** (per-subscription auth не работает, токен живёт в `connection_init` — ФАКТ 06:89-93) → повторная подписка с `since=lastSeq`; при неудаче refresh → экран LOGIN («Сессия истекла»); **4408** init timeout и **4409** дубликат id подписки → Warning-лог и повтор как обычный обрыв (без refresh). После любого refresh HTTP-сессии WS пересоздаётся всегда.
- Последствие: UI-SCR-RECONNECT (02 §2.8) реализует ровно этот путь; QA-сценарий «истёкшая сессия» (§6 ниже).

### INT-012. Идемпотентность `createGame` (+ `joinQueue` после MVP)

- Проблема: двойной клик «Создать» создаёт две комнаты; сетевой ретрай create может дублировать.
- Решение: `РЕШЕНИЕ` (контракт `ФАКТ` 03:29-33): `createGame` всегда с `idempotencyKey`, генерируемым клиентом (один ключ на одно намерение создания; новый — только после ошибки, вернувшей игру, или закрытия диалога). `joinQueue` (вне MVP) при включении — тот же механизм.
- Последствие: критерий приёмки лобби 02 §2.3 п.5; игровые мутации идемпотентности НЕ имеют → никогда не ретраятся вслепую (INT-004/005).

### INT-013. Rate limits 30/20 в мин → тосты без авторетрая

- Проблема: сервер ограничивает 30/мин (maneuver, moveFighter, endTurn, toggleDoor, setStance, resolvePendingEffect) и 20/мин (attack, playDefense, resolveCombat, playScheme, pass) — `ФАКТ` 04:21, 11:322-337.
- Решение: `РЕШЕНИЕ` (P2). При ошибке троттлинга: тост «Слишком часто — подождите пару секунд», БЕЗ автоматического повтора; локальный дебаунс повторных кликов (одна in-flight мутация — INT-005 — уже снимает большую часть риска). Словарь код→текст — в слое локализации (перечень ключей `why.*` — 02 §4.2; сюда добавляется `why.rate.limited`).
- Последствие: QA-109; намеренное «мягкое» троттлирование не вводится (02 §4.8 — не замедлять игру).

## 3. Привязка контента к ассетам

### INT-014. Манифест 06 печётся в сборку клиента; ключ — слаг

- Проблема: как связать серверный каталог (БД, пересоздаваемая) с UE-ассетами, не вшивая cuid.
- Решение: `ПРЕДЛОЖЕНИЕ` (по брифу §11.3; совпадает с прежним планом 07 «Baked»). Весь MVP-контент (модели, UI, арты карт, материалы) импортируется в проект UE и упаковывается в сборку; соответствие каталог ↔ ассет — через манифест `06-asset-manifest.csv`: `stableContentKey` = слаг (`medusa`, `king-arthur`, `cobble-city`, `heroSlug:cardSlug` для карт); **cuid не вшивается никуда** (БД может быть пересоздана). Каталог в runtime запрашивается по имени (`HeroDto.id = hero.name` — `ФАКТ` 05:395) и используется для текстов/значений, а НЕ для ассетов.
- Последствие: `contentSummary`/`contentVersion` запрашиваются при старте только для диагностики рассинхрона каталога и baked-контента (предупреждение «каталог изменился — требуется пересборка»); смена ассета = пересборка (INT-017).

### INT-015. `miniModelUrl` в runtime не используется

- Проблема: поле соблазняет «грузить .glb по URL».
- Решение: `РЕШЕНИЕ` (из `ФАКТ`а: в публичном GraphQL API `miniModelUrl`/`characterCardUrl` НЕ экспортируются — только в админских типах; 05:364-365, 12:88-90). Runtime-загрузка произвольного .glb и превращение его в работающий ассет packaged-игры не проектируется (бриф §11.3). .glb из скрапа — только референсы формы (D-06).
- Последствие: сборка не зависит от Supabase-бакета; GAP-013 закрыт «принять».

### INT-016. Конвейер артов карт: sync → WebP→PNG → упаковка

- Решение: `РЕШЕНИЕ` (следует из D-09). Конвейер: (1) `node scripts/sync-card-assets.mjs medusa king-arthur` → `public/assets/decks/<hero>/<card>.webp` (EN) и `.../ru/...` (RU) — сейчас арты `not_synced`/`blocked` в 06 (`ФАКТ` facts-content); (2) офлайн-конвертация WebP→PNG (`docs/unreal/07` — план; UE 5.8 нативно НЕ декодирует WebP — пометка «проверить для UE 5.8» в спайке TASK-013); (3) импорт PNG в `/Game/Textures/Cards/...` по именам строк `ASSET-CARDART-*` из 06; RU-арт — вариант, EN — базовый (INT-018).
- Последствие: 27 строк cardArt из 06 переводятся из `blocked` в `imported`; проверка пропорций 512×716 (прежний план — проверить фактические после синка); GAP-015.

### INT-017. Политика обновления контента

- Решение: `ПРЕДЛОЖЕНИЕ`. **MVP: контент обновляется пересборкой клиента** (следствие INT-014). Правки в админке, видимые БЕЗ пересборки: только значения, входящие в живое состояние партии (баланс HP/значения карт в состоянии, тексты в состоянии/каталоге для запросов runtime). НЕ видимые: ассеты, baked-каталог, структура колод при отсутствии в состоянии. **После MVP: live-обновление** — заблокировано серверными ограничениями: `contentVersion` — константа `'2.0.0'` (инкремент вручную), Redis-кэш контента TTL 1 ч, админ-мутации кэш НЕ инвалидируют — `ФАКТ` 05:387, 12:264-276 (GAP-021; решение «изменить сервер» — отложено).
- Последствие: QA-013 проверяет именно эту политику; в будильник baked-контента встает сверка `contentVersion` (INT-014).

### INT-018. Fallback-иерархия отсутствующего контента

- Решение: `РЕШЕНИЕ` (D-09/P2 + бриф §11.3). Единая иерархия:
  1. **Модель фигурки** отсутствует/не импортирована/неизвестный content key → `ASSET-PLACEHOLDER-MANNEQUIN` (серый манекен, static; кольцо команды сохраняется — ASSET-MARKERS-001) + Warning-лог; партия продолжается.
  2. **Арт карты** отсутствует → рамка-заглушка `UI-CARD-FRAME` с локализуемым названием/значениями/текстом (данные карты есть в состоянии/каталоге независимо от арта).
  3. **Перевод** отсутствует → EN-текст с индикатором «нет перевода» (критично для 14/16 карт Arthur — GAP-016, Q-104).
  4. **Неизвестный stableContentKey** → журнал + заглушка из п.1/2; никогда — молчаливый пропуск или краш.
  Звук/VFX отсутствующего ассета — тишина + лог (правило 07 «fallback»).
- Последствие: QA-012; манекен сознательно static — скелетные клипы на нём не играют, движение работает (CUE-007) — честное ограничение, не баг.

## 4. Геометрия игрового поля (бриф §11.4) — INT-019

`ПРЕДЛОЖЕНИЕ` (клетка 100 uu — из прежнего плана `docs/unreal/06`, статус ПЛАН; принято как предложение до контрольной сцены; масштаб согласован с 04 §1). Источник истины геометрии — `boardState` живой партии, НЕ контентный `Board` и НЕ арт (03 §4.2, GAP-014).

Контракт соответствия:

```text
serverCell(x,y) из boardState.cells
  → зоны cells[y][x].zones (мультизоны), типы клеток
  → мировая позиция UE (формула ниже)
  → область выбора мышью (L1: 100×100 uu на плоскости + «столб» ~60 uu для фигурки — 03 §4.1)
  → посадочная точка фигурки: центр клетки, Z=0 (pivot на опоре — 04 §1)
```

| Параметр | Значение |
|---|---|
| Начало координат | Центр доски в мировом (0,0,0); Z=0 — игровая плоскость |
| Оси | serverCell.x → мировая +X (колонки); serverCell.y → мировая +Y (строки), строка y=0 — ДАЛЬНЯЯ (север) от игрока (камера Yaw −90 смотрит вдоль −Y — 03 §2) |
| Масштаб | Клетка 100×100 uu (1 клетка = 100 uu) |
| Высота опоры | Игровая плоскость Z=0; подставка 5–6 uu; маркеры над плоскостью 2–4 uu (ASSET-MARKERS-001) |

Формула (W колонок, H строк — из boardState, НЕ хардкод):

```text
World(x, y) = ( (x − (W−1)/2) · 100 ,  (y − (H−1)/2) · 100 ,  0 )
```

Обратное преобразование (клик): луч → пересечение с плоскостью Z=0 →
`cellX = round(wx/100 + (W−1)/2)`, `cellY = round(wy/100 + (H−1)/2)`, затем проверка границ `0 ≤ cellX < W`, `0 ≤ cellY < H`; попадание по фигурке — трассировка в UCX_/UCP_-коллизию (столб выбора, 04 §1).

Проверочные точки (минимум три: два противоположных угла + соседние клетки):

Для **6 колонок × 4 строк** (код `src/core/data/boards/cobble-city.ts` — `ФАКТ` facts-content):

| serverCell | Ожидаемая мировая позиция | Проверяем |
|---|---|---|
| (0, 0) — дальний угол | (−250, −150, 0) | противоположный угол №1 |
| (5, 3) — ближний угол | (+250, +150, 0) | противоположный угол №2; дистанция до (0,0) = √(500²+300²) ≈ 583.1 uu |
| (2, 1) и (3, 1) — соседи | (−50, −50, 0) и (+50, −50, 0) | соседние клетки: расстояние ровно 100 uu по X, одинаковый Y |

Оговорка для **5×6** (30 клеток — проверка API брифа §2.2; геометрия НЕ подтверждена — GAP-014): формула та же, W=5, H=6; контрольные точки пересчитываются: (0,0) → (−200, −250, 0); (4,5) → (+200, +250, 0); (2,2)/(2,3) → (0, −50, 0)/(0, +50, 0) — соседи по Y через 100 uu. Если boardState даёт иные W/H (вплоть до нерегулярной сетки) — параметры W/H читаются из состояния; для нерегулярной доски потребуется адаптер (отдельное решение, не молчать — бриф §11.4).

Экранный Y и ориентация: экранная «верхняя» строка кадра = y=0 (дальняя). Какая серверная сторона достаётся локальному игроку на старте (seat + офсеты, 10 §5.5) — проверить спайком TASK-012 по стартовым позициям живой партии; если локальный игрок окажется на стороне y=0 — повернуть всю доску на 180° вокруг Z для локального игрока (параметр сцены; контракт координат не меняется, пересчитывается только экранное представление). `ВОПРОС` Q-102 (кто ходит первым/seatOrder) закрывается тем же спайком.
