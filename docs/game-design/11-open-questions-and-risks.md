## 1. Реестр вопросов Q-xxx

### Q-0xx — продуктовые/общие

**Q-005. Регистрация аккаунтов `[БЛОК 0–1]`**
- Формулировка: как создаются аккаунты для UE-MVP, если в веб-клиенте роут регистрации закомментирован (`ФАКТ` facts-web-ux), а GraphQL `register` существует (`docs/backend-api/02`)?
- Почему важно: без аккаунтов нет входа двух игроков — нет ни одной приёмочной проверки.
- Варианты: (а) аккаунты создаются вручную/напрямую GraphQL на время MVP (GAP-018-обход); (б) включить веб-роут регистрации; (в) сделать регистрацию в UE за флагом сборки (02 §1.4).
- Что блокирует: вход в клиент, все QA; решение по UI LOGIN (`UI-SCR-LOGIN`).
- Кому решать: автор (продукт) + сервер (если (б)).

### Q-1xx — геймдизайн (новые из файла 01)

**Q-101. Серверная валидация дубля героя `[БЛОК 0–1]`**
- Формулировка: оба игрока выбирают одного героя — есть ли серверная валидация, или дубли блокируются только веб-клиентом (01 GDD-001, пограничный случай)?
- Почему важно: определяет логику кнопки «Выбрать» в `UI-SCR-ROOM` и честность запрета; клиентский запрет без серверного = гонка на одновременный выбор.
- Варианты: (а) сервер валидирует (тогда клиент доверяет отказу); (б) сервер не валидирует (клиент обязан защищаться сам + правило «кто первый»).
- Что блокирует: UI комнаты (этап 2, TASK-025), сценарий QA-001.
- Кому решать: spike TASK-012 (живая проба одновременного выбора) + код сервера.

**Q-102. Кто ходит первым / seatOrder `[БЛОК 0–1]`**
- Формулировка: по какому правилу сервер определяет первого ходящего и рассадку стартовых позиций (seat)? В доках правило не зафиксировано (01 GDD-002; 05-матрица: startingPositionsJson из БД).
- Почему важно: баннер «Ваш ход» на старте, ориентация доски для локального игрока (INT-019: поворот доски на 180° при необходимости), тексты подсказок.
- Варианты: (а) случайный выбор сервером; (б) по seatOrder (хост первый); (в) по данным доски.
- Что блокирует: INT-019 (ориентация), UI первого хода, сценарий A файла 01.
- Кому решать: spike TASK-012 (дампы стартов нескольких партий) + код сервера.

**Q-103. Семантика pass `[БЛОК 0–1]`**
- Формулировка: `04:267` — «сброс верхней карты колоды + доп. действие» против `10 §1.2` — «тратит действие, passCount++» (01 §7 п.2). Какое поведение фактическое?
- Почему важно: кнопка «Пас» обещает игроку результат; неверная формулировка = сломанное ожидание (P2).
- Варианты: (а) тратит действие (10); (б) сброс верхней карты + доп. действие (04); (в) различается по фазе.
- Что блокирует: текст кнопки/подсказки, QA-002-класс проверок; до ответа UI подаёт пас нейтрально (01 §6.9).
- Кому решать: spike TASK-012 + код сервера; при расхождении кода с обоими доками — автор.

**Q-104. Источник RU-текстов карт Arthur**
- Формулировка: у 14/16 карт King Arthur нет RU-текста в скрапе (только Feint/Regroup — 01 §6.4, GAP-016). Откуда брать перевод для D-08?
- Почему важно: RU — язык по умолчанию (UI-ACC-010); EN-fallback допустим, но не должен стать молчаливой нормой для половины карт матча.
- Варианты: (а) принять EN-fallback на MVP (INT-018), перевод после MVP; (б) ручной перевод автором до этапа 5; (в) найти другой источник.
- Что блокирует: не блокирует 0–1; полнота локализации этапа 5 (TASK-051), QA-011/QA-104.
- Кому решать: автор.

**Q-105. Политика manualEffects**
- Формулировка: карты, чьи тексты движок не распознаёт, попадают в `manualEffects` (09 §2; 05-матрица: Winged Frenzy — воскрешение гарпии, EffectType отсутствует; «самые сложные карты — кандидаты на упрощение»). Что видит игрок и что делает UI?
- Почему важно: «эффект не сработал сам» должен быть объяснён (P2), а не молча проглочен; блокировать игру нельзя (01 GDD-007).
- Варианты: (а) баннер «Эффект карты примените вручную по тексту» без блокировки (05-матрица, строка 8); (б) упрощённое поведение для конкретных карт в MVP (сервер); (в) исключить проблемные карты из MVP-дек (меняет состав — решение автора).
- Что блокирует: не блокирует 0–1; UX схем этапа 3 (TASK-031), GAP-005.
- Кому решать: автор (объём) + сервер (реализация (б)).

### Q-2xx — UX/UI (новые из файла 02)

**Q-201. «Мои активные игры» для возврата в партию**
- Формулировка: поддерживает ли сервер перечисление активных игр игрока (в вебе есть MyGames — facts-web-ux; в 03 явно не описана)? Нужен ли возврат в живую партию из BOOT (02 §1.3)?
- Почему важно: перезапуск приложения во время партии — реальный случай (QA-006-смежный); без операции игрок «теряет» партию из UI.
- Варианты: (а) сверить API и сделать «Вернуться в партию» в BOOT; (б) MVP без возврата (fallback 02 §1.3: игрок создаёт новую; партия живёт на сервере и завершится таймаутом/соперником).
- Что блокирует: не блокирует 0–1; сценарий BOOT этапа 2+ (TASK-025).
- Кому решать: spike (introspection/код) + автор (объём).

**Q-202. Обязателен ли герой для ready/старта**
- Формулировка: `startGame` требует только isReady всех (ФАКТ 03); может ли игрок быть «готов» без героя (02 §10 п.4)?
- Почему важно: активность кнопки «Начать» и причина её блокировки (P2); защита от старта без героя.
- Варианты: (а) сервер требует героя → клиент блокирует «Готов» без героя; (б) не требует → клиент сам запрещает старт без героев.
- Что блокирует: не блокирует 0–1; UI комнаты (TASK-025).
- Кому решать: spike TASK-012/код сервера.

**Q-203. Рематч («Сыграть ещё»)**
- Формулировка: нужна ли кнопка быстрого реванша на `UI-SCR-GAMEOVER` и есть ли серверная поддержка быстрого пересоздания комнаты тем же составом (02 §2.9)?
- Почему важно: основной цикл «партия → партия» (00 §5) сегодня требует полного прохода через лобби.
- Варианты: (а) MVP без рематча (кнопка одна — «В лобби»); (б) рематч = createGame+join автоматикой клиента.
- Что блокирует: не блокирует; полировка цикла (этап 5+).
- Кому решать: автор (объём) + spike (мутации).

**Q-204. Показывать ли свою топ-карту колоды (topCard)**
- Формулировка: topCard своей колоды доступен только в полном `gameState` (ФАКТ 04); показывать ли его (02 §11 п.4)?
- Почему важно: лишнее состояние UI и лишние догрузки ради слабой ценности; в настольной игре верхняя карта скрыта.
- Варианты: (а) не показывать в MVP (ПРЕДЛОЖЕНИЕ 02); (б) показывать при клике на колоду (догрузка gameState).
- Что блокирует: не блокирует; UI-HUD-DECKS (этап 2/5).
- Кому решать: автор (UX-решение).

**Q-205. Минимальное окно 1280×720**
- Формулировка: фиксировать ли 1280×720 как нижнюю границу поддержки (D-07 говорит про 1080p; поведение ниже 720p не определено — 02 §11 п.5)?
- Почему важно: компоновка HUD (якоря 02 §4.1) и QA-011 привязаны к нижней границе.
- Варианты: (а) 1280×720 — минимум, ниже — фиксированный лейаут без гарантий; (б) поддерживать ниже с упрощённым HUD.
- Что блокирует: не блокирует; QA-011 условия, компоновка этапа 2 (TASK-026).
- Кому решать: автор (UX-решение).
