## 2. Почему WBP создаются скриптом UnrealEditor-Cmd арт-worktree вместе с C++

GUI арт-проекта не запущен, а главный редактор (PID 46136) открыт на другом проекте. Поэтому MCP UMGToolSet недоступен: его сервер живёт только внутри GUI-редактора с открытым проектом. Кроме того, функции UMGToolSet помечены `AICallable`, а не `BlueprintCallable`, и из Python их не вызвать. Чистый Python тоже не справится: `UWidgetBlueprint::WidgetTree` — `UPROPERTY()` без Edit/BlueprintVisible, Python до дерева не дотягивается.

Выбран путь «C++ `UUserWidget` + `BindWidget` + WBP-наследник, созданный скриптом»:

- `US08ArtHudAuthoringLibrary::AuthorArtHudWidgetBlueprints` (`S08ArtHudAuthoring.cpp`) — редакторная функция, тело под `WITH_EDITOR`. Зависимости `UnrealEd`/`UMGEditor`/`Kismet`/`AssetRegistry` подключаются только при `Target.bBuildEditor`, в игровой target они не линкуются. Функция создаёт WBP через `FWidgetBlueprintOperationUtils::CreateWidgetBlueprint`, строит дерево той же `BuildDefaultTree`, которую классы используют в рантайме, и прикрепляет узлы через `FWidgetBlueprintOperationUtils::AddWidget` (GUID переменных, как в дизайнере). Затем компилирует и сохраняет.
- `tools/art/umg/ue_author_art_hud.py` вызывает её из `UnrealEditor-Cmd … -run=pythonscript -nullrhi` **арт-worktree**, перезагружает ассеты, проверяет родителя и пишет отчёт с sha256.
- Обёртка — `python tools/art/art_hud_umg.py author`. Отчёт: [content/wbp-author.json](hud-umg-w4c-2026-09-29/content/wbp-author.json). Результат: `created`, `compileStatus up-to-date`. `WBP_S08ArtPlate.uasset` sha256 `5d0924ec…`, 16 виджетов; `WBP_S08ArtIcon.uasset` sha256 `cae00e77…`. Промежуточные предупреждения «привязка не найдена» появляются, пока дерево собирается по одному узлу; финальная компиляция без предупреждений.
- Папка `/Game/S08` уже в `DirectoriesToAlwaysCook`, поэтому `DefaultGame.ini`, входящий в production-baseline, не менялся. В packaged-трассе: `HUD art widget plate … source=/Game/S08/UI/ArtHud/WBP_S08ArtPlate class=…WBP_S08ArtPlate_C parts=1 codeDefaultTree=0`. Если WBP не скукан, клиент берёт дерево класса по умолчанию и пишет `source=code-default`. Если UMG-виджет не создался, клиент откатывается на Slate с `parts=0`.

### 4.4 ΔGT (игровой поток) — стоимость UMG против Slate

Метод. В режиме alternate оба вида стоят в одной геометрии, виден один, переключение каждые 3 с, начиная с ShotAfter + 4 с (после кадра-снимка и твина камеры). Первые 5 кадров после переключения не считаются. Каждый период пишет строку `HUD alternate period=N impl= frames= gameAvg= gameP50= gameP95= gpuP95=`. Разница считается по соседним парам периодов «UMG / Slate» внутри одного клиента: всплеск сторонней нагрузки попадает в обе половины пары. Раздельные прогоны umg/slate показаны только для справки: между процессами фон дрейфует, и это видно уже по кадрам до появления плашки (`afterWarmup`).

| Замер (хост, 5×, плашка + иконка 48 на экране) | ΔGT p95 UMG − Slate |
| --- | --- |
| **60 парных периодов, 6 прогонов, медиана** | **−0,017 мс** (среднее +0,029; 78 % пар ≤ 0,3) |
| Те же пары: медиана Δp50 / Δсреднего / ΔGPU p95 | −0,011 / +0,007 / −0,006 мс |
| p95 по всему прогону, 6 прогонов | +0,26, +0,01, +0,28, −0,10, −0,06, −0,05 — среднее **+0,057 мс** |
| Раздельные процессы, 2 + 2 прогона (справочно) | −1,435 мс — дрейф фона: `afterWarmup` 3,44/2,03 против 3,70/4,33 |

Критерий меморандума ΔGT p95 ≤ 0,3 мс **выполнен** и медианой пар, и средним по прогонам. Устойчивой стоимости UMG-плашки на игровом потоке не видно: разница медиан и средних в пределах ±0,01 мс.

История замера — честно. В промежуточном бинарнике G3 (тот же код umg/slate, период 3 с, 4 прогона) p95 по прогону дал +1,00, +0,51, +0,14, −0,21, среднее +0,36 мс, то есть выше порога. При этом Δсреднего +0,03, Δp50 ≈ 0. В те минуты сторонний headless Blender (§5.4) загружал около 14 ядер, и хвост p95 определяли всплески. Поэтому добавлены строки периодов и парный метод, а итоговый набор G4 снят заново. Прогоны G3 вынесены из дерева (§7).
