## 2. Почему три прогона, а не один

1. **Партия заканчивается раньше 240 с.** `run-combat-demo` доигрывает партию до GAME_OVER, а `-RunSeconds` — только
   верхняя граница, после которой клиент выходит. На Cobble партия длится ≈ 60–70 с, на всех досках в этой волне —
   52–88 с, из-за жадной атаки Medusa. Продлить её без изменения кода нельзя.
2. **Одна фокусировка на прогон.** Клиент (`S08FlowGameMode`) делает одну фокусировку `-ArtPreviewFocusZoom` за
   прогон при `-ArtPreviewSelectOwnHero`. Шага «снимок» в `-ArtPreviewInputPlan` нет. Серию из четырёх зумов в одном
   процессе без пересборки не снять.
3. **K2 в бою испортил бы K3.** В бою приближение хоста осталось бы на кадрах K3 хоста (`s09-damage-combat`,
   `s09-combat-result`).
4. **Задание требует один бинарник.** Поэтому код не менялся.

## 4. Производительность: как читать

- Везде ограничение `t.MaxFPS 30` на каждый клиент. `FrameRateLimit=60` из пакета перекрыт им для пары.
- **Фон машины без клиентов:** GPU p50 28 %, p95 32 %
  ([gpu-baseline.json](../ART-005/art3-live-3boards-r3-2026-09-30/packaged/gpu-baseline.json)). Основные
  потребители — `claude.exe` ≈ 20 % SM, `dwm.exe` ≈ 14 %. Были открыты Blender GUI :9876/:9877 (без рендера),
  параллельно шла только работа с документами.
- **Вклад пары** — примерно +10…+14 п. п. к фону по p50 (пара с фоном — p50 38–42 %).
- **gpuMs трассы и GPUTime** при ограничении FPS не годятся для сравнения стоимости рендера (AGENTS.md: для этого
  есть `render_bench.py`). GPUBusy — сумма именованных GPU-проходов, типичная стоимость кадра клиента.
- Это dev-PC (RTX 4090), не целевой D-07, и машина не тихая.
