## 1. Карта экранов

### 1.1. Экраны MVP

| UI-ID | Название | Назначение | Приоритет | Вход | Выход |
|---|---|---|---|---|---|
| UI-SCR-BOOT | Загрузка (Boot) | Инициализация, восстановление сессии, предзагрузка контента | P0 | Автозапуск приложения | → LOGIN (нет/протух токен) или → LOBBY (сессия восстановлена); при живой партии → предложение вернуться в игру |
| UI-SCR-LOGIN | Вход | Вход существующим аккаунтом (email+пароль) | P0 | Из BOOT, разлогин, потеря сессии | → LOBBY (успех) |
| UI-SCR-LOBBY | Лобби | Список открытых игр, создание приватной комнаты (1×1 / VS_AI), вход по коду | P0 | Из BOOT/LOGIN/GAMEOVER | → ROOM (create/join); выход из приложения |
| UI-SCR-ROOM | Комната | Слоты игроков, выбор героя, готовность, код приглашения, старт хостом, отсчёт | P0 | Из LOBBY | → GAME (старт) или → LOBBY (выход) |
| UI-SCR-GAME | Игровой HUD | Вся партия: поле, рука, бой, отложенные эффекты | P0 | Из ROOM; возврат после реконнекта | → GAMEOVER; → LOBBY («Покинуть») |
| UI-SCR-INSPECT | Инспектор карты (оверлей) | Только чтение: любая видимая карта, без отправки действий | P0 | ПКМ по карте/сбросу/журналу поверх ROOM/GAME | Закрытие (Esc/ПКМ/кнопка) — возврат в предыдущее состояние |
| UI-SCR-PAUSE | Пауза/Настройки (оверлей) | Минимальные настройки: звук, язык, UI, анимации; выход из партии | P0 | Esc/кнопка ⚙ поверх LOBBY/ROOM/GAME | Закрытие (Esc) — продолжение |

### 1.3. Слои и навигация (ПРЕДЛОЖЕНИЕ)

ПРЕДЛОЖЕНИЕ (идея из прежнего плана `docs/unreal/05-ui-screens.md`, §1.2): четыре слоя CommonUI — `Game` (HUD), `Menu` (экраны маршрута BOOT→LOGIN→LOBBY→ROOM), `Modal` (инспектор, настройки, подтверждения, результат), `Toast/Overlay` (реконнект, всплывающие ошибки). Экраны маршрута заменяют друг друга (стек не растёт); модалки поверх любого слоя; оверлей реконнекта — верхний, блокирует ввод. Обоснование: ровно одна «модальная» причина блокировки за раз (реконнект важнее подтверждения выхода), и предсказуемое поведение Esc (см. §2 каждого экрана).

Граф переходов маршрута (ПРЕДЛОЖЕНИЕ; триггеры — из контрактов `docs/backend-api/02`, `03`):

```
BOOT ──(refresh есть, refreshTokens OK)──► LOBBY ──createGame/joinGame──► ROOM ──startGame──► GAME ──GAME_OVER──► GAMEOVER ──► LOBBY
 │ нет токена / refresh провален                                          │ leaveGame                    │ «Покинуть» (confirm) ──► LOBBY
 ▼                                                                        ▼                             │
LOGIN ──login OK──► LOBBY                                              LOBBY                            ▼
любой экран ──(сессия потеряна)──► LOGIN                          (хост удалил игру: «Игра не найдена»)
ROOM/GAME ──(обрыв связи)──► RECONNECT (оверлей, см. UI-SCR-RECONNECT)
```

Возврат в живую партию после перезапуска приложения: BOOT после восстановления сессии проверяет наличие своей игры в статусе IN_PROGRESS (в вебе есть операция MyGames — ФАКТ, `facts-web-ux`; поддержка сервером — ВОПРОС (новый), см. §11) и предлагает «Вернуться в партию / В лобби». ПРЕДЛОЖЕНИЕ; не блокирует MVP (fallback — вход по ссылке/коду отсутствует, игрок просто создаёт новую).

### 1.4. Регистрация — Q-005

Вход в UE-клиенте MVP — только существующим аккаунтом (раздел 7 файла 00: «Вход существующим аккаунтом (email+пароль); `ВОПРОС` Q-005 о регистрации»). Экран UI-SCR-LOGIN проектируется без регистрационной формы: место под ссылку/кнопку «Создать аккаунт» зарезервировано, но скрыта за флагом сборки и включается только после решения Q-005 (в вебе роут регистрации отключён — ФАКТ, `facts-web-ux`). До решения аккаунты создаются вне клиента (напрямую через GraphQL `register` из `docs/backend-api/02` или вручную) — это эксплуатационное следствие Q-005, не решение.

## 2. Карточки экранов MVP

Формат карточки — §7.1 брифа. Общие соглашения (действуют для всех карточек, чтобы не повторять):

- Безопасные зоны: контент не ближе 24 px к краям окна при 1080p; интерактивные элементы — не ближе 48 px (ПРЕДЛОЖЕНИЕ).
- Якоря: верхняя панель — top-center stretch; боковые панели — left/right center; рука — bottom-center; журналы — left-bottom (ПРЕДЛОЖЕНИЕ).
- Ошибка сети вне партии: баннер в шапке экрана + кнопка «Повторить»; вход в ROOM/GAME при отсутствии сети невозможен, но окно остаётся работоспособным (локальная навигация) — ПРЕДЛОЖЕНИЕ.
- Ошибка сети в партии: не баннер, а оверлей UI-SCR-RECONNECT (§2.8).
- Escape: закрыть верхнюю модалку; если модалок нет — открыть UI-SCR-PAUSE (в GAME/ROOM) или ничего (LOBBY/LOGIN). Двух нажатий Escape подряд недостаточно для разрушительного действия: выход из партии/комнаты всегда через подтверждение (ПРЕДЛОЖЕНИЕ).
- Локализация: весь текст — локализуемые строки (RU/EN, D-08), даты/числа — по локали; проверка длинными строками — §7.5.
- Переходы экранов: затемнение/проявление 200–300 мс (ПРЕДЛОЖЕНИЕ; в вебе референс-тайминг tween 280 мс — ФАКТ, `facts-web-ux`).
- Звуки: имена событий звука фиксируются в `07-animation-vfx-audio.csv` (CUE-*); здесь — только качественные требования (клик, ошибка, успех, таймер).

### 2.1. UI-SCR-BOOT — Загрузка

```text
UI-ID / название / назначение: UI-SCR-BOOT / Загрузка / инициализация приложения,
восстановление сессии по refresh-токену, предзагрузка контента первой партии.
Как попасть / как выйти: автозапуск приложения / автоматический переход на
  LOGIN или LOBBY (см. сценарий).
Основной сценарий:
  1) логотип + прогресс-бар; 2) попытка восстановить сессию (refresh-токен из
  USaveGame — ФАКТ, docs/backend-api/02 «хранение в USaveGame»);
  3) при успехе — предзагрузка контента в порядке: contentVersion → AllHeroes →
  HeroDetails → AllBoards → HeroStanceOptions → ассеты (ФАКТ, docs/backend-api/05,
  порядок загрузки контента); 4) переход в LOBBY (или предложение вернуться в
  живую партию, §1.3).
Макет: по центру — логотип (ASSET, файл 04/06), под ним прогресс-бар 480×8 px
  с подписью этапа («Проверка сессии…», «Загрузка героев… 12/16»); внизу —
  версия сборки и адрес сервера (мелко, для отладки). Всё остальное — пусто.
Контент и источник: contentVersion/AllHeroes/... — публичные queries контента
  (docs/backend-api/05); восстановление сессии — mutation RefreshTokens
  (docs/backend-api/02); ничего не показывается из игровного состояния.
Действия и клавиши: нет интерактива; Esc игнорируется (нечего отменять).
Пустое состояние: нет.
Загрузка / ожидание: сам экран — состояние загрузки; этапы обязательны к
  показу, «висящий» прогресс без подписи этапа > 2 с — дефект приёмки.
Недоступность и её причина: сервер недоступен — не блокирует вход в LOGIN:
  контент догружается в фоне из LOBBY с индикатором (ПРЕДЛОЖЕНИЕ: логин не
  должен ждать каталога героев).
Ошибка / повтор / нет сети: ошибка контента → баннер «Контент недоступен,
  частичный офлайн-режим» + «Повторить» (частичный режим = игра возможна,
  если нужные данные уже в кэше; иначе блокируется экран ROOM с причиной);
  ошибка refresh (4403/ротация) → тихий переход в LOGIN без сообщения об
  ошибке (это нормальный сценарий, а не сбой).
Фокус и Escape: фокуса ввода нет; Escape глотается.
Изменение размера / длинный текст / локализация: центральная компоновка
  инвариантна к размеру окна; подписи этапов — короткие строки RU/EN.
Звуки и переходы: один звук запуска (по готовности ассетов); переход —
  проявление следующего экрана 250 мс.
Критерии приёмки: (1) при наличии валидного refresh-токена пользователь
  попадает в LOBBY без ввода пароля; (2) при его отсутствии — в LOGIN; (3) этап
  прогресса всегда подписан; (4) отсутствие сервера не приводит к вечному
  спиннеру дольше 10 с — показывается баннер с «Повторить».
```

### 2.2. UI-SCR-LOGIN — Вход

```text
UI-ID / название / назначение: UI-SCR-LOGIN / Вход / аутентификация существующего
аккаунта (email+пароль); регистрации нет (Q-005, §1.4).
Как попасть / как выйти: из BOOT (нет сессии), после потери сессии / «Выйти» /
  переход в LOBBY после успеха.
Основной сценарий: ввести email → Tab → пароль → Enter → индикатор «Вход…» →
  LOBBY. Второй сценарий: возврат в живую партию, если она есть (§1.3).
Макет: карточка 480×~420 px по центру (якорь center): логотип, поле Email,
  поле Пароль (с переключателем видимости), кнопка «Войти» (на всю ширину
  карточки), зона ошибки под кнопкой, снизу мелко — «Создать аккаунт» (скрыта
  до решения Q-005, §1.4), выбор языка RU/EN в правом нижнем углу экрана.
Контент и источник: mutation Login → accessToken/refreshToken/user
  (docs/backend-api/02); сохранение пары токенов + ротация (при refresh старый
  инвалидируется — сохранять оба — ФАКТ, docs/backend-api/02) в USaveGame.
Действия и клавиши: Tab/Shift+Tab — навигация; Enter — отправка; Esc — очистка
  фокуса/поля пароля (не выход из приложения).
Пустое состояние: поля с placeholder-примерами; кнопка «Войти» активна только
  при непустых полях (валидация длины — локальная, остальное — серверу).
Загрузка / ожидание: кнопка превращается в «Вход…» с индикатором (семейство
  UI-LOADER), повторный Enter/клик блокируется (одна мутация за раз, §4.8).
Недоступность и её причина: кнопка неактивна с причиной-тултипом «Заполните
  email и пароль» (P2).
Ошибка / повтор / нет сети: неверные учётные данные — «Неверный email или
  пароль» (без раскрытия, какой именно поле неверно — стандарт безопасности);
  нет сети — «Сервер недоступен» + «Повторить»; таймаут запроса — как нет сети.
  Автоповтор запрещён (login не ретраится вслепую — как в вебе мутации не
  ретраятся, ФАКТ facts-web-ux).
Фокус и Escape: фокус в Email при показе; Esc не закрывает приложение и не
  «проваливается» дальше.
Изменение размера / длинный текст / локализация: карточка фиксированной
  ширины, центрируется; строка ошибки до 2 строк с переносом; RU/EN на лету.
Звуки и переходы: звук успеха (вход), звук ошибки (короткий, не злой);
  переход в LOBBY — проявление 250 мс.
Критерии приёмки: (1) успешный вход с валидной парой; (2) сообщение об ошибке
  без стоп-слова «ошибка приложения»/стектрейса; (3) Enter всегда отправляет
  форму ровно один раз; (4) язык переключается до входа; (5) валидная сессия
  не требует повторного ввода пароля после перезапуска (через BOOT).
```

### 2.3. UI-SCR-LOBBY — Лобби

```text
UI-ID / название / назначение: UI-SCR-LOBBY / Лобби / список открытых игр,
создание приватной комнаты (ONE_V_ONE или VS_AI, доска Cobble City), вход по
коду приглашения.
Как попасть / как выйти: из BOOT/LOGIN/GAMEOVER / кнопка «Выйти» (logout →
  LOGIN), закрытие окна приложения.
Основной сценарий: игрок видит список открытых игр (обновляется), жмёт
  «Создать приватную комнату» (режим 1×1) → ROOM. Либо вводит код из 6 символов
  → «Войти» → ROOM. Либо жмёт «Присоединиться» в строке игры из списка.
Макет (схема §3.1): шапка (логотип, имя пользователя, ⚙ настройки, язык);
  слева — список игр (карточки-строки) с кнопкой «Обновить»; справа — колонка
  из двух панелей: «Создать игру» (режим: 1×1 | VS_AI; доска: Cobble City;
  кнопка «Создать») и «Войти по коду» (поле на 6 символов + кнопка).
Контент и источник: список — query availableGames (docs/backend-api/03) с
  полями id/status/mode/code/players (username, isReady); обновление —
  периодический опрос (в вебе 30 с — ФАКТ facts-web-ux; ПРЕДЛОЖЕНИЕ: 15 с +
  кнопка ручного обновления + обновление при возврате фокуса окна; подписка на
  изменение списка на сервере отсутствует — ФАКТ: в 03 подписок лобби-списка
  нет); создание — mutation CreateGame (input + idempotencyKey — ФАКТ 03;
  idempotencyKey генерирует клиент, чтобы повтор клика не создал две комнаты);
  вход по коду/из списка — mutation JoinGame.
Действия и клавиши: клики мышью; Enter в поле кода = «Войти»; F5/«⟳» =
  обновить список; Esc — ничего (или пауза-настройки).
Пустое состояние: «Сейчас открытых игр нет. Создайте свою комнату и передайте
  код другу» + акцент на панели создания (референс — веб-лобби, ФАКТ
  facts-web-ux).
Загрузка / ожидание: скелетон-строки списка (семейство UI-LOADER); кнопки
  создания/входа — в состоянии «…» на время мутации, повторный клик блокируется.

Изменение размера / длинный текст / локализация: список скроллится; имена
```

### 2.4. UI-SCR-ROOM — Комната

```text
UI-ID / название / назначение: UI-SCR-ROOM / Комната / ожидание соперника
(или бота), выбор героя, готовность, старт хостом, отсчёт до партии.
Как попасть / как выйти: из LOBBY (create/join) / «Выйти из комнаты»
  (mutation LeaveGame) → LOBBY; при старте — GAME.
Основной сценарий: хост создаёт комнату, видит свой слот и код A4KD9Q,
  выбирает Медузу, видит её характеристики; соперник входит по коду, выбирает

Макет (схема §3.2): шапка — код комнаты крупно + кнопка «Копировать код»,
  режим, доска; слева — два слота игроков (карточка: аватар/имя/роль
  хост-соперник, выбранный герой с HP/движение/помощники, индикатор готова);

  «Выбрать»/«Выбрано»; под ней — «Просмотр колоды» (открывает UI-SCR-INSPECT в

  (только хост) и общий статус («Ждём соперника…» / «Все готовы!»).
Контент и источник: состояние комнаты — RoomInfo-подобный query/poll и
  подписки PlayerJoined/PlayerLeft (payload лобби-фазы — ФАКТ docs/backend-api/
  03, 04: в игровой фазе playerJoined/playerLeft НЕ публикуются); герои —

Пустое состояние: слот соперника «Ждём соперника… код A4KD9Q» (мигающий
  акцент на коде); в VS_AI слот сразу «ИИ-соперник» (бот добавляется сервером
  автоматически — ФАКТ 03/04).
Загрузка / ожидание: загрузка деталей героя — скелетон в карточке; старт —
  полноэкранный отсчёт 3-2-1 (по 1 с) поверх затемнения; в вебе отсчёт 3 с
  перед startGame — ФАКТ facts-web-ux; ПРЕДЛОЖЕНИЕ: отсчёт локальный у хоста,
  гость видит «Партия начинается…» по факту статуса IN_PROGRESS (синхронный
  отсчёт обоих клиентов без серверного события невозможен — не выдумывать).
Недоступность и её причина (P2): «Начать партию» — «Вы не хост» (у гостя

  героя» (если selectHero обязателен перед ready — ВОПРОС (новый) №4, §11);

Ошибка / повтор / нет сети: мутации комнаты — тост с причиной («Вы уже
  готовы», throttle) + «Повторить» где применимо; обрыв связи в комнате —
  оверлей UI-SCR-RECONNECT (комната ещё не живое состояние — достаточно
  повторного RoomInfo); «Игра не найдена» (хост удалил комнату) — тост + в

Фокус и Escape: фокус — на карточках героев; Esc — подтверждение выхода.
Изменение размера / длинный текст / локализация: карточки героев — сетка

  «Король Артур/King Arthur»); русские длинные строки — по §7.5.
Звуки и переходы: игрок присоединился/покинул (два разных коротких сигнала),

Критерии приёмки: (1) два клиента видят одинаковую комнату: код, слоты,

  полной готовности; (3) VS_AI: комната сразу с ботом, старт после своей

```

```text
автоматическое переподключение с восстановлением состояния партии без
повторного расхода карт (MVP-требование файла 00).
Как попасть / как выйти: автоматически при обрыве WS/сети в GAME (и ROOM) /
  автоматически при успехе; вручную — «Переподключить»; «Выйти в лобби» —
  с подтверждением.
Основной сценарий (протокол — ФАКТ docs/backend-api/11): обрыв → оверлей с
  авто-попытками (ПРЕДЛОЖЕНИЕ: 5 попыток с задержкой 1 с — веб-референс,
  ФАКТ facts-web-ux) → при успехе: берём последний применённый sequenceNumber
  (lastSeq) → query GetGameSequence → если журнал жив: EventsSince пачками
  (по 100, hasMore) → свежий GetGameState → перевзятие подписки
  GameStateUpdated с since=lastSeq → оверлей закрывается, партия актуальна.
  Если журнал вычищен (30 дней — ФАКТ 11) — сразу полный GetGameState.
Макет (схема §3.5): полноэкранное затемнение 80% поверх замороженного
  последнего кадра HUD; по центру карточка: крупная иконка связи (семейство
  UI-ICON-RESOURCE — не эмодзи), заголовок, статус («Переподключение…
  попытка 2 из 5»), предупреждение «Партия продолжается на сервере.
  Не закрывайте приложение», кнопки: «Переподключить» (после исчерпания
  автопопыток), «Выйти в лобби» (с подтверждением: выход прерывает партию —
  ФАКТ 03).
Контент и источник: GetGameSequence/EventsSince/GetGameState +
  повторная подписка (все — ФАКТ 04/11); количество пропущенных событий —
  разница sequenceNumber; показываем «Пропущено событий: N» (ПРЕДЛОЖЕНИЕ —
  честность вместо фантомного «всё как было»).
Действия и клавиши: Esc заблокирован (нельзя отменить восстановление);
  Enter = «Переподключить»;Tab между кнопками.
Пустое состояние: нет.
Загрузка / ожидание: сам оверлей — состояние ожидания; таймаут попытки —
  10 с, дальше следующая (ПРЕДЛОЖЕНИЕ).
Недоступность и её причина: ввод в партию заблокирован целиком (олд-план
  «Input.Mode.Busy» — идея прежнего плана 05, §3.4); причина указана в
  заголовке оверлея.
Ошибка / повтор / нет сети: 5 неудачных авто-попыток → режим ручного
  «Переподключить» без ограничения числа повторов (ПРЕДЛОЖЕНИЕ); специальный
  случай WS 4403 (токен отклонён) — сначала тихо RefreshTokens (ротация:
  храним оба — ФАКТ 02), пересоздаём WS, и только при неудаче — выход в
  LOGIN с сообщением «Сессия истекла, войдите снова» (ФАКТ 06: 4403 →
  refresh+reconnect); 4408/4409 — логируем, ретраим как обычный обрыв (ФАКТ
  docs/backend-api/06).
Фокус и Escape: фокус на «Переподключить»; Esc глотается.
Изменение размера / длинный текст / локализация: центральная карточка
  инвариантна; строки статуса короткие RU/EN.
Звуки и переходы: один сигнал потери связи, один сигнал восстановления
  (обязательны: игрок мог отойти — ФАКТ-следствие таймера защиты 30 с);
  закрытие — 200 мс.
Критерии приёмки: (1) QA-006 (бриф §15): отключение после отправки действия
  и возврат не расходуют карту повторно; (2) восстановление показывает
  состояние не старше последнего sequenceNumber, дубликат не применяется
  (QA-007 по духу); (3) при севшей сессии игрок попадает в LOGIN, а не в
  тупик; (4) «Пропущено событий: N» совпадает с разницей seq; (5) во время
  оверлея ни один клик не доходит до поля.
Особый случай — партия закончилась без нас: при восстановлении фаза
GAME_OVER/событие GameEnded → вместо возврата в HUD показываем UI-SCR-GAMEOVER
с результатом (в т.ч. поражение по таймауту защиты, если оно применимо —
см. противоречие №1 в §10).
```

### 4.2. Своя рука, увеличенная карта, выделение, подтверждение розыгрыша (UI-HUD-HAND)

- Источник: `handZones[me].cards` — HandCard[] (поля: id, cardId, name/nameEn/nameRu, cardType, attackValue/defenseValue/boostValue, effects, text, bannerName, isVisible — ФАКТ 04). Порядок — серверный; ПРЕДЛОЖЕНИЕ: перетаскивание внутри руки локально (чисто визуальная сортировка, не отправляется).
- Карта в руке: 200×280 px (масштаб с UI); hover — увеличение до ~120% + подъём на 24 px, 150 мс (веб-референс: выбор 1.08× — ФАКТ facts-web-ux; UE-вариант больше, т.к. базовый размер крупнее); выделенная — рамка-подсветка (UI-CARD-FRAME, состояние selected) + постоянное «поднятие».
- Увеличенная карта: при hover показывается увеличенная копия (300×420) над рукой, не перекрывая поле по центру (позиция — над картой-источником). Требование P1: увеличенная карта не должна закрывать подсвеченные клетки/цели, если игрок держит hover во время выбора цели — см. §5, правило UI-INP-001.
- Подтверждение розыгрыша: без drag-and-drop (D-05 мышь+клавиатура; ПРЕДЛОЖЕНИЕ: drag-and-drop после MVP). Схема — §5: одиночный клик = выбрать, двойной клик/клик по цели = разыграть.
- Типы карт в руке: ATTACK/DEFENSE/SCHEME/VERSATILE (по данным каталога — ФАКТ 05). НЮАНС: в `handZones` в примере доков встречается также cardType `UNIVERSAL` (04) — противоречие имён с `VERSATILE` (05); UI отображает оба как «универсальная» (двойная рамка), финальное решение — файл 08. Противоречие №5, §10.
- Неиграбельные карты: приглушены, причина — тултип («нет действий», «не ваш ход», «карта защиты — ждите атаки», «баннер не совпадает» — bannerName). Основание: P2; перечень причин-ключей локализации фиксируем здесь: `why.not.your.turn`, `why.no.actions`, `why.defense.only.in.combat`, `why.banner.mismatch`, `why.syncing`, `why.wait.defender`, `why.immobilized`, `why.not.in.range` (ПРЕДЛОЖЕНИЕ; отображение — RU/EN).

### 4.3. Панели игроков (UI-HUD-PANEL-*)

Содержимое панели (сверху вниз): портрет героя + имя игрока; герой: HP-бар (текущий/макс) + число; помощники: компактные плашки с HP (Медуза: 3×Гарпия по 1 HP; Артур: Мерлин 7 HP — ФАКТ facts-content); счётчики: рука N, колода N, сброс N; статус: «ваш ход» (акцент) / «ходит соперник»; в COMBAT — роль (атакующий/защитник).
- Источники: HP и живость — `players`/`fighters` (JSON-строки снапшота, ФАКТ 04); счётчик руки соперника — длина `handZones[opp].cards` (рубашки, содержимое скрыто — ФАКТ 04); счётчики колод/сбросов — только из полного состояния (`decks`, `discardPiles` в подписку не входят — ФАКТ 04): ПРЕДЛОЖЕНИЕ — обновлять при собственных мутациях (HTTP-ответ содержит полное состояние — ФАКТ 04) и при полном resync, между событиями соперника помечать счётчики как «≈» (честный индикатор устаревания; идея bDecksStale прежнего плана 05 §3.3).
- HP-бар: заполнение + число; изменение HP — плавная анимация ≤ 400 мс + всплывающее «−N» над фигуркой (веб-референс showDamage — ФАКТ facts-web-ux); смерть помощника — затемнение плашки + слот «погиб» (не исчезает: история видима — ПРЕДЛОЖЕНИЕ).
- Скрытая информация: никаких значений чужих карт; только количество (QA-005).

### 4.4. Поле, подсветки выбора, доступных клеток и целей (UI-HUD-BOARD)

- Геометрия: `boardState.cells` живой партии — единственная истина (ФАКТ файла 00, п. 8: код 6×4 ≠ API 5×6; блокирует финальные ассеты доски — GAP, файл 08). UI обязан строить сетку из boardState, не из константы.
- Подсветки (все — локальные ПОДСКАЗКИ, не истина — P4; сервер отклонил — тост + сброс):
  - выбранная фигурка: кольцо-выделение подставки + мягкий луч света (D-02);
  - достижимые клетки (манёвр/перемещение): контур + заливка 20% + ГЛИФ «шаг» (иконка UI-ICON-ACTION «манёвр») в центре клетки — не только цвет (P1, QA-011);
  - цели атаки: рамка-прицел на вражеской фигурке + ГЛИФ «меч»;
  - клетки для PLACE-эффекта: пунктирный контур + ГЛИФ «метка»;
  - препятствия/занятые клетки: отдельное обозначение (крест-штрих), клик даёт причину «занято» (P2).
- Зоны клеток: 12 зон (ФАКТ 05: «12 зон-цветов»); каждая зона = цвет + уникальный ГЛИФ/БУКВА + тип штриховки краёв клетки (семейство UI-ICON-ZONE, §8.5); легенда зон — раскрывающаяся плашка у нижнего края поля (все 12 не нужны одновременно; ПРЕДЛОЖЕНИЕ: показывать только зоны, присутствующие на текущей доске).
- НЮАНС веб-референса: в реальной веб-игре подсветка доступных клеток всегда пустая (не реализована — ФАКТ facts-web-ux) — UE обязан реализовать (требование файла 00: «подсветки» в списке цифровых улучшений); расчёт достижимости — клиентский, как подсказка; финальная ответственность деления «клиент считает подсказку / сервер проверяет» — файл `01-gameplay-experience.md` (не дублировать).
- Зум колесом (D-10): плавный, 150–250 мс на шаг; пределы зума фиксируются в `03-art-direction.md` (камера — там); при зуме попадание кликов по клеткам сохраняется.
- Числа/подписи на поле: HP-мини-бары над фигурками (референс веба — ФАКТ facts-web-ux), имена фигурок при hover.

### 4.5. Панель атаки/защиты с таймером (UI-HUD-COMBAT)

Активируется при `phase: COMBAT` / `COMBAT_RESOLVE` (ФАКТ 04 — фазы; продакшен-поток: TURN_START пропускается, SETUP/TURN_END legacy — ФАКТ facts-backend).

Для ЗАЩИТНИКА (меня атакуют):
- Заголовок: «Вас атакуют: <фигурка> → <моя фигурка>, значение атаки N» (из `metadata.combatInfo`: attackerId, targetFighterId, attackValue — ФАКТ 04).
- Таймер: кольцо/полоса 30 с от серверного дедлайна `metadata.combatInfo.timeoutAt` (ФАКТ 04: DEFAULT_DEFENSE_TIMEOUT, дедлайн в timeoutAt). Поведение: показ секунд, изменение цвета+пульса последние 10 с (не только цвет — цифры крупно), звук-тихий тик последние 5 с. При 0 — не блокируем экран: сервер сам выполнит auto-resolve (ФАКТ 04); UI остаётся в состоянии «ждём резолв».
  - ПРОТИВОРЕЧИЕ (обязательно к фиксации в 08): прежний план `docs/unreal/05-ui-screens.md` (§3.2/§3.5, со ссылкой на ADR §1.3 п.5) утверждает, что `timeoutAt` НЕ доставляется, и предписывает считать дедлайн локально: `StartedAt + DefenseTimeoutSec×1000`. Актуальные доки сервера (`docs/backend-api/04`, строки 225/233/406/531) `timeoutAt` СОДЕРЖАТ. Решение этой спецификации (ПРЕДЛОЖЕНИЕ): источником дедлайна считать `timeoutAt`, локальный расчёт `startedAt+30 с` оставить fallback'ом на случай отсутствия поля; финальное решение и сверка с живым сервером — `08-integration-decisions.md`.
- Действия: (а) клик по карте DEFENSE/VERSATILE в руке → выбор буста (если допустим — вторая мини-панель выбора буст-карты: «Усилить: [карта1] [карта2] [без буста]») → PlayDefense(cardId, boostCardId?) — ФАКТ 04: не тратит действие, отменяет таймер; (б) «Без защиты» → ResolveCombat (аналог кнопки веба — ФАКТ facts-web-ux).
- Нюанс фаз: защитник играет карту в `COMBAT`; в `COMBAT_RESOLVE` — только ожидание/резолв (10 с DEFAULT_RESOLVE_TIMEOUT — ФАКТ facts-backend).

Для АТАКУЮЩЕГО:
- «Ждём карту защитника… N c» (тот же таймер timeoutAt); в `COMBAT_RESOLVE` — кнопка «Разрешить бой» (ResolveCombat); ОГОВОРКА VS_AI (GAP-010 файла 08, из 01 §3 п.3): в первые секунды окна защиты бота кнопка скрыта/недоступна — преждевременный resolveCombat отнимает у бота окно защиты (серверного гейта нет); ПОДВОДНЫЙ КАМЕНЬ сервера: auto-resolve при таймауте защиты НЕ применяет урон (TODO на сервере — ФАКТ файла 00, п. 3; обход/задача — GAP в 08). UI не должен показывать «бой разрешён» с нулевым уроном как норму: если auto-resolve прошёл без применения урона, показываем баннер «Сервер разрешил бой автоматически (без урона — известное ограничение)» — ПРЕДЛОЖЕНИЕ до решения GAP.
- Результат: разница значений, «−N» над целью, карты атаки/защиты показываются крупно по центру 1.2 с (P3: пропускаемо кликом), затем уходят в сброс.
- Показ карты атаки соперника: ПОСЛЕ резолва — из `discardPiles` полного состояния (фильтрация скрывает только руку и topCard колоды — ФАКТ 04); до резолва — только значение из combatInfo. Не восстанавливать карту по attackerCardId из каталога (правило скрытой информации; ПРЕДЛОЖЕНИЕ; проверка полноты — QA-005 по духу).

### 4.6. Очередь отложенных выборов (UI-HUD-PENDING)

- Источник: `metadata.pendingEffects[]` — {id, type, playerId, value, text} (ФАКТ 04); показываем только свои (playerId == me).
- Типы баннеров:
  - CHOOSE_ONE: заголовок-текст эффекта + кнопки вариантов (optionIndex → ResolvePendingEffect(effectId, optionIndex)) — веб-референс «кнопки вариантов» ФАКТ facts-web-ux;
  - MOVE: «Кликните бойца, затем клетку (до N шагов)» → выбор бойца → клетки → ResolvePendingEffect(effectId, fighterId, path-подобный выбор приводится к x,y — контракт 04: fighterId?, x?, y?);
  - PLACE: «Кликните клетку для размещения» → ResolvePendingEffect(effectId, x, y); зонные ограничения PLACE на сервере TODO (ФАКТ-ограничение 10 — файл 08).
- Очередь: эффектов может быть несколько — показ по одному + индикатор «в очереди: k» (референс: веб-баннер один, очередь — ПРЕДЛОЖЕНИЕ по духу прежнего плана FUmPendingView.QueueCount).
- Взаимная блокировка с боем: ПРЕДЛОЖЕНИЕ (правило прежнего плана, «G19»): во время COMBAT/COMBAT_RESOLVE отложенные выборы неактивны, баннер показывает «выполните после боя»; обоснование — серверные фазы взаимоисключающие, входящая мутация в COMBAT всё равно будет отклонена.
- Подсказка контекста: при активном MOVE/PLACE поле подсвечивает допустимых бойцов/клетки тем же механизмом §4.4, но глифом «метка эффекта» (отличимым от манёвра — не только цветом).

### 4.7. Колода, сброс, журнал (UI-HUD-DECKS, UI-HUD-LOG)

- Колода (своя): рубашка + счётчик; клик — «колода: N карт» (просмотр contents запрещён — скрытая информация; topCard свой доступен в полном состоянии — ФАКТ 04; ПРЕДЛОЖЕНИЕ: не показывать вообще в MVP, чтобы не плодить состояния).
- Сброс (своя): верхняя карта видна; ПКМ — инспектор; клик — раскрывается стопка в строку мини-рубашек-лиц (ПРЕДЛОЖЕНИЕ; данные — discardPiles из GetGameState, в подписке их нет — ФАКТ 04, см. §4.3 «≈»).
- Сброс соперника: только счётчик и верхняя карта, если она видима в полном состоянии (те же источники; доступность чужого сброса следует из описания фильтра — ФАКТ 04; пометить на проверку в 08 — противоречие №7, §10).
- Журнал: последние ~50 событий, каждое — локализованная строка по типу события (MANEUVER, ATTACK_INITIATED, DEFENSE_PLAYED, COMBAT_RESOLVED, CARD_PLAYED, TURN_ENDED, PASSED, FIGHTER_MOVED, DOOR_TOGGLED, SPECIAL_ABILITY — «шпаргалка мутация → событие», ФАКТ 04) + кто/над кем; источник — собственные мутации (HTTP-ответы) и `eventsSince` при восстановлении (ФАКТ 04/11); авто-скролл вниз, пауза автоскролла при ручном скролле.

### 4.8. Состояние связи, блокировка ввода, дедупликация (UI-HUD-CONN + глобально)

- Индикатор связи: ● зелёный (подписка жива, seq непрерывен) / ◐ жёлтый (in-flight мутация или догоняем gap) / ● красный (нет связи; тогда открыт UI-SCR-RECONNECT) — ПРЕДЛОЖЕНИЕ; референс веба (🟢/🟡) — ФАКТ facts-web-ux.
- Одна мутация за раз (ПРЕДЛОЖЕНИЕ; обоснование — P4 + серверный distributed lock TTL 10 с на мутацию, ФАКТ 11): пока мутация in-flight, ВСЕ игровые кнопки/клетки/карты неактивны с причиной «Отправка действия…»; ввод накапливать нельзя. Двойной клик по «Разыграть» не отправляет вторую мутацию (QA-003, бриф §15).
- Дедупликация: HTTP-ответ мутации и подписка несут одно и то же состояние (ФАКТ 04) — применяем по `sequenceNumber` ровно один раз: `seq <= last` — отброс; `seq == last+1` — применить; `seq > last+1` — gap → `eventsSince(gameId, lastSeq)` пачками по 100 и/или полный `gameState` (ФАКТ 04/06). UI-следствие: анимации урона/перемещения проигрываются по ПЕРВОМУ применению номера, не повторно (QA-007).
- Обновление состояния во время выбора игроком цели/клетки: см. §6 (кратко: выбор валидируется против нового снапшота; стал недопустимым — сброс с коротким тостом причины, не молча).
- Rate limits (ФАКТ 04): 30/мин (maneuver/moveFighter/endTurn/toggleDoor/setStance/resolvePendingEffect), 20/мин (attack/playDefense/resolveCombat/playScheme/pass). UI-защита (ПРЕДЛОЖЕНИЕ): локальный «мягкий» троттлинг не вводим (замедлит игру), но при ошибке rate limit показываем тост «Слишком часто — подождите пару секунд» и НЕ ретраим автоматически.
- Ошибки мутаций: баннер в верхней части HUD: причина (перевод кода ошибки сервера; словарь кодов — файл 08, там же GTM-таблица код→строка) + сброс выбора до «ничего не выбрано» + подсветка того, что изменилось (быстрая ориентировка после отказа — P2).

### 4.9. Специфика VS_AI (D-12)

- Ходы бота приходят ТОЛЬКО по подписке после моей мутации, асинхронно (ФАКТ 04:533): после моего endTurn/последнего действия HUD показывает индикатор «Соперник (ИИ) думает…» — пульсирующая плашка у панели соперника.
- НИКАКОГО локального таймера ожидания бота: серверного таймера на ход нет (ФАКТ facts-backend), боту «думать» можно сколько угодно; индикатор бесконечен до события. Если бот «завис» > 30 с (эвристика — ПРЕДЛОЖЕНИЕ), показываем подсказку «Похоже, соединение потеряно» → проверка связи (пинг-запрос) → UI-SCR-RECONNECT при необходимости; не выдаём эвристику за истину.
- Атака бота: тот же контракт ATTACK_INITIATED + COMBAT-фаза с timeoutAt — панель боя не отличает бота от человека (кроме имени и портрета «ИИ»).
- Комната VS_AI: слот соперника сразу занят ботом (ФАКТ 03 — бот добавляется автоматически при старте; показываем сразу — ПРЕДЛОЖЕНИЕ, чтобы комната не выглядела «пустой»).

## 6. Таблица состояний ввода

Легенда состояний: **S0** ничего не выбрано → **S1** боец выбран → **S2** карта выбрана → **S3** цель выбрана (клетка/фигурка/вариант) → **S4** подтверждение (превью действия, кнопка активна; включает выбор буста) → **S5** запрос выполняется (in-flight; ввод заблокирован) → **S6** подтверждено (переход к S0 по новому снапшоту) / **S6E** ошибка (баннер, сброс к S0).

Правило для входящих обновлений (действует на всех стрелках вне S5): новый снапшот с большим `sequenceNumber` (P4):
(a) выбранные сущности живы/валидны → выбор СОХРАНЯЕТСЯ, подсветки пересчитываются;
(b) выбор стал невалиден (карта ушла, боец погиб, цель недопустима) → тихий сброс в S0 + тост причины («Ход передан», «Цель недоступна» и т.п. — по факту);
(c)incoming в S5 — см. строку S5.

| Переход | Событие | Отмена возможна? | Реакция на входящее обновление состояния |
|---|---|---|---|
| S0→S1 | ЛКМ по своей фигурке | Да (Esc/ПКМ/клик в пустоту) | (a) боец жив → сохранить, пересчитать клетки; (b) погиб → сброс + тост «Боец недоступен» |
| S0→S2 | ЛКМ по карте руки (если играбельна; иначе тултип-причина) | Да | Карта ещё в руке? да → сохранить; ушла (напр. вынужденный сброс) → сброс + тост |
| S1→S0 | Esc/ПКМ/клик в пустоту | — | — |
| S1→S1' | Клик по другой своей фигурке (перевыбор) | Да | Как S0→S1 |
| S1→S3(клетка) | В режиме «Манёвр»: клик по подсвеченной клетке ДОБАВЛЯЕТ сегмент пути выбранного бойца (перестроение пути = повторные клики); отправка — только по «Подтвердить» (S4→S5, maneuver, INT-009) | Да (до «Подтвердить» — весь манёвр отменяем) | Снапшот между кликами: клетка стала занятой → подсветка пересчитывается, путь обрезается до достижимого |

| S6/S6E→S0 | Автопереход после применения снапшота / закрытия баннера ошибки | — | — |

Особые строки:
- COMBAT (я защитник): S2 ограничен DEFENSE/VERSATILE; S3 отсутствует; S4 = выбор буста; «Без защиты» — прямой переход S0→S5 (ResolveCombat) с мини-подтверждением (ПРЕДЛОЖЕНИЕ: одна кнопка без подтверждения, чтобы уложиться в 30 с).
- Pending-эффекты: CHOOSE_ONE — S2(вариант)→S4(кнопка «Подтвердить» — ПРЕДЛОЖЕНИЕ, защита от случайного варианта); MOVE/PLACE — цепочка как S1→S3, подтверждение кликом по финальной клетке.
- В VS_AI после S6 при передаче хода боту — блок-состояние «ИИ думает» (ввод в поле разрешён только для read-only: hover/инспектор; §4.9).

### 7.2. Требования доступности ввода

- Всё интерактивное достижимо мышью; критические действия — дублированы клавишами (§5 UI-INP-009).

### 7.3. Контраст и палитра

Тёмная тема — базовая и единственная MVP (D-02: мрачноватая атмосферная диорама; «светлый фон» для семейств ассетов не заказываем — §8). Пороги: текст ≥ 4.5:1, крупный текст/иконки ≥ 3:1 (ПРЕДЛОЖЕНИЕ по WCAG-духу без ссылки на сертификацию).

### 7.4. Не только цвет (P1/QA-011)

Три обязательных класса различий: (1) зоны поля — цвет+глиф+буква (UI-ICON-ZONE); (2) типы подсветки поля — разные ГЛИФЫ (шаг/меч/метка) + разные формы контура (сплошной/прицел/пунктир); (3) состояния кнопок — яркость + рамка + иконка состояния. Проверка — QA-010, QA-011 (бриф §15).

### 7.5. Проверка реальными длинными русскими строками (D-08, QA-011)

ФАКТ данных (из `scraped-data/api/heroes/medusa.json`, выжимка facts-content):

## 10. Противоречия в источниках, затрагивающие этот файл (сводка; разбор — 08)

1. **Дедлайн защиты**: прежний план `05-ui-screens.md` (со ссылкой на ADR §1.3 п.5): `timeoutAt` не доставляется, считать локально `startedAt+30 с`; актуальные `docs/backend-api/04` (225/233/406/531): `metadata.combatInfo.timeoutAt` доставляется. Решение этого файла (ПРЕДЛОЖЕНИЕ): primary — `timeoutAt`, fallback — локальный расчёт; финал — `08-integration-decisions.md`.
2. **Геометрия Cobble City**: код 6×4=24 против API 5×6=30 (ФАКТ facts-content). Влияет на UI-ICON-ZONE (какие зоны реально на доске) и на легенду зон; блокирует финализацию. Истина — `boardState` живой партии.
3. **Возврат в живую партию после перезапуска**: в вебе есть MyGames (ФАКТ facts-web-ux), в `docs/backend-api/03` операция «мои игры» не описана явно. Влияет на сценарий BOOT (§1.3). Нужна сверка — ВОПРОС (новый) №1.
4. **Обязательность выбора героя до готовности**: старт требует только isReady (ФАКТ 03); может ли игрок быть ready без героя — не зафиксировано. Влияет на кнопку «Начать» (§2.4). ВОПРОС (новый) №2.
5. **cardType UNIVERSAL vs VERSATILE**: в `handZones` примера 04 встречается `UNIVERSAL`, в контенте 05 — `VERSATILE`. Влияет на UI-CARD-FRAME (четыре типа + запасной пятый). Решение — 08.
6. **maxSize руки**: прежний план — 7; пример 04 — 10. UI не хардкодит, берёт из `handZones[me].maxSize`.
7. **Видимость чужого сброса**: из описания фильтра 04 следует, что скрываются только рука и topCard колоды (сброс виден), но явно это не подтверждено. Влияет на §4.7 (просмотр сброса соперника). Пометка «требует проверки».
8. **cardId в мутациях = инстансный id карты**: пример 04 (`HandCard.id:"card-42"` ↔ `attack.cardId:"card-42"`, контентный `cardId:"c-42"` — отдельное поле) говорит, что мутации принимают ИНСТАНСНЫЙ id; имя поля при этом «cardId» — ловушка. Влияет на UI-INP-007 (две копии карты). Сверка — 08.
9. **movement героя = 3 захардкожен** в публичном запросе (ФАКТ 05:396) против фактических данных (Артур — 2; ФАКТ брифа/facts-content). Экран ROOM не должен показывать «движение» из каталога без сверки с фактом; ПРЕДЛОЖЕНИЕ: в ROOM движение показывать с пометкой из данных каталога, в партии использовать только состояние партии.
10. **Старый план §05 Register-экран** против отключённой регистрации (Q-005): экран регистрации исключён из MVP-карты (§1.2), в отличие от прежнего плана.
