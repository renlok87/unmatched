# R4. Технические паттерны подбора хода (repo + web)

> Срез 2026-10-03. Роль: исследователь технических паттернов. Тема — «подбор хода»: как игрок выбирает бойца, видит достижимые пространства, строит и смотрит путь, выбирает буст, подтверждает или отменяет ход, как фигурка движется и как ход видит соперник. Доски двух видов: сетка (Cobble City) и граф пространств оригинальных карт (Marmoreal, Sarpedon). Второстепенно — подсказки ходов и выбор хода ботом.
>
> Документ только исследовательский: код, конфиги и другие документы не менялись. Факты репозитория даны как `path:line` (ветка `fix/admin-panel`, HEAD `fe12eb7c`). Веб-факты даны как URL с датой обращения 2026-10-03. Всё, что не удалось проверить, помечено «не проверено». Оценки, которые не измерялись, помечены «оценка».

## 0. Короткий вывод

1. **Алгоритм достижимости уже правильный и одинаковый по смыслу на клиенте и сервере.** Шаг стоит 1, поэтому нужен BFS по слоям; A* и кэш путей для превью не нужны. Не хватает трёх вещей: последовательной симуляции нескольких ходов одного манёвра на клиенте, канонического tie-break пути и общих golden-фикстур паритета.
2. **Найдены пять расхождений клиента и сервера.** Одно из них, вероятно, ломает команду: ход «остаться на месте» уходит на сервер с пустым путём, а сервер отвечает `EMPTY_PATH` (§2.3, F1). Остальные: клиент отказывает в части законных ходов (F2), не учитывает `immobilized` (F3), считает movement иначе, чем сервер (F4), и держит два пути ввода манёвра (F5).
3. **Соперник не видит путь хода, только откуда и куда.** Снапшот не несёт пути, а журнал `eventsSince` показывает входные данные только автору. CUE-007 при этом нормативно требует путь. Рекомендация: добавить в состояние публичное поле `metadata.lastManeuver` с путями и порядком ходов. По §8 сетевого контракта это обратно совместимое добавление. Резервный вариант — канонический путь, который клиент пересчитывает сам.
4. **Оптимистичного применения манёвра не делать.** Превью (подсветка, линия пути, призрак фигурки) остаётся локальным черновиком. Фигурка сдвигается только по авторитетному снапшоту. Это совпадает с уже принятыми правилами GD-037/ACC-012 и с двухфазным протоколом `beginManeuver` → `maneuver`.
5. **Подсветку в UE перевести с «актор на клетку» на один ISM с per-instance custom data.** Линия пути: пул `USplineMeshComponent` вдоль `USplineComponent`. Призрак: та же фигурка с dithered-fade через Custom Primitive Data (индекс `Fade` уже зарезервирован в контракте cue). Niagara — только для акцентов. Ввод: Enhanced Input с отдельным контекстом черновика манёвра.
6. **Анимация перемещения — скольжение по пути (решение D-11).** Опционально маленький «подскок» на каждом шаге и доворот корпуса. Общая длительность ограничена. При reduced motion фигурка сразу ставится в конечную точку (`snap`). Скелетный walk-цикл и root motion для этой игры избыточны.
7. **Подсказки ходов собрать в чистую серверную функцию оценки** (поле дистанций + угроза + достижимость атаки + зоны). Её используют и `ai-decision.service`, и опциональный запрос подсказок. Подсказка учитывает только публичную информацию и никогда не подтверждает ход сама.

### 1.2. Протокол манёвра — сервер

- `beginManeuver(gameId, expectedSequenceNumber)` списывает действие, добирает 1 карту и открывает `metadata.pendingManeuver = { id: "maneuver:<turn>:<seq>", playerId }`. Если `expectedSequenceNumber` не совпадает с текущим seq, запрос отклоняется (`backend/src/game-engine/services/game-action-executor.service.ts:1645-1667`, проверка seq — `:1656`).
- `maneuver(gameId, maneuverId, moves[], boostCardId?)` (`backend/src/games/dto/gameplay.dto.ts:112-160`):
  - Принимается, только если `pendingManeuver.id === maneuverId` (`game-action-executor.service.ts:1708-1711`). После успеха `pendingManeuver` очищается (`:1811`), поэтому повтор той же команды получает ошибку и не применяется второй раз. Это фактическая идемпотентность по `maneuverId`.
  - Каждый боец — не больше одного раза за манёвр (`:1731-1735`).
  - **Ходы применяются последовательно.** Каждый следующий проверяется на состоянии после предыдущего (`:1739-1777`).
  - Буст даёт +boostValue **каждому** бойцу (`game-rules.validator.ts:318-344`; комментарий DTO — `gameplay.dto.ts:131-133`).
  - Весь манёвр даёт **один** +1 к seq (`:1782-1785`).
  - Реакции на движение (`applyMoveReactions`) видят только «откуда и куда», путь им не передаётся (`:469-497`).
  - `moves: []` — законное завершение: все бойцы остаются на месте (`backend/src/games/resolvers/game-actions.resolver.ts:289`).
- `validateManeuver` (`backend/src/game-engine/validators/game-rules.validator.ts:277-390`):
  - отклоняет бойца с эффектом `immobilized` (`:298-305`);
  - отклоняет **пустой path** (`EMPTY_PATH`, `:333-335`);
  - отклоняет путь длиннее allowance (`:344-351`);
  - требует, чтобы каждый шаг шёл на соседнюю клетку (`:356-367`);
  - проверяет блокировку врагом и свободу конечной клетки (`:372-391`).

  Путь передаётся **без** стартовой клетки. Валидатор допускает петли: A→B→A проходит, если B проходим, а конечная клетка совпадает со стартом.
- Координаты в GraphQL ограничены диапазоном 0..19 (`gameplay.dto.ts:63-76`).
- `PathfindingCacheService` подключён в DI, но не используется: `pathCache` внедрён в `MovementService` и нигде не вызывается (`backend/src/game-engine/engine/movement.service.ts:31-34`; других вызовов нет — проверено grep). Ключ кэша не учитывает позиции бойцов (`backend/src/game-engine/movement/path-cache.service.ts:191-193`). Если этот кэш когда-нибудь включить, при TTL 5 с он вернёт устаревшую достижимость. Для превью его использовать нельзя.

## 3. Тема 1. Достижимость и путь

### 3.1. Какой алгоритм

- Цена каждого шага сейчас 1, на обоих видах досок (`adjacency.service.ts:77`, `cost: 1`). Поэтому **BFS по слоям** даёт точные минимальные числа шагов. Red Blob Games описывает дальность движения на hex-сетке как такой послойный BFS: каждая итерация расширяет слой k-1 до слоя k ([Hexagonal Grids, раздел Movement Range](https://www.redblobgames.com/grids/hexagons/), 2026-10-03). Граф пространств — тот же граф, только с другой функцией соседей ([Grids and Graphs](https://www.redblobgames.com/pathfinding/grids/graphs.html), 2026-10-03).
- Dijkstra нужен, только если появится разная цена шага: например, «вход в зону X стоит 2» или карты, меняющие цену. Тогда меняется только очередь. Red Blob пишет, что при разных ценах простую очередь заменяют приоритетной ([Introduction to A*](https://www.redblobgames.com/pathfinding/a-star/introduction.html), 2026-10-03).
- A* нужен для одной цели на большом графе. Для превью нужны **все** достижимые клетки сразу, так что A* бесполезен. Доски крошечные: Marmoreal — 31 пространство и 42 ребра, Sarpedon — 38 пространств и 61 ребро (подсчитано по `backend/prisma/fixtures/boards/{marmoreal,sarpedon}.topology.json`), сетка — до 20×20 (`gameplay.dto.ts:63-76`). Один BFS на таком графе стоит микросекунды (оценка). Кэш между кадрами не нужен: результат можно пересчитывать при каждом изменении черновика.
- **Один BFS даёт и подсветку, и путь.** Если хранить `dist[]` и `parent[]` (Red Blob называет это `came_from` — «хлебные крошки», [Introduction to A*](https://www.redblobgames.com/pathfinding/a-star/introduction.html)), то путь к клетке под курсором восстанавливается за O(длина пути) без нового поиска. Сейчас `BuildManeuverPath` при каждом вызове заново делает BFS (`S08BoardModel.cpp:385-407`). При наведении это лишняя работа, но небольшая.
- Текущий клиентский обход использует LIFO-стек с релаксацией (`Frontier.Pop`, `S08BoardModel.cpp:345-365`). Это label-correcting поиск: он корректен, но может обрабатывать узлы повторно. Для детерминизма и простоты паритета лучше FIFO-очередь, как на сервере (`movement.service.ts:121-150`, `board-topology.ts:224-236`). Результат `dist[]` от этого не меняется, меняется только `parent[]`.

### 3.2. Правила, которые BFS обязан применять (сводка для одного шага)

| Ситуация | Войти как промежуточная | Закончить ход | Источник |
|---|---|---|---|
| Пустая проходимая клетка | да | да | `traversal.ts:28-31` |
| Стена / препятствие / закрытая дверь / дыра | нет | нет | `traversal.ts:28-31` |
| Живой союзник | да | **нет** | `traversal.ts:47-69` |
| Живой враг | **нет** | нет | `traversal.ts:47-69` |
| Побеждённый боец | как пустая | как пустая | `traversal.ts:19-21` |
| Своя стартовая клетка | — | да (ход нулевой длины). На сервере это выражается **отсутствием** хода в `moves[]` (F1) | `resolvers/game-actions.resolver.ts:289` |
| Топология: соседняя по решётке клетка без `links` | нет (не сосед) | нет | `board-topology.ts:5-10` |
| Боец с `immobilized` | ход запрещён целиком | — | `game-rules.validator.ts:298-305` |

### 3.3. Несколько бойцов в одном манёвре

Правило Unmatched, как его реализует сервер: манёвр двигает **всех своих** бойцов, каждого не больше одного раза, буст добавляется каждому (`gameplay.dto.ts:131-133`). Ходы применяются в порядке `moves[]`.

Рекомендуемая модель черновика на клиенте:

```
draft.moves: упорядоченный список {fighterId, path}   // порядок = порядок отправки
workFighters(i) = исходные бойцы, к которым применены moves[0..i-1]
reach(i)  = BFS(board, workFighters(i), mover_i, allowance_i)
path_i    = canonicalPath(board, workFighters(i), mover_i, dest_i)  // §3.4
```

Как это работает:

- При изменении хода k пересчитать ходы k+1..n. Если какой-то из них стал недостижим, пометить его «конфликт» (а не удалять молча) и показать причину. Ориентир — правило UX-спеки «путь обрезается до достижимого» (`02-ux-ui-spec.md:821`).
- **Порядок ходов** виден игроку: номер на линии пути и порядок в списке бойцов HUD. Игрок может его менять, например перетаскиванием в списке или клавишами. Пример, где порядок важен: союзник A стоит на клетке X и уходит, после этого B встаёт на X. Если A ходит первым — законно, если B первым — нет. Сейчас клиент такой ход запрещает (F2).
- Проверка «две цели на одной клетке» (`S09ManeuverUi.cpp:618-627`) становится частным случаем: занятость конечной клетки в `workFighters`.
- «Обмен местами» двух союзников за один манёвр невозможен при любом порядке: первый не может закончить ход на клетке второго. Нужен понятный текст отказа.
- Сложность: n ≤ 4 бойцов (Medusa + 3 гарпии) × BFS на ≤ 400 узлах. Пренебрежимо мало (оценка).

### 3.4. Детерминированный tie-break (одинаковый на клиенте и сервере)

Зачем он нужен, хотя правила от пути сейчас не зависят:

1. Анимация чужого хода, если сервер не присылает путь (резервный вариант F7).
2. Стабильная линия превью: при одинаковых входных данных она не «прыгает».
3. Golden-фикстуры паритета, которые сравнивают пути бит в бит.
4. Будущие способности, которым важен путь (например, «прошёл рядом»). Сейчас таких нет: `applyMoveReactions` видит только from/to (`game-action-executor.service.ts:469-497`).

Red Blob отмечает, что на однородной сетке много одинаково коротких путей и алгоритм выбирает любой. Путь получается коротким, но выглядит плохо. Для BFS там предлагают «шахматный» порядок соседей по `(x + y) % 2`. Для Dijkstra и A* порядок вставки игнорируется приоритетной очередью, поэтому цену немного варьируют ([A* Implementation, §6.2 Ugly paths](https://www.redblobgames.com/pathfinding/a-star/implementation.html), 2026-10-03).

**Предлагаемая спецификация канонического пути (для обсуждения в плане):**

```
canonicalPath(board, fighters, mover, dest):
  dist = BFS-слои от старта по правилам §3.2 (без обрезки по allowance)
  если dest недостижим или dist[dest] > allowance -> нет пути
  путь собирается от dest назад:
    cur = dest
    пока cur != start:
      кандидаты = соседи(cur), у которых dist == dist[cur]-1
                  и в которые можно войти как в промежуточную клетку
                  (или это start)
      prev = min(кандидаты, по ключу K)
      ...
  K(сетка)     = (y, x) лексикографически         // не зависит от порядка соседей
  K(топология) = spaceId лексикографически ('M01' < 'M02'), при равенстве (y, x)
```

- Ключ не зависит от порядка `neighbours()`. Расхождение трёх серверных констант (F6) и клиентского +X/−X/+Y/−Y на путь не влияет.
- Шахматный порядок даёт более «красивую» лестницу на сетке. Для доски 20×20 это эстетика, а не правило. Рекомендация: начать с простого ключа. Если на Cobble City линии будут выглядеть как «Г» вместо лестницы, заменить ключ на шахматный, одинаково на обеих сторонах. Решение за владельцем плана.
- На графе оригинальных карт ветвлений с равной длиной мало (средняя степень 2.7–3.2, подсчитано по фикстурам), так что ключ почти не нужен. Но пересечение линий без развилки M22-M29 × M25-M26 (`board-topology.ts:9-10`) — два независимых ребра. Линия превью не должна выглядеть как поворот на перекрёстке: это вопрос отрисовки, §5.2.

### 3.5. Паритет клиента и сервера

Сейчас клиент читает топологические фикстуры бэка `backend/prisma/fixtures/boards/<key>.topology.json` в UE-тестах (`S08BoardGraphTests.cpp:332-376`, `:780-784`). Это хорошая база. Предлагается добавить **golden-фикстуры движения** (формат `unmatched.move-fixture/1`, предложение):

```json
{ "board": "marmoreal" | {inline lattice},
  "fighters": [{ "id","ownerId","position":{"x","y"},"health","isDefeated","movement","effects":[] }],
  "draft": [{ "fighterId","dest":{"x","y"} }], "boost": 0..N,
  "expect": { "reach": {"<fighterId>": [[x,y],...]},
              "paths": {"<fighterId>": [[x,y],...]},
              "server": "ok" | "<code>" } }
```

- Jest прогоняет фикстуру через `validateManeuver` и `executeManeuver` (`server`) и через референсную TS-реализацию канонического пути.
- UE Automation прогоняет ту же фикстуру через `FS08BoardModel` и `FS09CommandUi` (`reach`, `paths`, итоговая команда).
- Обязательные кейсы: всё из §7 (граничные значения) плюс F1–F4 и F10.
- Дополнительно: property-тест на случайных досках (сид в имени теста) — клиентское множество `reach` совпадает с серверным `getValidMoveTargets` (`movement.service.ts:113-153`) плюс своя клетка. Сервер не включает старт (`:116-121`), клиент включает (`S08BoardModel.cpp:333`); различие нужно зафиксировать в фикстуре.

## 4. Тема 2. Превью и авторитетное подтверждение

### 4.1. Модель

- Сервер авторитетен. Клиент строит черновик **только из применённого снапшота**. Так уже сделано (`S09ManeuverUi.h:1-23`), и это совпадает с ADR («клиент считает подсказку, сервер проверяет», `02-ux-ui-spec.md:711`).
- Предсказание на клиенте в духе Gambetta (нумерация команд, применение их локально с последующей сверкой и повтором неподтверждённых, [Client-Side Prediction and Server Reconciliation](https://gabrielgambetta.com/client-side-prediction-server-reconciliation.html), 2026-10-03) рассчитано на непрерывный ввод в реальном времени. Здесь оно **не нужно**:
  - манёвр — одна дискретная команда раз в несколько секунд;
  - после `beginManeuver` добор скрыт и уже зафиксирован;
  - манёвр может вызвать реакции чужих героев (`applyMoveReactions`), которые клиент не моделирует;
  - контракт запрещает повтор при неизвестном исходе (GD-037).

  Оптимистичное перемещение фигурки до ответа потребовало бы отката при отказе. При задержке сервера порядка сотен миллисекунд это даёт мелькание без выигрыша.
- Что можно делать «оптимистично» (чистая презентация, без изменения модели):
  - сразу после Enter: зафиксировать линию пути (стиль «отправлено»), призрак оставить на месте назначения, ввод черновика заблокировать (`bCommandInFlight`);
  - по авторитетному снапшоту: фигурка едет по пути (CUE-007), призрак исчезает;
  - при отказе: призрак и линия гаснут, черновик восстанавливается из `pendingManeuver`, который всё ещё открыт, в баннере причина (`02-ux-ui-spec.md:756`).

### 4.2. Порядковые номера и идемпотентность

| Этап | Защита | Где |
|---|---|---|
| `beginManeuver` | `expectedSequenceNumber == seq`, иначе отказ. Повтор после успеха получает отказ: seq ушёл вперёд, `pendingManeuver` уже открыт | `game-action-executor.service.ts:1651-1658` |
| `maneuver` | `maneuverId == pendingManeuver.id`, после успеха `pendingManeuver` очищается | `:1708-1711`, `:1811` |
| Ответ потерян | recovery-lock, команда не повторяется; ждём свежего снапшота | `S08FlowController.cpp:1639-1643`, `:1729-1733` |
| Дубли HTTP-эхо и WS-событий | seq-guard: одинаковый seq мержится, cue не повторяется | `S08FlowController.cpp:1327-1358`; `16-network-contract.md:16-19` |

Вывод: новых механизмов идемпотентности для подбора хода не требуется. `maneuver` не принимает `expectedSequenceNumber`. Это достаточно, пока между begin и maneuver состояние может менять только сам игрок. Не проверено, может ли что-то ещё изменить `pendingManeuver` или позиции между двумя запросами, например таймаут соседней стадии. Если может, в мутацию `maneuver` стоит добавить `expectedSequenceNumber` (ломающее изменение DTO; решение за бэкендом).

### 4.3. Отмена и откат

| Момент | Что можно отменить | Как |
|---|---|---|
| Выбран боец, цели нет | всё | Esc / ПКМ: локально |
| Цели и путь нарисованы, `beginManeuver` ещё не отправлен | всё | локально. В наследном потоке F5 begin уходит сразу по клику — после унификации так не будет |
| После `beginManeuver` (карта добрана) | черновик (цели, буст, порядок) | `CancelDraft`, локально. **Добор и потраченное действие не возвращаются** (`S09ManeuverUi.h:16-18`); можно вернуться и подтвердить ноль ходов |
| После Enter, ответа ещё нет | ничего | in-flight lock |
| После подтверждения | ничего (правила настольной игры) | — |

Ориентир для UX. В Into the Breach ход меха можно отменить, пока он не совершил действие, и раз в раунд можно сбросить весь ход ([Kotaku review](https://kotaku.com/into-the-breach-the-kotaku-review-1823365331), 2026-10-03). Destructoid пишет о кнопке Reset Turn раз за миссию ([Destructoid review](https://www.destructoid.com/review-into-the-breach/), 2026-10-03; источники по частоте расходятся). У нас аналог «отмены до действия» — локальный черновик. Сброса после подтверждения нет: сервер авторитетен, добор открыт.

Рекомендация: подтверждение двухступенчатое. Клик по цели только **ставит** её, отправляет — отдельный Enter или кнопка. Так уже требует `02-ux-ui-spec.md:789`, а наследный поток F5 это нарушает. Отдельное «Начать манёвр» (begin = добор) должно показывать, что это необратимо.

### 4.4. Как ход видит соперник (контракт)

Предложение `metadata.lastManeuver` — публичное аддитивное поле, обратно совместимое по `16-network-contract.md:221-226`:

```json
"lastManeuver": {
  "seq": 128, "playerId": "...",
  "moves": [ { "fighterId": "...", "path": [{"x":3,"y":2},{"x":4,"y":2}] } ],
  "boostCardId": null
}
```

- Пишется в `executeManeuver` при том же +1 к seq (`game-action-executor.service.ts:1782-1785`). Очищается или заменяется следующим манёвром.
- Путь в настольной игре публичен: соперник видит, как двигают фигурку. Поэтому viewer-проекция не нужна. Карта буста после сброса тоже публична, но проверка приватности (§5 контракта) обязательна.
- Клиент строит cue `FighterMoved` с `Path`: берёт путь из `lastManeuver`, если `lastManeuver.seq == Snapshot.SequenceNumber`; иначе from/to плюс канонический путь (§3.4); иначе прямая. Ходы в одном seq идут в порядке `moves[]`.
- Перемещения от эффектов (MOVE/PLACE из pendingEffects) тоже требуют пути. Для MOVE — тот же механизм или канонический путь. Для PLACE пути нет: телепорт с отдельным cue. Вне рамок этого документа, отмечено как открытый вопрос.

## 5. Тема 3. Презентация в UE 5.8

### 5.1. Подсветка достижимого

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| Актор + MID на клетку (сейчас) | просто | спавн и уничтожение N акторов при каждом выборе; N draw calls (оценка) | заменить |
| **ISM с per-instance custom data** | один компонент, один draw call на материал; состояние клетки (достижима, на пути, наведение, недоступна, «только с бустом») — float-ы инстанса | custom data читается в вертексном шейдере; в пиксельный передаётся через VertexInterpolator ([unrealcommunity.wiki](https://unrealcommunity.wiki/using-per-instance-custom-data-on-instanced-static-mesh-bpiygo0s), 2026-10-03) | **рекомендуется**: пул на max(клеток) инстансов, меняются только `SetCustomDataValue` и видимость |
| Custom Primitive Data на отдельных мешах | параметры живут на примитиве, а не в MI; меньше draw calls у одинаковых объектов ([Storing Custom Data in Materials Per-Primitive](https://dev.epicgames.com/documentation/en-us/unreal-engine/storing-custom-data-in-unreal-engine-materials-per-primitive), 2026-10-03) | всё равно компонент на клетку | для фигурок (уже принято: `M_UM_Figure` FxFlash/Rim/Fade, `CUE-DISPATCHER.md:42`) |
| Deferred decals | ложатся на неровный рельеф диорамы | цена растёт с площадью экрана; сортировка большого числа декалей с разными sort-значениями бьёт по производительности ([Decal Materials](https://dev.epicgames.com/documentation/en-us/unreal-engine/decal-materials-in-unreal-engine), 2026-10-03); на круглых пространствах карты-иллюстрации выигрыша нет | только если 3D-остров (P8 «путь 1») даст рельеф под пространствами. Не проверено |
| Material Parameter Collection | глобальные скаляры и векторы: время пульса, позиция курсора, цвет команды; до 1024 скаляров и 1024 векторов ([Using MPC](https://dev.epicgames.com/documentation/unreal-engine/using-material-parameter-collections-in-unreal-engine), 2026-10-03) | не хранит состояние на клетку | **в паре с ISM**: общий пульс и «фонарик» под курсором |
| Niagara | красиво, частицы | CPU/GPU-стоимость, недетерминизм кадров доказательств без seed | только акцент: вспышка цели, пыль на финише (CUE-007) |

Требования UX к форме: не только цвет — глиф «шаг» и форма контура (`02-ux-ui-spec.md:706`, `:868`). В ISM это второй ISM-слой глифов или атлас в одном материале с индексом из custom data.

Отдельное состояние **«достижимо только с бустом»**. BFS с `allowance = movement + maxBoostInHand` минус BFS без буста даёт кольцо клеток, которое показывается пунктиром. Это подсказывает, когда буст нужен. Похожий приём в XCOM 2: синяя зона — одно действие, жёлтая — оба ([Gamepressure: XCOM 2 Movement](https://www.gamepressure.com/xcom2/movement/za848f), 2026-10-03). Значение буста карт в своей руке известно только владельцу, утечки нет.

### 5.2. Линия пути

- `USplineComponent` по центрам клеток пути (`CellToWorld`). На каждый сегмент — `USplineMeshComponent` из пула. `SetStartAndEnd(StartPos, StartTangent, EndPos, EndTangent)` деформирует один меш между двумя точками ([USplineMeshComponent API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/USplineMeshComponent), 2026-10-03). Длина пути ≤ movement + буст: десяток сегментов, пул фиксированного размера.
- На графе карты связь может перекрывать несколько шагов решётки (`S08BoardModel.h:18-21`). Сегмент строится по `CellToWorld` двух связанных пространств, то есть **прямой по нарисованной линии карты**, а не по решётке. На пересечении без развилки (M22-M29 × M25-M26) касательные должны идти вдоль своего ребра. Иначе сплайн «загнёт» линию в соседнее ребро.
- Касательные: на сетке — по направлению сегмента (длина ≈ 0.3–0.5 клетки, оценка), чтобы углы были мягкими, но клетки не «срезались».
- Наконечник-стрелка на последнем сегменте. Цифра шага или остатка очков — бейджем у курсора (UMG) или мировым текстом.
- Альтернатива: Niagara Ribbon с точками пути из data interface ([Beam effect in Niagara](https://dev.epicgames.com/documentation/en-us/unreal-engine/how-to-create-a-beam-effect-in-niagara-for-unreal-engine), 2026-10-03). Даёт анимированный поток, но дороже и сложнее в детерминированных кадрах. Рекомендация: SplineMesh как основа, Niagara — опциональный слой.
- Для анимации фигурки та же сплайн-кривая даёт параметризацию по длине: `GetLocationAtDistanceAlongSpline` и `GetSplineLength` ([UE 4.27 API](https://docs.unrealengine.com/4.27/en-US/API/Runtime/Engine/Components/USplineComponent/GetLocationAtDistanceAlongSpline/index.html), 2026-10-03; в 5.8 сигнатура не проверена).

### 5.3. Призрак фигурки

- Лёгкий актор с тем же мешем фигурки, без плашки и коллизии, на клетке-цели. Нужен только для выбранного бойца, либо для всех нарисованных ходов — тогда их максимум 4.
- Материал: **dithered opacity mask** через параметр `Fade` Custom Primitive Data (индекс 11 зарезервирован, `CUE-DISPATCHER.md:42`), а не translucent. Translucency с Lumen хуже по сортировке и стоимости — общеизвестная практика, в документации UE в рамках этого исследования не проверено.
- Поворот призрака: в направлении последнего шага пути (доворот, §5.6).
- Для сайдкиков, которые используют одну модель (3 гарпии), призрак обязан нести номер (`Label`, `S08BoardModel.cpp:564-581`).

### 5.4. Наведение и трассировка

- Сейчас клик трассируется по `ECC_Visibility` (`S08FlowGameMode.cpp:994`). Клетки и фигурки блокируют этот канал (`S08BoardActor.cpp:105-117`, `S08FighterActor.cpp:84-136`). Риск: декор окружения (3D-остров, FX) тоже блокирует Visibility.
- Рекомендация: собственный trace channel `BoardPick` (default Ignore). Его блокируют только плоскость или коллайдер доски (`MapPickBox`, `S08BoardActor.cpp:2024`) и капсулы фигурок. Каналов до 18 своих, включая object и trace ([Collision settings](https://dev.epicgames.com/documentation/unreal-engine/collision-settings-in-the-unreal-engine-project-settings); [Add a custom trace type](https://dev.epicgames.com/documentation/unreal-engine/add-a-custom-trace-type-to-your-project-in-unreal-engine), 2026-10-03). `GetHitResultUnderCursorByChannel` с этим каналом.
- Топология: точка на плоскости, затем `WorldToSpace` (уже есть, `S08BoardModel.cpp:277-293`). Между кругами клетки нет, поэтому линия превью не меняется и курсор нейтральный.
- Наведение пересчитывается, только когда меняется клетка под курсором (кэш `HoverCell`). Тогда путь берётся из `parent[]` (§3.1), без нового BFS.
- CUE-001: не чаще одного тика за 150 мс (`07-animation-vfx-audio.csv:2`).

### 5.6. Анимация перемещения фигурки

| Вариант | Как | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| **Скольжение по пути** | интерполяция позиции по сплайну пути, easing на старте и финише | D-11 так и требует; не нужны клипы; работает с мешем-манекеном | без подскока выглядит как «скользящая шахматная фигура» | **база** |
| Подскок по шагам | на каждом шаге арка по Z (синус), высота ~8–12 uu (оценка, подобрать в live tune) | читается как «шаг» в настольной игре, считается клетками | на графе разная длина рёбер: арку надо масштабировать по длине или вести с постоянной скоростью | **опция**, включена по умолчанию после проверки |
| Walk-цикл на месте + следование по сплайну | in-place клип, root bone зафиксирован (Force Root Lock, [Root Motion](https://dev.epicgames.com/documentation/en-us/unreal-engine/root-motion-in-unreal-engine), 2026-10-03) | живее | нужен клип на героя, а D-11 и бриф его исключают (`18-animation-production-brief.md:40`) | не в MVP |
| Root motion | движение задаёт анимация | физически точнее | длина шага у разных рёбер разная; синхронизация с клетками; клипы на героя | не рекомендуется |

Тайминги и правила:

- База CUE-007: 280 мс на клетку (`07-animation-vfx-audio.csv:8`, веб-референс). При пути в 8–9 шагов это 2.2–2.5 с. Предложение: **ограничить общую длительность** (например, ≤ 1.4 с, при длинном пути сокращать время на шаг; число на утверждение), чтобы ход соперника не «тянулся». Ввод при этом не блокируется (`blocks_input: no`).
- Доворот (turn-in-place): yaw интерполируется к направлению следующего сегмента за ~80–120 мс (оценка). Без клипа — простой поворот корпуса. После финиша — возврат к «лицом к центру» (сейчас yaw задаётся по половине поля, `S08FighterActor.cpp:550-561`).
- Несколько бойцов одного манёвра: **последовательно в порядке `moves[]`** с перекрытием ~30 % (оценка). Иначе гарпии «проходят друг через друга». Порядок нужен из `lastManeuver` (F7).
- Новое событие той же фигурки — `jump_to_final`. Реконнект — `skip`, фигурка сразу на финале. Reduced motion (UI-ACC-006) — `snap`, 0 мс (`CUE-DISPATCHER.md:46-47`, `:72`). Основание: WCAG 2.3.3 (AAA) — анимацию движения, вызванную взаимодействием, можно отключить, если она не существенна ([W3C](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions.html), 2026-10-03).
- **Состояние не ждёт анимации** (`CUE-DISPATCHER.md:24-26`). Логическая позиция фигурки = снапшот. Визуальная позиция догоняет её, а хит-тест клика идёт по логической клетке.

### 5.7. Камера

- D-10: фиксированный угол и зум колесом (`00-vision-and-scope.md:104`). Автокадрирование пути — мягкое: если концы пути выходят за безопасную рамку экрана (например, 10 % от края, оценка), камера плавно сдвигается (pan) без изменения угла. Зум не трогается, если игрок задал его сам.
- Чужой ход: камера не дёргается. Если путь вне экрана, у края показывается индикатор-стрелка (UMG). Это снижает укачивание и согласуется с reduced motion.

### 5.8. Связь с cue-диспетчером

- Вход `FS08CueDispatcher::Feed` получает `(CUE-007, fighterId, seq, params.path[])` (`CUE-DISPATCHER.md:24`, `:138-139`). `FS08Cue` нужно расширить полем `TArray<FIntPoint> Path` и порядком внутри seq.
- Дедупликация `(cueId, subject, seq)` (D2) корректна для нескольких бойцов: subject у них разный.
- Пыль на финише и «следы» на промежуточных клетках из CUE-007 — Niagara-пул, CPU, с детерминированным seed (`CUE-DISPATCHER.md:45`).

### 5.9. Бюджет производительности

Ориентиры проекта:

- 60 FPS для упакованного клиента; ACC-022 — 1080p/60 (`AGENTS.md`, раздел Unreal GPU load; `00-vision-and-scope.md:102`);
- демо из двух клиентов — по 30 FPS на процесс;
- dynamic resolution как лимит не использовать.

| Элемент | Бюджет (оценка, проверить `-Bench`) |
|---|---|
| BFS + путь на изменение черновика | < 0.1 мс CPU game thread |
| Подсветка (ISM, ≤ 400 инстансов) | 1–2 draw call; обновление custom data только у изменившихся инстансов |

| Niagara-акценты | ≤ 2 систем одновременно на клиента, CPU-sim |

- Сравнивать стоимость только через `render_bench.py` (`-Bench`, без ограничения FPS), не по `gpuMs` в ограниченном режиме (`AGENTS.md`, Rendering).

## 6. Тема 4. Подсказки ходов и бот

### 6.1. Что есть

Бот (`ai-decision.service.ts`):

- жадно сближается с ближайшим врагом по полю дистанций, двигает только героя, без буста (§1.4);
- PickApproachDestination на клиенте делает почти то же для автодрайвера S09AUTO (`S08BoardModel.h:223-239`);
- PickRangedPosition ищет позицию с целью только через зону для ranged-бойца (`S09ManeuverUi.h:166-178`).

Получается три близкие реализации «куда идти», и все без оценки угрозы.

### 6.2. Рекомендуемая модель оценки (Dijkstra maps и influence maps)

Приём из Brogue (Brian Walker):

- несколько карт дистанций (Dijkstra maps) от разных целей;
- ход выбирается по взвешенной сумме карт с коэффициентами «желаний»;
- карта бегства — это карта дистанций, умноженная примерно на −1.2 и пересчитанная;
- карты пересчитываются только при изменении условий и общие для всех юнитов.

([RogueBasin: The Incredible Power of Dijkstra Maps](https://www.roguebasin.com/index.php/The_Incredible_Power_of_Dijkstra_Maps), 2026-10-03.) Поле дистанций у нас уже есть (`board-topology.ts:280-296`), а Red Blob показывает такое поле как основу «flow field» для многих юнитов ([Tower Defense flow field](https://www.redblobgames.com/pathfinding/tower-defense/), 2026-10-03).

Признаки клетки-кандидата c для бойца f (все — по публичной информации):

| Признак | Как считать | Вес (стартовое предложение) |
|---|---|---|
| `canAttackAfter` | после хода есть цель: melee — соседняя, ranged — соседняя или общая зона (`IsTargetInAttackRange`, `S09ManeuverUi.h:132-134`) | +10 |
| `distToNearestEnemy` | мультиисточниковое поле от живых врагов, бойцы не мешают (`S08BoardModel.cpp:455-481`) | −1 за шаг |
| `threat` | число врагов, которые в свой ход могут атаковать c: movement врага + **публичная** оценка буста (максимум из уже сброшенных карт либо константа) + досягаемость. Рука соперника скрыта, поэтому только оценка | −3 за каждого (герой ×2) |
| `zoneControl` | c в зоне, общей с вражеским ranged-бойцом, или наоборот | ± по роли |
| `protectAlly` | c рядом с раненым героем или перекрывает путь к нему | +2 |
| `stepsUsed` | длина канонического пути | −0.1 (тай-брейк, лучше короче) |

- Финальный тай-брейк: канонический ключ клетки (§3.4).
- Для манёвра из нескольких бойцов: жадно по одному в порядке «герой → сайдкики», каждый на `workFighters` (§3.3). Перебор всех сочетаний не нужен: на 4 бойцах и ≤ 40 кандидатах на бойца он возможен, но избыточен для подсказки (оценка).

### 6.3. Где жить коду

- **Сервер**: чистая функция `scoreMoves(state, playerId, options) → [{fighterId, dest, path, score, reasons[]}]` в `game-engine/ai/` (имя — предложение). Её используют:
  - `ai-decision.service.ts`: бот берёт лучшую комбинацию, а буст выбирает по разнице «с бустом / без»;
  - новый **опциональный** GraphQL-запрос `moveHints(gameId, maneuverId)`. Отвечает только владельцу открытого `pendingManeuver`, считает по viewer-проекции, без руки соперника.
- **Клиент**: только показывает подсказку. Топ-1…3 клетки с меткой «подсказка» (отдельный глиф) и причиной (`reasons[]` → строки). Кэш по `seq + maneuverId`. Подсказка **никогда не подтверждает ход** и не ставит цель сама. Включение — настройка (по умолчанию выкл. в PvP, вкл. в VS_AI; решение за дизайном).
- Почему не клиентское зеркало: сейчас у клиента уже два зеркала логики (PickApproach, PickRanged), третье увеличит долг паритета. Цена — один HTTP-запрос на открытие черновика. Это ниже порога заметности, потому что черновик открывается после begin, который и так ходит по сети.

### 6.4. Ориентиры UX подсказок

- Into the Breach показывает намерения врагов и порядок, в котором события произойдут в конце хода ([Kotaku review](https://kotaku.com/into-the-breach-the-kotaku-review-1823365331), 2026-10-03). Аналог у нас — показать, **кто сможет атаковать клетку в следующий ход** (признак `threat`), прямо на подсветке достижимого (иконка-глаз). В XCOM похожую роль играет предупреждение, что точка назначения под наблюдением ([Pixel Twelve guide](https://pixeltwelve.com/guides/xcom-2-beginner-guide-first-mission-cover-overwatch), 2026-10-03; детали не проверены).
- Полная детерминированность Into the Breach у нас недостижима: у соперника скрытая рука и бусты. Значит, угроза — «возможно», а не «точно», и это надо прямо писать в подсказке.
