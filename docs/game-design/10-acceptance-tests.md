## Часть 1. Обязательный минимум брифа §15

### QA-001. Два игрока входят в одну комнату, выбирают героев, начинают одну партию

- Связи: GDD-001, GDD-002, UI-SCR-LOBBY, UI-SCR-ROOM, INT-012, TASK-025/TASK-034; исключение матчмейкинга — см. «Исключённые сценарии».
- Подготовка: сервер `localhost:3000` поднят; два аккаунта (GAP-018/Q-005); клиенты UE-сборки.
- Участники: игрок A (хост), игрок B (гость).
- Given: A и B залогинены, находятся в лобби.
- When: A создаёт приватную комнату 1×1 (Cobble City), передаёт код, B входит по коду; A выбирает Medusa, B — King Arthur; оба «Готов»; A нажимает «Начать».
- Then: оба клиента переходят в партию с одинаковыми `gameId`, фазой ACTION_MANEUVER, `currentTurnPlayerId` = один и тот же игрок у обоих, у каждого — 5 карт в руке, фигурки на стартовых клетках.
- Ожидаемое состояние: статус IN_PROGRESS; подписки обоих дают одинаковые sequenceNumber на каждом шаге.
- Визуальный результат: у A — Медуза + 3 гарпии; у B — Артур + Мерлин; баннер «Ваш ход» ровно у одного.
- Доказательство: скриншоты обеих сторон одного момента + лог мутаций (createGame c idempotencyKey, joinGame, selectHero×2, startGame); равенство seq.

### QA-002. Действие вне своего хода объяснено и не меняет состояние

- Связи: GDD-016, P2, UI-INP-008, CUE-004, TASK-027; словарь причин `why.not.your.turn` (02 §4.2).
- Подготовка: активная партия; ход соперника.
- Участники: один проверяющий (в роли игрока вне хода).
- Given: `currentTurnPlayerId` ≠ я, фаза ACTION_MANEUVER.
- When: игрок кликает по своему бойцу и подсвеченную клетку/кнопку «Конец хода»/разыгрываемую карту.
- Then: ни одна мутация не отправляется; показывается причина («Не ваш ход» / «нет действий» / соответствующая).
- Ожидаемое состояние: seq не изменился; actionsRemaining без изменений.
- Визуальный результат: встряска курсора/иконка «стоп» + всплывающая причина (CUE-004); заблокированные кнопки с тултипом-причиной.
- Доказательство: сетевой лог пуст (0 мутаций за время проверки) + скриншот причины.

### QA-003. Манёвр расходует ресурсы только после подтверждения сервера; повторный клик не создаёт второе действие

- Связи: GDD-004, INT-005 (одна in-flight), INT-006 (без оптимистики), INT-009 (maneuver, не moveFighter; GAP-006), CUE-007, TASK-024.
- Подготовка: мой ход, 2 действия, боец с достижимыми клетками.
- Участники: один проверяющий.
- Given: выбран боец, построен путь, кнопка подтверждения активна.
- When: игрок дважды быстро нажимает «Подтвердить» (и повторно кликает по клетке во время полёта запроса).
- Then: отправлена ровно одна мутация maneuver; до HTTP-ответа/подписки позиции фигурок, счётчик действий и рука НЕ меняются; после — позиции изменены, `actionsRemaining` −1, рука +1 карта.
- Ожидаемое состояние: seq +1 ровно один раз; повторное нажатие блокировано («Отправка действия…»).
- Визуальный результат: «Отправлено…» → скольжение фигурки (CUE-007, 280 мс/клетка), добор карты (CUE-005).
- Доказательство: лог сети (1 запрос maneuver) + дифф снапшотов до/после.

### QA-004. Атака/защита/результат и обязательный дополнительный выбор видны правильному игроку

- Связи: GDD-005/GDD-006/GDD-008/GDD-010, UI-HUD-COMBAT, UI-HUD-PENDING, CUE-008/CUE-009/CUE-010/CUE-011, GAP-002; сценарий B файла 01.
- Подготовка: партия, ход игрока A (Arthur), боец B (Medusa) достижим.
- Участники: A (атакующий), B (защитник).
- Given: A выбрал атаку Skirmish + буст Momentous Shift (GDD-010).
- When: A подтверждает атаку; B видит панель защиты, выбирает Hiss and Slither; резолв; после-эффект Skirmish порождает MOVE-выбор у A.
- Then: панель защиты и таймер — только у B; карта атаки/буст не видны B до резолва (только значение); результат урона и баннер MOVE — у A (у B — факт урона на своей фигурке); управление возвращается правильному игроку (после исчерпания действий — B).
- Ожидаемое состояние: COMBAT → COMBAT_RESOLVE → ACTION_MANEUVER; `combatInfo.attackValue` = карта+буст с объявления (GAP-002).
- Визуальный результат: выпад атакующего (CUE-008), пульс защиты (CUE-009), раскрытие значений (CUE-010), «−1» над Медузой (CUE-011), баннер выбора перемещения у A.
- Доказательство: двухсторонние скриншоты фаз + лог событий ATTACK_INITIATED/DEFENSE_PLAYED/COMBAT_RESOLVED; у B отсутствует трафик с составом буст-карты до резолва.

### QA-005. Закрытые карты соперника не раскрываются нигде

- Связи: GDD-011, P4, 00 §10 п.5, UI-SCR-INSPECT, UI-HUD-PANEL-OPP, UI-INP-006 («просмотр ≠ действие»), CUE-005; фильтрация — ФАКТ 04:427-433.
- Подготовка: активная партия.
- Участники: проверяющий (сторона A).
- Given: у соперника карты в руке.
- When: игрок наводит/открывает инспектор на чужой карте руки, чужой колоде, открывает журнал боя, панель сброса.
- Then: все пути показывают только рубашки/«Скрытая информация»/счётчики; ни одно поле (значение, тип, эффект, текст) не заполнено данными каталога по известному id; просмотр не порождает мутаций.
- Ожидаемое состояние: wire-данные руки соперника = `name:"???"`, `isVisible:false`; topCard чужой колоды отсутствует.
- Визуальный результат: рубашки UI-CARD-BACK; инспектор в режиме «Скрытая карта».
- Доказательство: автотест «нулевой сетевой лог» просмотра + инспекция полученных JSON (нет значений чужих карт).

### QA-006. Отключение после отправки действия и возврат не расходуют карту повторно

- Связи: GDD-013, INT-004 (gap-протокол), INT-005 (никогда вслепую), UI-SCR-RECONNECT, сценарий C файла 01, TASK-033.
- Подготовка: партия; способ оборвать сеть (брандмауэр/отключение интерфейса).
- Участники: A (проверяющий, атакующий), B (оппонент или бот).
- Given: A отправил attack (карта уже списана сервером), ответ не получен, сеть падает.
- When: клиент показывает оверлей RECONNECT, сеть возвращается.
- Then: клиент НЕ повторяет attack; выполняет gameSequence → eventsSince/gameState → переподписка; партия показывается в фактической фазе (COMBAT), карта атаки в сбросе ровно в одном экземпляре, ни одна карта не потрачена дважды.
- Ожидаемое состояние: seq клиента = seq сервера; дубликаты отброшены.
- Визуальный результат: «Пропущено событий: N» совпадает с разницей seq; партия продолжается.
- Доказательство: лог мутаций (один attack за партию) + счётчики колоды/сброса до/после + дамп финального состояния.

### QA-007. Дубль HTTP+WS не проигрывает урон/анимацию дважды (расширение: ровно одна анимация урона)

- Связи: INT-003, CUE-011, TASK-023/TASK-028; факт дубля — 04:530.

- Доказательство: счётчик запусков CUE-011 = 1 в логе; значение HP в HUD = серверному.

### QA-012. Отсутствующий ассет заменяется понятным fallback и не ломает партию

- УТОЧНЕНИЕ (по заданию пакета): проверяются ОБА уровня fallback-иерархии INT-018 — манекен (модель) и рамка-заглушка (арт карты).

- Given: партия начата с «повреждённым» контентом.
- When: состояние загружено; игрок выбирает фигурку без модели, открывает карту без арта.

### QA-013. Изменение контента в админке проявляется согласно выбранной политике обновления

- Связи: INT-014/INT-017 (политика: MVP = пересборка), GAP-021, UI-SCR-BOOT (сверка contentVersion), TASK-062.
- Подготовка: сервер + админка; packaged-сборка; выбран «разрешённый контент» (например, описание способности героя или значение карты — поля, входящие в живое состояние).
- Участники: проверяющий с доступом к админке.
- Given: клиент подключён и содержит baked-версию контента.
- When: в админке изменяется разрешённое поле (например, HP гарпии/текст карты), изменения сохранены; (а) клиент продолжает партию без пересборки; (б) клиент пересобирается/перезапускается.
- Then: (а) клиент не падает и не показывает противоречивых данных: в партии значения приходят из состояния сервера; ассеты/baked-каталог не меняются; предупреждение «каталог изменился — требуется пересборка» при расхождении contentVersion допустимо; (б) после пересборки новые данные согласованы с ассетами.
- Ожидаемое состояние: политика INT-017 соблюдена: без пересборки меняется только то, что живёт в состоянии; с пересборкой — всё.
- Визуальный результат: скриншот «до/после» в админке и в клиенте; лог сверки contentVersion.
- Доказательство: журнал изменений админки + сравнение дампов состояния до/после.

### QA-014. Packaged build запускается без редактора и подключается к настроенному адресу сервера

- Связи: INT-011/INT-014, TASK-060/TASK-061, GAP-018 (аккаунты), 08 §6.4 (измерения только packaged).
- Подготовка: чистая машина/профиль Windows без UE-редактора; сервер на настроенном адресе (не localhost по умолчанию — адрес задаётся конфигом сборки); инструкция TASK-061.
- Участники: проверяющий «посторонний» (не разработчик).
- Given: packaged build установлен; адрес сервера настроен.
- When: приложение запускается; выполняется вход; создаётся партия VS_AI.
- Then: вход в лобби без редактора; контент загружен/запечён; подписка жива (индикатор связи зелёный); VS_AI-партия проводится минимум один ход; токены переживают перезапуск (BOOT → LOBBY без пароля); при истёкшей сессии (WS 4403) — тихий refresh → пересоздание WS без потери партии, при неудаче refresh — экран LOGIN «Сессия истекла» (INT-011).
- Ожидаемое состояние: 0 обращений к Supabase-URL моделей (GAP-013); сетевой трафик только к настроенному серверу.
- Визуальный результат: скриншот лобби и партии с packaged-сборки; версия/адрес в углу BOOT.
- Доказательство: лог запуска + захват трафика (только настроенный адрес) + скриншоты; FPS-замеры packaged (08 §6.4).

## Часть 2. Дополнительные проверки (бриф §15 «пары реальных случаев» + специфика пакета)

### QA-101. Гарпия с 1 HP умирает с одного урона

- Связи: 01 §6.1, GDD-012, ASSET-HARPY-001, CUE-013, 05-content-matrix (medusa-sidekick-harpy).
- Подготовка: партия; атака значением ≥ 1 доступна по гарпии.
- Участники: атакующий (человек/бот).
- Given: гарпия противника на смежной клетке, HP 1.
- When: резолв боя даёт урон ≥ 1 по гарпии.
- Then: `isDefeated = true`, фигурка убирается (оседание CUE-013 ≤ 950 мс, пропускаемо), партия продолжается (смерть сайдкика не завершает игру).
- Визуальный результат: «−N» и оседание фигурки; плашка гарпии в панели — «погиб» (не исчезает).
- Доказательство: дифф fighters (isDefeated) + скриншот.

### QA-102. Три одинаковых гарпии различимы; адресация — по fighter.id

- Связи: 01 §6.2, GDD-003, TASK-021, UI-HUD-PANEL-*, CUE-002; правило «бриф §11.2: ID бойца ≠ имя».
- Подготовка: партия Medusa (старт — 3 гарпии).
- Участники: игрок за Medusa.
- Given: три гарпии на доске, возможно на соседних клетках.
- When: игрок поочерёдно выбирает каждую; направляет действие (манёвр/атака) на конкретную.
- Then: каждая подписана «Гарпия 1/2/3»; выбор не «перепрыгивает» на одноимённую; мутация уходит с fighter.id именно выбранной; три фигурки не слипаются силуэтами (карточка ASSET-HARPY-001).
- Визуальный результат: три читаемых силуэта с номерами; кольцо выбора на правильной фигурке.
- Доказательство: лог мутаций (разные fighterId) + скриншот К-1 с тремя гарпиями.

### QA-103. Две копии одной карты в руке: инстансные id, тратится выбранная

- Связи: 01 §6.3, UI-INP-007, 02 §10 п.8 (cardId инстансный — сверка TASK-012), GDD-005; буст «той же картой» запрещён на уровне экземпляра (09 §3).
- Подготовка: рука с двумя копиями (например, Second Shot ×2 у Medusa — факты facts-content).
- Участники: один проверяющий.
- Given: в руке копия A и копия B одной карты; у второй карты в руке есть ещё карта для буста.
- When: игрок выбирает копию A и разыгрывает (атака/схема); проверяет буст «той же копией B».
- Then: разыгрывается ровно A (id из HandCard.id), B остаётся в руке; буст картой B — одной из тех же имён — допустим, буст картой A (самой разыгрываемой) — отклоняется с причиной; UI не «склеивает» одинаковые карты.
- Ожидаемое состояние: в мутации передан инстансный id выбранной копии; после подтверждения в руке минус одна конкретная копия.
- Доказательство: дамп handZones до/после + лог мутации (cardId) + скриншоты выделений A и B.

### QA-104. Карта с длинным RU-текстом в инспекторе и руке

- Связи: D-08, D-09, 02 §7.5, UI-SCR-INSPECT, UI-HUD-HAND, GAP-016 (карта без RU-перевода → EN с пометкой).
- Подготовка: рука Medusa с «Гончими могучего Зевса» (эффект 45 символов); карта Arthur без RU-текста (14/16 — GAP-016).
- Участники: проверяющий.
- Given: масштаб UI по умолчанию и 150%.
- When: игрок открывает hover-превью и инспектор обеих карт.
- Then: полный текст читаем (скролл в инспекторе; превью вытягивается вниз, не обрезается); у карты без RU — EN-текст с индикатором «нет перевода»; в мини-карте — свёртка по правилам 02 §7.5.
- Визуальный результат: скриншоты инспектора (RU длинная, EN-fallback) и мини-карты.
- Доказательство: скриншот-набор; текст в инспекторе совпадает с серверными данными карты.

### QA-105. Переход фазы при открытом инспекторе

- Связи: 01 §6.5, GDD-011, UI-SCR-INSPECT (критерий 3), P3/P4.
- Подготовка: активная партия; соперник/бот готов действовать.
- Участники: проверяющий (с открытым инспектором).
- Given: инспектор открыт на карте руки; соперник завершает бой/ход.
- When: приходит снапшот с новой фазой (карта могла уйти из руки — например, вынужденный сброс).
- Then: состояние применяется «под» инспектором (HUD/поле обновляются); инспектор не блокирует применение; если открытая карта ушла из руки — пометка «карта больше не в руке» (не закрывается принудительно); после закрытия HUD согласован со снапшотом.
- Доказательство: скриншот до/после + дифф seq; в логе — применение состояния во время открытого инспектора.

### QA-106. Таймаут защиты: авто-урона НЕТ (GAP-001), обход INT-008 применяет урон

- Связи: GAP-001, INT-007/INT-008, GDD-006, 01 §6.6, CUE-010/011; серверный TODO — ФАКТ 10 §3.3/11:397.
- Подготовка: партия; атака объявлена; защитник бездействует; часы синхронизированы с timeoutAt (INT-007).
- Участники: атакующий (проверяющий), защитник (второй клиент без ввода).
- Given: phase COMBAT, таймер защиты идёт.
- When: окно защиты истекает без playDefense.
- Then: сервер сам переводит в COMBAT_RESOLVE БЕЗ урона; клиент атакующего по локальному таймауту (+страховочная пауза) вызывает resolveCombat → резолв штатный, урон применён, карты в сброс; UI не заявлял «урон применится сам».
- Ожидаемое состояние: HP цели уменьшен на attackValue; ход продолжается по правилам.
- Визуальный результат: раскрытие значений (CUE-010), «−N» (CUE-011) ровно один раз.
- Доказательство: лог: (1) отсутствие урона в серверном auto-resolve, (2) мутация resolveCombat от атакующего, (3) итоговый HP.

### QA-107. VS_AI: ход бота приходит только по подписке

- Связи: D-12, 01 §3, 02 §4.9, GAP-010, UI-HUD-PANEL-OPP («думает…»), TASK-032; ФАКТ 04:533.
- Подготовка: VS_AI-партия; сетевой лог; отладка источника обновлений.
- Участники: игрок против бота.
- Given: игрок завершил ход (endTurn/исчерпание действий).
- When: HTTP-ответ подтверждает конец хода; далее приходят обновления.
- Then: ответ endTurn НЕ содержит ходов бота; действия бота приходят только событиями gameStateUpdated (seq +1, +2, …); индикатор «думает…» висит до первого апдейта; кнопка «Раскрыть бой» у атакующего против бота-защитника недоступна первые секунды окна (GAP-010-обход) — бот успевает сыграть защиту.
- Визуальный результат: пульсирующая плашка «Соперник (ИИ) думает…»; перемещения/атаки бота анимируются по подписке.
- Доказательство: лог: мутации игрока → только ответы подтверждения; изменения состояния бота — только в payload подписок.

### QA-108. Реконнект не проигрывает очередь CUE заново

- Связи: CUE-018 (правило пакета), INT-004, 07 (колонка onReconnect), GDD-013, TASK-033/TASK-028.
- Подготовка: партия с активными эффектами; способ обрыва сети.
- Участники: проверяющий.
- Given: во время хода соперника (2–3 события: манёвр, атака, урон) связь рвётся.
- When: связь возвращается, клиент догоняет пропущенные события.
- Then: старая очередь эффектов НЕ проигрывается (нет повторного «спектакля» урона/перемещений); сцена сразу в финальном состоянии + один резюмирующий тик «позиции обновлены (пропущено N событий)» (CUE-018).
- Визуальный результат: статичная актуальная сцена + короткий тост.
- Доказательство: счётчик запусков CUE за окно реконнекта (только CUE-018) + лог seq.

### QA-109. Rate limit: тост без авторетрая

- Связи: INT-013, 01 §6.7, P2, TASK-024+; лимиты — ФАКТ 04:21.
- Подготовка: партия; отладочный сценарий быстрого повтора действий (или тестовый токен с урезанным лимитом).
- Участники: проверяющий.
- Given: игрок в свой ход.
- When: за минуту отправляется больше разрешённого числа мутаций одной группы (30/мин или 20/мин).
- Then: сервер возвращает ошибку троттлинга; UI показывает тост «Слишком часто — подождите пару секунд»; НЕТ автоматического повтора; выбор игрока сбрасывается с причиной; через паузу действие доступно снова.
- Ожидаемое состояние: состояние партии не изменилось от отклонённых мутаций.
- Доказательство: лог сети (ошибки троттлинга + отсутствие ретрай-запросов) + скриншот тоста.
